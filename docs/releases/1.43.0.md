## 改动凭据

| 改动 | 依据 |
| --- | --- |
| 两项都是 | 1.42.0 部署后的测试号真实收件（用户确认「对得上」）：<br>- 「几点可以入住？」回复末尾多了「暂未找到已核实归属的有效订单，请联系管家核实本次住宿。」；<br>- 「明晚201多少钱」列出 7 个房间，每行重复一遍免责说明；<br>- 「这周末有房吗」逐房写「不可订」。<br>用户指示「修复吧」 |
| 订单口径的根因 | 生产只读查询：测试号只有一张 2026-08 的测试订单（状态 `crm_test`）；全部 239 张订单中，有 144 张退房日已过、状态却不是终态。模型上下文把它们算作进行中，住宿确认只认退房日在今天之后的订单，于是每条回复都触发确认，又找不到订单 |
| 顺带统一的范围 | 按「修一类问题」的原则，两处共用同一个判定函数。`context.py::get_customer_room_number` 也用了同样的旧写法，但没有任何调用方，本版不动 |

## 风险与未覆盖

- 模型上下文不再包含退房日已过的订单。客人问「上次住的房间」这类历史问题时，模型看不到旧订单。历史咨询另有入住备注的查询路径（`latest_stay_note`），不受影响。
- 144 张状态停在非终态的过期订单，本身是订单同步留下的状态问题，本版只是不再把它们当成进行中，没有修改订单数据。
- 房态分组后，客人看不到每个房间各自的日期。同一次查询的日期本来就相同，所以只在开头写一次。

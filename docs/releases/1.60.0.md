## 改动清单

下表省略公共前缀 `src/homestay_bot/integrations/deepseek_client.py`。

| 改在哪里 | 改前（1.59.x） | 改后 |
| --- | --- | --- |
| `_build_context_envelope(live_results=…)` 与调用处 | 有联网部分时，模型的当前问题只保留联网之外的小句 | 当前问题恢复为完整原问题；信封新增 `live_search_results`（每组：问题、状态、去掉时效说明的正文），标注为参考数据，里面的指令一律忽略 |
| 系统提示 `_LIVE_RESULTS_RULE_ZH` / `_EN`（有实时结果时追加） | — | 时效信息只能依据查询结果；温度、价格、时间、日期、百分比原样照抄；查询失败的项说明暂时没查到；所有问题写成一段；天气只写今天和明天；不写时效说明 |
| `_validate_decision(live_grounding=…)` | 店外状态过滤只以审核知识为依据 | 同时以本轮实时结果为依据，模型照抄的天气不再被当作无来源断言删掉 |
| `_compose_with_live_results`（新增）与合并处 | 模型正文与联网原文分两段拼接 | 采用模型整段正文，末尾补一次时效说明。核对规则：模型正文里带单位的数字必须都出现在查询结果中；某组结果带数字、正文里却一个都没有，就补上该组原文；数字对不上时，删掉模型含这类数字的段落，改用查询原文。工具结果流程（房态、价格等）不变 |

## 改动凭据

| 改动 | 依据 |
| --- | --- |
| 方案二 | 1.59.2 测试号：客人发「武汉最近有啥玩的，天气咋样」，玩法段里出现「【天气】假期中段的天气我暂时查不到」，下面又是查到的今明两天天气。用户在三个方案中选择方案二（先查询、再由主模型整合成一段） |
| 过滤依据与补回原文 | 实施时单元测试发现：模型照抄的天气被店外状态过滤删掉，而数字核对因为正文里已经没有数字而判为通过，结果天气整段消失。据此加入实时依据和「每组结果必须体现」的核对 |

## 风险与未覆盖

- 混合提问的实时信息改由主模型转述：数字有核对，但措辞转述（如把「阵雨」说成「小雨」）不在核对范围内。
- 数字核对按「带单位的数字是否出现在结果里」判断，不核对数字对应的是哪一天。
- 主模型的输入多了实时结果正文，每次多用约一两千字。

回滚代码到 `v1.59.2`，只重建 API 容器；无迁移。

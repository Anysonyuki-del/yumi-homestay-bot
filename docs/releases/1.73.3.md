## 部署前置（复审 M1）

- Compose 对整个文件做变量插值，部署脚本的 `docker compose build api` 在缺少 `POSTGRES_PASSWORD` 时会失败。生产 `.env` 发版前没有这一项。
- 发版前只读核对结果：生产数据库角色仍在使用旧 `compose.yaml` 里的固定口令；运行中的 PostgreSQL 容器以同一口令初始化；`DATABASE_URL` 的密码段解码后与它一致。
- 处理：在生产 `.env` 追加 `POSTGRES_PASSWORD`，值等于当前口令，不改变任何凭据。部署脚本用 `up -d --no-deps api`，不会调和 PostgreSQL 服务；另用 `docker compose config --hash postgres` 核对追加前后哈希不变。
- **遗留风险**：生产数据库口令仍是曾经提交进仓库的值。PostgreSQL 没有映射宿主机端口，只在容器网络内可达，但仍建议另排维护窗口按 README 轮换。本次不做。（2026-11-18 更正：已于同日轮换，见文末「生产数据库口令轮换」。）

## 生产数据库口令轮换（2026-11-18 补记）

- **授权**：用户先同意在本会话处理「轮换生产数据库口令（维护窗口）」，看过维护方案后回复「现在执行」。
- **缘由**：生产库 `homestay` 角色一直使用旧 `compose.yaml` 中提交进仓库的固定口令（见上文「部署前置」）。另外，本记录改动清单里原本写有这个口令的原文，现已改成文字描述。轮换后，原文和 Git 历史里的旧值都已失效。
- **轮换前只读核对**
  - 认证方式为 SCRAM-SHA-256。容器内本地连接使用 trust，容器网络连接使用 SCRAM。PostgreSQL 没有映射宿主机端口。
  - 用这个口令连库的只有 API 容器（API 与 worker 在同一个容器里），没有定时任务或其他服务。
  - 服务器上残留的旧口令都只是历史副本，轮换后全部失效，未删除：项目目录里几份旧 `.env` 备份、一个早期回滚构建目录，以及 root 的命令历史。
- **执行方式**：整个流程写成一个脚本，在服务器后台一次跑完。SSH 当时时断时续，被服务器的并发连接限制随机断开，这样可以避免中途断线留下改了一半的状态。停掉 API 之后，任何一步失败都会自动回滚：恢复旧的口令校验值，还原 `.env`，重新启动 API。
- **步骤与结果**
  1. 备份：dump 447 个对象、1007871 字节，可读性复验通过；`.env` 与旧口令校验值另存到只有管理员可读的备份目录。
  2. 在服务器上生成 32 字节的 URL 安全随机口令。数据库只收到它的 SCRAM-SHA-256 校验值（`alter role … password '<校验值>'`），明文不经过数据库，也不会出现在数据库日志里。口令没有输出到终端或日志。
  3. 等待在途作业清零（当时为 0），然后停止 API。
  4. 更换角色口令，同步更新 `.env` 里的 `DATABASE_URL` 与 `POSTGRES_PASSWORD`。
  5. 用 API 镜像起一次性容器验证：新口令（经 `.env`）连接成功；旧口令被拒绝，异常是 `InvalidPasswordError`（口令认证失败）。
  6. `docker compose up -d --no-deps api`。第 3 次探测时应用应答，API 停机约 26 秒。
- **轮换后核对**
  - API 容器 running、重启 0，包版本 1.73.3，Alembic 在 head。启动以来 ERROR、Traceback、Exception、WARNING 均为 0 行，后台历史清理轮次已正常执行完一次。
  - 以 `homestay` 身份的 TCP 连接有 5 条；RUNNING 作业 0，到期未领取的作业 0。
  - PostgreSQL 容器没有重启（启动时间仍是 2026-10-21）。近 15 分钟的口令认证失败日志只有 1 条，就是第 5 步故意用旧口令做的探测。
  - 从本机访问：公网 `/health` 返回 503 degraded（原有稳态），登录页 200，OpenAPI 版本 1.73.3。
- **后续影响**：`postgres` 服务的 Compose 配置哈希与运行中容器的标签已经不同。部署脚本用的是 `--no-deps`，不受影响。手动执行不带 `--no-deps` 的 `up` 会重建 PostgreSQL 容器（数据卷保留，但会短暂中断），手册里的部署清单已改为只重建 API 的写法。
- **回滚**：备份目录里留有旧 `.env` 与旧口令校验值的 SQL。执行那条 SQL 并还原 `.env`，再用 `up -d --no-deps api` 即可回到旧口令。除非新口令出问题，不建议回滚。
- **没有核对**：轮换后到核对时没有新的外发作业，还没有观察到 worker 在新口令下实际处理作业（数据库读写已由历史清理轮次证明）。

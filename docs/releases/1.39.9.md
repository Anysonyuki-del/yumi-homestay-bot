## 改动凭据

- **用户决定**：
  1. 先选 A（按字节截断）。
  2. 实现后发现 A 与「审核原文不截断」相冲突，用户回复「拆分吧」。
  3. 说明拆分会改动所有客人消息的出站链路后，用户选 B：先写完整 Spec，不赶当天上线。
  4. 看过 Spec 后回复「开始」，六项决策按建议实施。
- **测量证据**：
  - 生产路线回复 675 字、1817 字节，接近上限。
  - 评估集长答案用例的审核答案在 2600～4900 字节之间，整条发出会被拒收，此前判为「能回答」并不成立（Spec §1.1）。
- **代码证据**：出站链路逐环节核对，见 Spec §1.2。顺序会被打乱的三种情形见 Spec §1.3。
- **被取代的方案**：按字节截断的本地分支提交 `3997480` 未合并、未发布。

## 风险与未覆盖

- 两条 worker 同时取任务未单独测试，也未在多进程环境实测；链式设计下同一回复任何时刻只有一段在队列里。
- 审核知识被安全拦截后由模型改写重发，会改动原文。这是既有问题，本版未处理。
- 首次同步发送失败的非分段回复没有员工通知，属既有缺口。

## 回滚

只回滚代码到 `v1.39.8`，只重建 API 容器；无迁移。回滚前若仍有排队中的续发任务，旧代码会忽略载荷里的分段信息，该段按普通消息发出。这是依据载荷结构的推断，未验证。

## 改动清单

| 改在哪里 | 改前 | 改后 |
| --- | --- | --- |
| `integrations/deepseek_client.py` 主回复系统提示词 | 要求「必须调用旅游联网搜索」，但主模型没有这个工具（时效问题在调用前已由 `classify_tourism_query` 分流）；写死「必须调用某某工具」，而工具是否开放由 `_allowed_tool_names` 决定 | 本轮提供了查询工具时先调用再回答，房源名称、房态和参考价只以工具结果为准；时效信息没有查询结果时不给具体数值或安排 |
| `deepseek_client.py::tool_definitions` | 三个工具的描述各只有一句话 | 写明返回内容与边界；房态判读规则（`stay_available`，`days` 逐晚列出、不含退房日）从系统提示词移入 `search_availability`；`search_reference_price` 注明客人问价时调用 |
| `deepseek_client.py::_refine_reply`、`deepseek_tourism.py` 搜索提示词 | 要求用「我帮您看了一下」开场，程序 `_warm_weather_reply` 又补一遍 | 开场白只由程序补充；两处都补上「正文只写武汉的公开信息，不写民宿自己的设施、物品或服务」 |
| `deepseek_complaint.py` 客诉草稿提示词 | 三句字段类型要求 | 删除：这三个字段由 `_derive_risk_flags` 覆盖，或在类型不对时回退为「待核实」 |
| `services/guest_reply_policy.py::_contains_ungrounded_property_claim`、`_drop_emptied_headings` | 设施断言要求「场所词在前、供应动词在后」，两份词表都是枚举的 | 同一句里同时出现本店一侧的主体与供应说法即删除，不论顺序；小节正文被删空时，标题一并删除 |
| `deepseek_client.py::_should_force_property_catalog` | 只有带「介绍 / 详情 / 名称」的问题才开放房源工具 | 按意图归类：凡是问本店有哪些、哪几种房都开放；房态与房内设施问题不触发 |
| `AGENTS.md`（项目） | 写着本机绝对路径；文档例外没有发布变更记录 | 改为「所在目录树」；例外补上 `docs/releases/` |

## 改动凭据

| 改动 | 依据 |
| --- | --- |
| 提示词、工具描述、客诉类型要求、AGENTS.md | 用户执行 `/claude-api prompt-audit` 后回复「开始」。审计报告逐条给出了代码位置、所属模式与可信度。其中「必须调用旅游联网搜索」这句与分流是 2026-08-13 同一个提交加入的（`git blame`），从那时起就无法执行 |
| 真实模型对比与参考价补强 | 用户回复「授权」，并选择在生产容器内运行（「2」）。首版弱化了调用要求，问价时 2 次中 1 次没有调用工具；补强后 3/3 调用 |
| 编造设施、房型不查房源 | 真实对比中复现，修改前后都存在；用户回复「一起修了再发」，确认 Spec `docs/specs/2026-09-24_amenity-claims-and-room-catalog-spec.md` 后回复「开始」 |
| 撤回的改动 | 审计第 8 项（客诉、FAQ 草稿改由 pydantic schema 生成字段清单）在真实 DeepSeek 下导致客诉草稿缺 5 个必填字段、校验失败，已恢复手写字段清单，未随本版发布 |

## 风险与未覆盖

- 设施过滤和房型触发仍依赖词表，只是从「固定词序」改成了「意图归类加同句共现」。编造的**服务**（如「帮叫车、安排接送」）没有供应说法，拦不住。
- 按句删除时，同一句里的正常建议会一起删掉。
- 时效问题的编造只是减少，没有消除：修改后仍有 1 次说出了去汉口站的用时。
- 房型回复偶尔被排版成小节标题，只影响版式。
- 英文回复不做设施过滤，因为还没有观察到英文的同类写法。

## 回滚

只回滚代码到 `v1.39.11`，只重建 API 容器；无迁移，不恢复数据库。

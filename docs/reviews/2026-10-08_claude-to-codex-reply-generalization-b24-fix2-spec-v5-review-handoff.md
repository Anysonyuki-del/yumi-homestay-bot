## 3. 新增功能：知识缺口转管家确认，确认后生成待审知识

源码现状（§1.5）：未确认文案不通知任何员工；`FrequentFaqService` 要 72 小时 3 次才生成草稿，草稿由模型从已有审核知识生成，不来自管家的真实回答；知识缺口不调用 `_notify_employee`；STAFF 只读资料库，候选转知识只给管理员。

方案（§2.6）：
1. **逐项判定**：新增 `gap_referrals: [{item_id, canonical_question, category}]`，由模型标出属于「民宿常识性补充、适合沉淀」的本店事实项。本地只接受同时满足以下三条的项：
   - 该项或该小句的剩余内容本地确实落到未确认；
   - 不属于房态、价格、订单、退款、预订、实时旅游、紧急或客诉（复用 `FrequentFaqService` 的排除规则与计划风险）；
   - 标准问题非空。
2. **实际通知**：同一事务创建或复用 FAQ 候选（新增立即转交入口，不走 3 次门槛）与转交记录，并给值班管家发卡片，卡片带「填写答案」链接。
   - 客人文案以登记结果为准：通知入队成功才写「这一点资料里还没有确认，已请管家核实后在这里回复您」，否则用现行未确认文案（D-G14）。
   - 同一会话同一问题 24 小时只转一次；会话不切人工（D-G13）；重放不重复通知。
3. **后台填写答案**（D-G12）：STAFF 与 ADMIN 可在核实页填写答案，可勾选「只对这位客人成立，不入库」。
   - 管家仍需在企业微信里亲自回复客人，系统不代发。
   - 填写后排草稿任务，草稿以「客人原问 + 管家答案」为唯一事实来源；管理员在现有候选页一键 `convert_candidate`。
   - 不自动入库；一直没人填写时保持开放。
4. **边界**：无计划路径不做逐项转交；不改变交易类人工确认链路。

## 4. 请 Codex 重点复审

1. **小句目标的继承规则**是否足够保守而不误拦：特别是「明天401有房吗，402呢」这类第二小句只有房号、没有日期时，按规则继承项日期，但房号不同、需要 402 的证据行。
2. **剩余检查**的形式词清单要按回归样本校准（Spec D-G11 记录了试算里「房费怎么算」剩「算」等假剩余）。在不补领域词的前提下，这个校准方式是否可接受。
3. **`gap_referrals` 的本地门槛**：「本地确实落到未确认」由逐项组合结果决定，与模型标记解耦。是否还需要额外约束，防止把客人个人信息写进标准问题（现有 `redact_example` 只遮手机号、邮箱、证件号、订单号）。
4. **转交与通知的事务边界**：候选、转交记录、管家通知、客人出站在同一业务会话提交。与 §2.4 的中断窗口合并验收时，计数里要加「转交记录 1、管家卡片 1」。这样纳入是否足够。
5. **核实页**是新的员工可写页面：STAFF 可写转交答案，但不能改资料库。这一权限划分是否与现有后台安全边界一致。
6. **范围**：这项新功能让 1.69.2 同时包含修复与新功能、迁移与新页面。是否应在实施计划里拆成可独立验证的两步（先修复覆盖契约，再接转交链路），共用一次门禁与发布。

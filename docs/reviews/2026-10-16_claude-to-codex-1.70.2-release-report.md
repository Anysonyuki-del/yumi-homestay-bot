## 2. 改动范围

房号身份解析的修复。完整清单见发布记录「改动清单」及各修订节，要点如下：

- `services/item_coverage.py`：
  - `room_mentions`：解析带楼栋、短横线、「号楼」的写法，跳过标识语境；
  - `room_identity`：room_number 优先，否则取标题里唯一的房号写法；
  - `resolve_rooms`：六种状态，与顺序无关；读取失败为 `unavailable`；
  - `clause_target` 读取解析结果；`clause_residue` 整段删除房号和并列连接词，只剩订房意图词时视为没有剩余；
  - 三处斜杠日期加数字边界。
- `application.SessionKnowledgeRepository.list_room_profiles`、`knowledge_service.room_profiles`：替代原来按字符串精确匹配的 `find_property_by_room`；读取失败时返回空值。
- `integrations/deepseek_client.py`：
  - 本轮身份快照：`_room_identities`、`_item_room`；
  - 枚举交接：`_clause_rooms`，含同日证明、整组提示原文、`orphans`；
  - `_asks_static` 统一判断资料缺口开放、静态取证和补未确认；
  - `_tool_reply_parts` 有目标时，空结果失败关闭；`_unmatched_room_header` 逐个说明对不上的写法，并区分「无法核对」。
- 门禁：替身走同一入口；夹具新增 `property_profiles`、条目 9903 和 9904，以及 K-带栋房号、K-同号异栋；K-周末分日从 1.70.1 的已知未通过晋升为 must_pass。基线为 142 个 must_pass、16 个 known_failures。

审查闭环：Codex 对 Spec v1 提了 RI-R1 至 R7，对实施提了 IRI-R1 至 R4、F5、F6（含展示）、F7、C1 至 C3，最后一轮 F7 复审结论为「三项修复通过，未发现新的阻断项」。门禁中发现的 AV-102 修复，**在 Codex 复审之后才做，未经 Codex 审查**，见 §3。

## 3. 门禁中发现的问题与修复（请重点审查）

- **现象**：`rc-1.70.2-2` 的 all 门禁里，AV-102「我想订102，今晚和明晚两晚」三次失败两次。失败时主模型没有调用查房工具。
- **定位**：用同一问题和同一份门禁资料，在 v1.70.1 与当前代码上分别构造首次主调用请求并比较。
  - 规划为 stay_query、又没填房号和日期时，新代码会向模型开放 `gap_units: [{"text": "我想订102"}]`。旧代码在规划填了 102 时同样会开放。
  - 根因是剩余只删房号，留下「订」「和」，而住宿项里没有工具锚点的小句，不看剩余就被当成资料问题。
- **修复**（Spec §10）：
  1. `clause_residue`：只剩订房意图词（订、预订、预定、订房、一间）和连接词时，视为没有剩余。
  2. `_asks_static`：住宿、目录项里没有工具锚点的小句只看剩余，资料缺口开放、静态取证、补未确认三处共用这条规则。
  3. `_clause_rooms.orphans`：后面有工具问法却没能并入的房号片段，保留保守提示，避免第 2 条让 F7 退回静默漏答。这一点在修复中途实际出现过：8 个 F7 回归失败后才补上 orphans。
- **验证**：
  - 新增 10 项回归，其中订房意图残留 7 项、三种规划变体不开放缺口 3 项；
  - 三种规划变体的首次请求里都不再有 `gap_units`；
  - 全量 3121 passed；`rc-1.70.2-3` all 通过。
- **审查请求**：
  - `_BOOKING_NOISE` 的词表和全匹配条件，是否会误吞真实问题。已保留「怎么预订」「预订要交定金吗」。
  - 静态事实项不受 `_asks_static` 影响；住宿项里只有日期的小句不再开放缺口，是否有遗漏的合法静态子问。
  - `orphans` 只标两类片段：带明确日期或日期无法解释的房号片段、日期不一致的片段。后面没有工具问法的片段不标，这个取舍是否合理。

## 4. 观察项与未覆盖

- **AV-102 首轮波动**：`rc-1.70.2-3` 首轮仍有一次模型没调用查房工具，两次重跑都通过，不判退步。这次请求里已经没有资料缺口，属于模型选择波动；1.70.1 门禁首轮通过。
- **K-安静-C 首轮**：答案后多了一段第二小句的未确认。这个场景没有房号和订房意图，`rc-1.70.2-2` 首轮通过，判断与本次改动无关。
- **真实收发的取证路径**：日志里证据选择为 `invalid reason=out_of_candidates`，由按对象约束的本地证据计划答对。模型实际选的条目，在离线测试和门禁之外没有核对。
- **生产没有实测的分支**：同号异栋、带楼栋写法、并列房号、读取失败。这些只由离线测试、门禁场景和 SQLite 集成测试证明。
- **数据依赖**：生产 7 个房源里 5 个 room_number 为空，靠百居易标题兜底，标题改名可能导致错配或歧义。补填需要生产数据操作授权。
- **已知保守上限**：
  - 枚举片段写了相对日期，但接收问法和本项都没有入住日时，不并入；
  - 歧义时不追问楼栋；
  - 节日名修饰的周末（如「国庆周末」）仍按本周末核验。
- **既有状态**：`/health` 为 503 degraded，原因是百居易回调从未收到，与 1.70.1 相同。
- **流程失误（已补救）**：收尾时 AOCI 写入与文档提交并行执行，写入因 S 字段超长被拒，提交 `d8cd44e` 已先推送。随后补写成功，另提交 `9d150d6`，Verify 和 Guide 已对齐。
- **回滚**：回退到 v1.70.1 即可，没有迁移和数据需要恢复；部署前备份保存在服务器受限目录。

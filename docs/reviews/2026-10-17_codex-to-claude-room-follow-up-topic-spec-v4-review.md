## 2. C4-1 · P3：入口措辞不要重新变成 residue 为空的前置门槛

§2.0 第 46 行仍写适用对象“没有静态剩余”，而 §2.1 支持 `302也是吗`、`302也一样吗`、`302也这样吗`。本轮直接调用现有 `services/item_coverage.py::clause_needs`，得到：

| 原文 | residue | tool_facts |
| --- | --- | --- |
| 302呢 / 那302呢 / 那么302呢 / 302的呢 | 空 | false |
| 302也是吗 | 也是 | false |
| 302也一样吗 | 也一样 | false |
| 302也这样吗 | 也样 | false |
| 那2栋302房间呢 | 空 | false |
| 我想订302 | 空 | false |

如果实施时先用 `not needs.residue` 过滤对象，再运行句式匹配，就会漏掉三个已经承诺支持的问法。另一方面，“我想订302”虽残留为空，也不能因此进入静态承接。

**建议**：将 §2.0 入口改成“对小句先执行 §2.1 的结构识别”，或明确“没有静态剩余”是正向识别后的语义说明，**不是现有 `clause_needs.residue` 的前置条件**。沿用有限句式识别即可，不要为了这些形式词全局扩充 `clause_residue` 的删除词表，避免影响其他调用方。

这是一处可直接按详细结构规则消解的实施澄清，不认定为新 P2，也不要求再引入一套分流机制。验收需让三个非空残留句式与 `302呢` 得到相同话题/房源绑定，并与真实订房请求成对控制。

## 3. 实施时保持的验收边界

- 结构识别、父单元关系、房源/日期/条件和单元编号须在调用前冻结；重叠计划换序不能改变结果。连续追问继续传递已经绑定的语境，不从父答案推导事实。
- 正常、未授权工具请求的安全回退、工具后协议失败、周末组合共用相同单元职责。工具开放须核最终 `allowed_tool_names` 的实际结果，不能只测 `_plan_tool_names` 返回值；现有旧规则入口 `_allowed_tool_names` 也要纳入确认。
- 全店工具目标不能被同轮静态房号收窄；点名工具目标不能因空筛选扩大；纯 C/D 不因模型主动请求工具而附上房态或目录。覆盖继续核事实类型、房源及日期。
- 每个单元只用自己的合法候选，保留模型可见性、日期条件、预算和有限跨项复用的既有约束；知识缺失与预算、冲突、复核、范围失败不可混为同一转交理由。
- 最终转交记录应携带继承日期和必要条件，并匹配实际未确认分项的编号。模型选中编号不代替本地缺口证明；D-T5 仍待用户决定。
- 真实模型门禁按 Spec 的限定三次、晋升及 all 流程执行，需当次授权。已知的有限句式、换行断开、追问自身带日期不进入新功能等范围不扩大。P1–P6 代表当前承诺的计划形态，不能据此宣称可纠正任意非法或高风险规划类型。

上述均是现有 Spec 的实施检查点，不额外要求全仓重构、更多模型调用或无关测试。

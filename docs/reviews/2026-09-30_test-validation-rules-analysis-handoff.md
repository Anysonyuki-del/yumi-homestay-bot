## 1. 目标与结论

用户要求：「我要更改我的全局规则，减少测试，现在的测试流程过于复杂，每次改动都测试过于繁杂，是否可以只做修改相关测试，以专业的角度审查并给出建议」，随后要求「写分析交接报告」。

建议采用：**默认只运行受影响的验证，全量测试必须有具体理由；已有结果仍覆盖最终改动时直接复用。**

受影响范围按行为、调用方和数据流判断，包括间接调用及跨请求状态，不只按文件名选择。高风险决定验证的深度，影响范围决定测试的广度：一个事务缺陷可能需要目标数据库上的并发测试，却不需要全仓无关单测。

本轮授权为审查、建议和报告编写。本报告不代表新规则已生效，也不授予修改规则、业务代码、测试、CI、提交、推送、部署或真实接口操作的权限。接手时依据用户当前明确授权继续，不从报告自行推导授权。

## 3. 建议的验证尺度

| 改动情形 | 默认验证 | 扩大条件 |
| --- | --- | --- |
| 文档、注释、纯版本号 | 差异、必要的链接或格式检查；不跑业务测试 | 实际改变脚本、依赖、配置或运行行为时重新判断 |
| 局部功能或稳定可复现的 bug | 已有相关行为测试；缺少缺陷覆盖时补最小回归，保留必要反向边界 | 真实调用链跨越其他模块时补对应测试 |
| 共享函数的局部变化 | 受影响调用方及关键集成路径 | 多类业务行为共同变化或无法可靠界定时才全量 |
| 权限、安全、事务、并发、迁移 | 对应的拒绝路径、隔离、竞争或回滚验证；使用适用的目标环境 | 范围广泛或环境变化影响整个系统时再扩大 |
| 页面交互或视觉修改 | 受影响交互的浏览器验证，或必要的视觉检查 | 公共布局、导航或全局交互确实变化时覆盖相关页面 |
| 模型提示、事实校验、检索或回复行为 | 本次受影响场景；确定性问题优先离线测试 | 公共提示、分类路由或流程实际影响广泛、无法圈定时全量模型回归；真实调用仍需当前授权 |
| 全局依赖、运行机制、大范围重构或范围不明 | 扩大验证，必要时全量 | 必须说明具体影响，不只写“核心模块”或“安全起见” |

“常量”和“文案”不自动等于低风险：超时、金额、安全阈值、SQL、主模型提示中的文字可能改变行为，必须依据内容判断。

全量测试也不能替代原缺陷验证；如果目标风险是 PostgreSQL 行锁竞争，应验证该竞争，不用增加无关用例数量代替。

## 6. 验收方式

规则和文档修改采用静态审查，不运行 pytest、真实模型门禁、真实消息或生产操作。

- 核对全局、Claude 引用、项目规则和手册的优先级及措辞一致；技能原文可以保留，但权威规则必须明确覆盖冲突要求。
- 检索仍作为有效要求存在的“每次全量”“即使本地全量通过仍须等 CI”“当前消息必须重跑”等表述，逐处判断；不因历史记录或技能原文匹配就删除。
- 用四个情形走读：纯文档无需业务测试；局部共享函数只覆盖相关调用方；行锁修复补目标数据库竞争验证；全局依赖变化无法界定时扩大。已有通过结果后只改交接文档，不触发重跑。
- 确认报告里的 CI 更正仍成立，不重新引入双重必过；不把本地 pytest 全量写成所有运行环境已通过。
- 差异检查只包含获准的规则/文档；没有无关业务代码、测试、版本、依赖、Hook 或 CI 变化。明确区分静态引用已核对与新会话中规则实际执行，未观察后者时如实说明。

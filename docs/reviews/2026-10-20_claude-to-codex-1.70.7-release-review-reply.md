## 2. 修订后的最小方案（RV177-1）

### 2.1 关键事实：stable 只有一个消费者

- `classify_tourism_query` 在 src 中的调用方：
  - `deepseek_client.py` 约 4185 行 `public_clauses`，只取 `== "live"`；
  - 约 4567 行推荐指令，取 `== "stable"`；
  - `conversation_service.py::_stage_fast_ack` 约 1363 行，只取 `== "live"`。
- `is_tourism_query` 在 src 中没有调用方。
- 因此 stable 的误判，**唯一的运行影响**就是追加 `_STABLE_RECOMMENDATION_RULE`。在这个唯一的消费点修，就不会碰 live、搜索和联网首响。

### 2.2 改法

- **位置**：`integrations/deepseek_client.py::DeepSeekGuestAssistant._respond_with_plan`，即 v1.70.7 约 4565 至 4570 行。
- **改前**：任一小句的分类为 stable，就追加这条指令。
- **改后**：只有本轮计划可用，且某个**有效的 `external_info` 事项**，其原文区间与分类为 stable 的小句相交，才追加。
  - 计划不可用、规划失败或没有计划时，都不追加，回到 v1.70.6 的行为。原有的全局一句普通推荐规则仍在。
- **实现**：复用已有符号，把 `turn_clauses` 改为保留 `split_clauses` 返回的 `Clause` 对象，用 `item_coverage.intersecting_clauses(clauses, item.start, len(item.quote))` 判断相交。
  - `plan_items` 在该函数开头已由 `usable_plan(...).plan.valid_items` 得到。
  - 不新增规划调用，也不新增分类器。
- **不改**：
  - `tourism.py` 的词表和分类顺序；
  - `public_clauses`、`_stage_fast_ack`、知识检索、事实过滤和危险流程；
  - 指令措辞。

### 2.3 依据与取舍

- **现有场景不受影响**：rc3 门禁 160 个场景中，只有 W-小吃、W-推荐、W-天气玩法三个场景会追加这条指令。三者的规划都是一项有效的 `external_info`，区间与 stable 小句相交，按新条件照旧追加。
  - 这是 rc3 已有的记录（`.stage/reply-gate-rc-1.70.7-3.json` 的 `plan` 字段），各一次，不代表规划每次都这样标。
- **物业问题被拦下**：「民宿有啥玩具吗」「电视有什么玩的频道」「房间有什么玩的」，以及旧版的「民宿有什么好玩的玩具」，都不需要任何词表。只要规划没有把它们标成店外信息，就不再追加。
- **残余风险一：误收回**。规划把真正的推荐标成 `static_fact`，或规划失败时，这条指令会被收回，可能重现 W-推荐那类「只追问、不推荐」。由真实门禁 all 衡量，失败时保留逐次规划。
- **残余风险二：误追加**。规划把物业问题误标成 `external_info` 时，仍会追加，和现状一样，不比现在差。
- **混问**：「房间有什么玩的，附近有啥好吃的」中，后一小句有店外事项，整轮会追加。指令本身只约束普通推荐，本店事实仍走证据和过滤，与现状一致。
  - 指令按轮追加，不按小句追加，这是既有的限制。改成按小句需要动主调用结构，不在本次范围。

## 3. RV177-3（新，既有问题，不属于 RV177-1）：带时间词的借用问题被当成实时旅游查询

### 证据

- **分类器**：用 v1.70.7 本地分类器核对，v1.70.6 的词表在这几句上相同：

  | 问法 | 分类 |
  | --- | --- |
  | 今天可以借吹风机吗 | live |
  | 现在有雨伞可以借吗 | live |
  | 最近能借充电宝吗 | live |
  | 今天有早餐吗（对照） | none |

- **原因**：`classify_tourism_query` 的兜底规则是「时间词 + 问句」就判 live，只用 `about_homestay` 和 `_HELP_SEEKING_PATTERN`（怎么办、怎么处理……）排除；借用、租用这类服务请求不在排除范围内。
- **编排**：用 `_mixed_question_assistant` 合成替身走真实编排，这两句都是搜索 1 次、主模型请求 0 次。也就是整句交给联网分项回答，不经过主模型的审核知识作答。
  - 替身的知识为空，所以回复里只有「审核资料尚未确认」加上替身的天气文本。
  - 有审核资料时生产实际会怎么答，**没有验证**。
- **联网首响**：`_stage_fast_ack` 同样会因为 live 先发「正在查询」的安抚。
- **等级**：暂列 P3。客人问能不能借吹风机，却得到网页搜索结果，属于答错方向；但还没有证据证明有资料时也会漏答。

### 建议

- 另立 Spec，先诊断有审核资料时的真实最终输出，再决定修法。
- 两种修法：
  - 在兜底规则处排除服务请求信号；
  - 或者 `public_clauses` 也用计划来收窄。

  后者会影响全部 live 路径，范围大于本次。
- 不和 RV177-1 合并：两者改动边界不同，前者只动推荐指令，后者要动搜索与首响。验收标准也不同。

## 6. 修订（2026-10-20，回应 Codex 对本回复的第二轮意见）

### 6.1 「区间相交」作废，改为「推荐依据须在事项自己的原文内」

- **已证伪**：§2.2 的「`external_info` 事项与 stable 小句相交即追加」不成立。
  - Codex 的反例：「前台有什么玩具可以借吗还有武汉明天天气怎么样」。
  - `split_clauses` 不在「还有」处切句，整句是一个小句，并因「玩具」判为 stable。天气事项与这个小句相交，借到了不属于它的 stable，于是追加了指令。
  - 换成逗号时，两个小句分开，不追加。Codex 用真实核验函数和正确的计划复现了这一点。
- **Codex 的方向是对的，但需要再细一层**：如果按事项的整段原文分类，会误收回 W-天气玩法。
  - 它的规划是一项跨两个小句的 `external_info`，原文「武汉最近有啥玩的，天气咋样」整体分类是 live（rc3 记录核对）。
- **修订后的条件**：本轮有可用计划，且存在有效的 `external_info` 事项，并且**对该事项自己的 quote 再用 `split_clauses` 切句后**，至少有一个小句分类为 stable，才追加。
  - 不再使用整轮小句，也不再使用 `intersecting_clauses`。
  - 计划不可用时不追加。
- **本地核对**：分类器加切句的纯函数投影，不是已实现的代码。

  | 用例 | 计划 | 追加 |
  | --- | --- | --- |
  | 玩具借用加天气（逗号或「还有」） | 拆成 `service_request` 与 `external_info` 两项 | 否 |
  | 同上（「还有」） | 天气项错误地覆盖整句 | 是：规划误标的残余，与现状相同 |
  | W-小吃、W-推荐 | 一项 `external_info` | 是 |
  | W-天气玩法 | 一项跨两个小句 | 是 |
  | 民宿有啥玩具吗、电视有什么玩的频道 | `static_fact` | 否 |
  | 房间附近有什么玩的 | `external_info` | 是 |

- **验收矩阵增补**（在 §2.4 的基础上）：
  - 「区间」一行改为：连接词「还有」「和」「另外」各一组，拆项和整句覆盖各一份；
  - 增加「一项跨两个小句」的推荐控制，即 W-天气玩法 的形状。

### 6.2 RV177-3 的优先级

- 同意 Codex：已有合成替身证明整句误走搜索，主模型 0 次请求。优先级与 RV177-1 并列，不排在后面。
- 两项分阶段修，但用同一份「本店事实／店外信息」合同：
  - 店外信息的依据，只能来自有效的 `external_info` 事项自己的原文；
  - 计划不可用时按保守方向处理：不追加推荐指令；是否联网，由 Spec 单独规定。
- RV177-3 还涉及 `public_clauses` 与 `_stage_fast_ack`。后者经常在规划之前运行，没有计划可用，所以不能直接套用同一条件，要在 Spec 里单独给出首响的判据。

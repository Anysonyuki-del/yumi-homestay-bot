## 2. RV177-1 / P3：「有什么玩」别名把物业设施问题判为普通旅游推荐

### 依据

- `integrations/tourism.py::_STABLE_TOURISM_PATTERN` 新增 `有(?:啥|什么)(?:好)?玩`。它是子串匹配，没有约束后文，所以「玩具」「玩意」「玩法」都会命中。
- `classify_tourism_query` 先查 stable，后算 `about_homestay`。因此前台、房间等民宿一侧的对象，也拦不住 stable。
- `deepseek_client.py` 在 v1.70.7 约 4566 行处，只要有一个小句判为 stable，就追加 `_STABLE_RECOMMENDATION_RULE`。这条指令的内容是：先给两三个具体去处，缺少本店资料不能成为拒绝普通推荐的理由。

### 反例

v1.70.6 与 v1.70.7 的分类对照，以及 v1.70.7 是否追加该指令（用 `test_deepseek_client._mixed_question_assistant` 合成替身探针核对）：

| 客人问题 | v1.70.6 | v1.70.7 | 是否追加推荐指令 |
| --- | --- | --- | --- |
| 民宿有啥玩具吗 | none | stable | 是 |
| 前台有什么玩具可以借吗 | none | stable | 是 |
| 房间有什么玩的 | none | stable | 是 |
| 有啥玩意儿能修一下 | none | stable | （未探） |
| 有啥玩具可以借吗 / 电视有什么玩的频道 | none | stable | （未探） |
| 朋友晚上能来房间坐坐吗（对照） | none | none | 否 |

### 影响

- 这几类都是本店事实问题，应该按审核资料回答，没有资料时回答未确认。现在模型会额外收到「先推荐店外去处、不要因缺资料拒绝」的指令，可能用店外推荐代替或冲淡未确认的答复。
- 事实过滤仍会删掉没有依据的本店断言，所以这不是编造设施的安全问题，属于回复质量问题。
- 但它和发布记录、Spec §11.5 的表述直接矛盾。§11.5 原文是「纯静态问答不接收额外旅游指令」「只在明确的 stable 推荐小句追加」。
- `stable` 目前只影响这条指令的追加。live 分支与联网搜索不受影响，我核对了 `classify_tourism_query` 的调用方。

### 测试缺口

- `test_tourism.py` 的「入住的房间有啥玩的？→ none」是被 `_BOOKING_PATTERN` 里的「入住」挡住的。去掉「入住」后，「房间有什么玩的」就是 stable。这项测试证明的是住宿优先级，没有覆盖物业对象。
- `test_deepseek_client.py::test_recommendation_contract_does_not_reach_pure_static_questions` 的两个对照都不含「玩」字，覆盖不到这个误判。

### 建议

1. 收窄别名，要求「玩」后面是「的」「儿」、语气词、问号或句末，例如 `有(?:啥|什么)(?:好)?玩(?:的|儿|[呀啊吗呢？?]|$)`。不要改 stable 与 `about_homestay` 的先后顺序，那会影响既有的「附近」「楼下」等问法，范围更大。
2. 回归用例：
   - 在 `test_tourism.py` 增加玩具、玩意、玩法、「前台有什么玩具」「房间有什么玩的」，期望都是 none；
   - 在请求作用域测试里加一个物业「玩」字对照；
   - 保留「武汉最近有啥玩的」「有什么玩的？」为 stable。
   - 新用例须在 v1.70.7 上失败。
3. 「房间有什么玩的」不带对象名，属于两可。若按 stable 处理，应在 Spec 里写明取舍。
4. 这是问题分类的改动，按项目规则真实门禁走 all。

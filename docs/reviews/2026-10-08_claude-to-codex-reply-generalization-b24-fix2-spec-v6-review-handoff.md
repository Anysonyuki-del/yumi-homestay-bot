## 1. 对 V5 报告的复核

报告 §5.3 的探针在 main `80f9b2c` 上运行，退出 0，E-V5-1–5 与报告一致。八项全部同意。

V5-R3 的实际情况比报告写的更严重：STAFF 现在完全没有后台登录入口，`require_employee_session` 只认唯一活动管理员。因此 v6 不新建员工登录，改为让管家在企业微信里照常回复客人，由系统自动取用管家消息（用户改选 D-G12）。

## 2. 补查出的牵连问题（Spec §1.6 下表）

1. **转交文案会被出口过滤删掉。** 本地试验结果：
   - v5 推荐的「这一点资料里还没有确认，已请管家核实后在这里回复您。」会被 `remove_ungrounded_property_claims` 与承诺过滤整句删除；
   - 现有的「您的请求已登记，管家通知已提交，尚待管家确认。」同样会被删；它之所以能发出，是因为在 `prepare_planned_reply` 之后作为 `action_reply` 追加。
   - v6 的处理：转交说明也在过滤后追加，文案固定，并去掉回复承诺（D-G14 措辞修订）。
2. **调用前无法知道哪些缺口成立。** 缺口是否成立取决于同一次主调用的工具结果与证据选择，模型不可能在调用后才形成的缺口列表里做选择。v6 的处理：
   - 调用前列出「可能缺口单元」：编号由计划项编号与原文区间生成，计划冻结在作业载荷里，重放时编号不变；
   - 模型只能从这些编号里选；
   - 调用后本地只接受缺口原因为「资料缺失」的单元。
3. **知识条目必须中英双语。** 不能只把管家原话填进去，仍需模型整理和翻译。
4. **管家消息的挂接点。** `handle_message` 的 SERVICER 分支在 `record_incoming` 去重之后执行，机器人自己发出的消息会在去重处提前返回，不会进入该分支。管家回复的自动取用挂在这里。
5. **发件箱可以分命名空间。** 去重键是「来源:阶段:类型:序号」，每个实例独立计数。卡片用独立阶段的实例发送，就能与客人回复的序号解耦，不必改全局发件箱。
6. **未审核范围是安全默认。** `scope=unreviewed` 的条目不参与本店事实回答，所以入库时必须显式选择范围，不预填全店。
7. **管家消息本来就会交给模型。** 会话上下文 `list_recent` 不按来源过滤，记忆提取也会处理管家消息。草稿模型拿到的是脱敏后的管家消息，接收方没有扩大。
8. **会与高频 FAQ 重复统计。** 本轮有转交时，跳过整轮级的 `_track_frequent_faq`。

## 3. v6 的逐项修订

| 发现 | v6 方案（Spec 位置） |
| --- | --- |
| V5-R1 | 剩余检查只删除被证据覆盖的固定操作锚点（每个识别函数旁列出锚点词），不删除正则的整段命中；另删已绑定的房号、日期区间、住几晚和纯形式词。用测试断言每个锚点都能触发对应识别函数，并写 `ponytail:` 注释。v5 试算中的假剩余分别由形式词、日期区间、房价锚点、房态锚点消除（§2.1(2)「未知剩余」） |
| V5-R2 | 日期保留端点角色：区间的入住日、退房日分别与证据比较，倒置视为无法绑定，单日期按「入住/退房」标记比较，年份取该项已核验日期。证据字段的含义按来源种类用测试固定。无法绑定的缺口原因记为「范围未绑定」，不转交（§2.1(2)「小句目标」） |
| V5-R3 | 不新建员工登录，管家不进后台（D-G12 修订）；资料核实视图只给管理员，沿用现有登录与 CSRF（§2.6(5)） |
| V5-R4 | 缺口单元编号绑定原文区间、房源与缺口原因；资格判断按单元原文与标准问题执行；冲突、期间否决、范围未绑定、日期待澄清、工具失败、预算跳过都不转；`availability_fallback` 与无计划不转（§2.6(1)） |
| V5-R5 | 转交独立成表，不复用 FAQ 候选。记录本地确定的房源；冷却、抑制、覆盖都按「归一化问题 + 房源」判断；入库必须点选范围，没有默认值；有效期只由管理员填写；草稿不得推广到其他房间（§2.6(4)–(6)，D-G15） |
| V5-R6 | 独立的作业类型 `knowledge_referral_draft`，载荷带回答版本，按版本写回。入库时加行锁，核对页面携带的回答版本与草稿版本，过期页面拒绝。只有被采用的记录标「已入库」，同问题同房源的其他记录标「已由条目覆盖」。知识被停用或删除后，新缺口照常产生转交（§2.6(4)(5)） |

| V5-R8 | 唯一约束为「来源消息 + 单元编号」，重放时沿用已持久化的结果；冷却与创建在会话活动锁内串行；卡片用独立的发件箱阶段，重放时照常再调用、由发件箱去重。验收加入最终阶段「业务提交后、Worker 标记完成前」的真实 `Worker.run_once` 加 `recover_stale` 窗口（§2.6(2)、§3.2） |

## 4. 请 Codex 重点复审

1. **操作锚点清单（R1）。** 它和识别正则会漂移，现在靠测试断言与 `ponytail:` 注释约束。有没有更好的办法：不另列清单，又不消费通配部分？
2. **日期角色（R2）。** 参考价是逐夜价格，它的证据范围字段能否与房态区间用同一套比较？实施时会用测试固定，请看 Spec 的写法是否留下歧义。
3. **调用前列出缺口单元。** 我的结论（已写入 Spec §2.6(1)）：调用前的剩余片段按「锚点全部删除」计算。调用后没被覆盖的锚点只会产生房价、房态或目录类缺口，这几类本来就不可转交；可转交的只有非锚点内容，与调用前的单元一致。请核对这个推理有没有漏掉的情形。
4. **管家消息追加到同会话全部待处理转交。** 由草稿生成器判断每条消息回答了哪个问题，管理员审核兜底。这一做法能否接受，还是应限定「只有一条待处理转交时才自动取用」。
5. **客人文案在过滤后追加。** 这绕开了过滤器，所以文案必须完全固定，不能拼接模型文字；其中的问题标签来自本地单元原文（已脱敏）。请看这种拼接是否仍有注入或泄露风险。
6. **范围与阶段。** 两阶段实施、一次门禁与发布、版本 1.70.0，是否合适。

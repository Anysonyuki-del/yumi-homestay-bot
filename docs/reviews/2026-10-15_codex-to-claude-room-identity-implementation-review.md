## 2. 必须修复

### IRI-R1 · P1：缺少楼栋资料被当作任意楼栋，可答出另一栋的资料

**位置：**`src/homestay_bot/services/item_coverage.py::_match_mention`，约 345–360 行；调用链为 `_item_room` / `_fact_layout` → `_merge_item_knowledge` → `_item_evidence_plan` → 最终正文。

**问题：**条件包含 `or identity.building is None`，使明确的“2栋1803”也能匹配楼栋未知的裸号 `1803`。候选有多个时，当前会话房源又会优先，因此即使正确的 2栋1803 已在表中，也能选错。

**完整助手链路反例：**

| 资料 | 值 |
| --- | --- |
| 房源 101 | room_number=`1803`；知识：“1栋1803没有浴缸，只有淋浴。” |
| 房源 202 | room_number=`2栋1803`；知识：“2栋1803有独立浴缸。” |
| 本轮会话房源 | 101 |
| 客人问题 | 2栋1803有浴缸吗 |
| 实际最终正文 | **1栋1803没有浴缸，只有淋浴。** |
| 实际证据 | 知识 731，property_id=101；无缺口 |

这与 Spec §2.1“客人写了楼栋时，楼栋也必须相等”冲突。现有测试只覆盖所有相关身份都有楼栋的情况，没有覆盖裸号身份和明确楼栋并存。

**最小修复：**客人明确楼栋时要求身份楼栋严格相等，楼栋未知不能证明相等；会话偏好只在满足全部显式约束的候选中消歧。最小实现可删除上述通配条件。仅写裸号的提问继续允许匹配已有带栋身份。

**验收：**上述反例必须只引用房源 202；只有裸号身份而客人指定楼栋时，应无法绑定。补当前会话属于另一候选、静态和工具两类断言，保留原来的裸号正常匹配。

**不修后果：**把其他房间的设施、停车等专属事实作为客人所问房间的已审核答案，且不会生成缺口提醒。

### IRI-R2 · P2：混合状态丢失已确定房源，也会吞掉未知房号说明

**位置：**`item_coverage.py::resolve_rooms`，约 364–385 行；`deepseek_client.py::_tool_reply_parts`、`_unmatched_room_header`、`_tool_coverage`。

**问题：**只保留第一处 unresolved。第一处是 ambiguous 时，返回值只保留它的候选，丢掉已经 resolved 的房源；第一处是 unknown 时，则不再保留后面 ambiguous 的候选。未匹配说明又因 `matched=True` 被整体抑制。聚合结果无法表达“有些已确定、有些歧义、有些未知”。

**已复现：**身份表包含 302、1栋1803、2栋1803，工具返回三者可订：

| 输入 | 实际结果 |
| --- | --- |
| 明天302和1803还有房吗 | 最终只列 1栋1803、2栋1803；**302 被丢掉**；正常与协议回退都如此 |
| 明天302和9999还有房吗 | 只列 302；“没有找到9999”的说明被抑制，只有整句未确认，客人无法从中确定哪个房号有问题 |
| 9999和1803 | 聚合为 unknown，property_ids 为空 |
| 1803和9999 | 聚合为 ambiguous，property_ids 为两栋 1803 |

两种顺序表达相同房号集合，却得到不同候选集合和输出策略。`clause_target` 还只核聚合后的歧义候选，因此丢失的 302 不会再由工具覆盖缺口补回。

**最小修复：**保留全部已确定房源、各歧义候选和未匹配写法，不能用“第一处错误”替代其他信息；工具筛选使用正确集合，对未知写法单独说明。可以保留静态多房号不作答的既定政策，不要求本版实现逐房静态检索。

**验收：**known+ambiguous、known+unknown、unknown+ambiguous、多个未知及调换顺序。断言最终正文、工具证据和缺口；同一集合不得因顺序变化漏掉某间房。正常和协议回退出口均覆盖。

**不修后果：**一句问多间时，有资料、有工具结果的房间仍会无声漏答；作者实施报告 §5 第 1 项所问的问题需要处理，不能仅补一句文案而保留错误集合。

### IRI-R3 · P2：目标房源已确定但工具漏行时，筛选静默退回其他房源

**位置：**`deepseek_client.py::_tool_reply_parts`，约 2993–3002 行。

**问题：**仅在 `selected` 非空时才替换 `rows`。目标 resolved，但工具未返回它时，原始其他房源行被继续输出；若问题含“最便宜”，还可能进入其他房源的最低价选择。

**完整链路反例：**问“明天302还有房吗”，身份表中 302 已 resolved；合成工具只返回两栋 1803。最终先列“可订：1栋1803、2栋1803”，再说“明天302还有房吗这次没有查到对应的房态”。该分支没有“以下是其他房间”的说明。作者实施报告 §5 第 3 项准确暴露了这个行为，但不能据此认定它合理。

**最小修复：**resolved / multiple / ambiguous 已有目标集合时，即使筛选为空也使用空集合，返回所问房源未查到的回执；不要进入全店最低价分支。无房号及经确认的 UNKNOWN 展示全店政策单独处理。

**验收：**目标存在但工具漏行、工具全空、缺目标且含其他房源报价，以及“最便宜”与明确目标并存。正常与协议回退都不应把其他房源行当成本次目标筛选的结果。

**不修后果：**筛选在最需要失败关闭时失效。这个回退方向继承自旧实现，但本次已确认的统一身份筛选仍未覆盖它；报告不把整类问题说成此次首次引入。

### IRI-R4 · P2：身份读取失败被转述为房间不存在

**位置：**`knowledge_service.py::KnowledgeService.room_profiles`，约 820–834 行；`DeepSeekGuestAssistant._room_identities` → `resolve_rooms` → `_unmatched_room_header`。

**问题：**仓储读取异常被转换成成功读取到空表。匹配阶段因此给所有点名房号 UNKNOWN，输出端确定性宣称“没有找到这个房间”。日志虽留类型，但客人仍收到错误业务结论。

**完整链路反例：**身份仓储抛出合成 RuntimeError，知识读取正常，工具返回真实形态的 302 可订行。最终同一条回复同时出现：

> 没有找到「302」这个房间，以下是全部房间：
>
> 可订：302家庭房、1栋1803、2栋1803

**最小修复：**保留本轮身份读取是否成功的信号，把读取不可用与成功读取但无匹配区分；前者回“暂无法核对房号”类中性失败说明，保持静态未绑定、不转交，不据此宣称不存在。无需无界重试、额外查询或把工具标题重新作为第二套身份来源。

**验收：**读取异常、成功空表、成功且无匹配三个情况分别断言；身份读取失败但工具有目标行时，不得出现“不存在/没有找到”的确定性结论。缺少可选仓储能力也不能冒充成功空表。

**不修后果：**临时数据库故障被伪装成房号不存在，同时产生自相矛盾的答复。作者实施报告 §5 第 2 项需要修复。

| 上轮编号 | 本轮结论 |
| --- | --- |
| RI-R1 工具行统一身份 | 已接入按 property_id 筛选；IRI-R1/R2/R3 表明边界尚未完整闭合 |
| RI-R2 楼栋残留 | 常见带栋、短横线、号楼写法已整段删除；相关回归通过，未发现新的独立阻断 |
| RI-R3 原文与规划优先级 | 原文覆盖错填及 token 核对已在消费端实现；明确楼栋仍受 IRI-R1 影响 |
| RI-R4 标识数字 | 已排除列明的标识语境；裸号上限已说明，不以未承诺的任意语义识别提出新要求 |
| RI-R5 标题兜底 | 已删除绝对安全保证，room_number 优先、唯一标题兜底和停用过滤有覆盖；仍是已声明的上游命名依赖 |
| RI-R6 完成门槛 | 发布记录写明三个目标场景各三次全过再 all；真实测量尚未执行，不能判为已完成 |
| RI-R7 服务费依据 | Spec 已更正，不再以错误归因为由修改追问逻辑 |

对实施报告 §3 的取舍：

- **不修改 verify_turn_plan：**本轮追踪确认房源解析在 `_item_room` 按原文和完整号码核验；保留现行核验层可接受，避免重复规则。`service_fee_followup` 仍读原规划字段，但普通点名房号不会进入该话题借用路径；这不替代 IRI-R1 的楼栋约束。
- **把新房态门禁改为静态 K-同号异栋：**夹具基线未加入额外 Hostex 房源，避免影响现有全店目录、房态和最低价场景，是可解释的缩小影响面；但静态保守用例不能证明工具筛选可靠。修复 IRI-R1 至 IRI-R4 后，应补完整工具链路的确定性边界测试，再按修订后的目标场景和 all 验收，不能只引用当前单函数筛房测试。
- **电话号段风险：**实施报告已指出楼栋前缀仅支持 1–2 位数字、部分分隔号码仍可能产生写法。本轮未证明该项是新引入缺陷；保留为已说明边界，不扩展成通用号码解析项目。

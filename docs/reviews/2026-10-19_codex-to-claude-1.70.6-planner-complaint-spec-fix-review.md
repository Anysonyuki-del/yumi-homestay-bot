## 3. F176-F1 / P2：危险标签正确，仍可能先被客诉分支截走

### 3.1 依据与反例

Spec §6.7 对“插座一直滋滋响还发烫！！！太离谱了”要求故障项为 `possible_hazard` 或 `current_hazard:electric`，不能只剩 complaint。这还不足以证明危险没有被客诉吞掉：规划允许一句拆成多个有效事项，故障项可保留危险，而另一项保留不满。

源码顺序：

- `services/conversation_service.py::process_debounced_message`（1067附近）在 `agitated_cleared_by_plan=False` 时调用 `_enter_complaint_mode` 并直接返回；
- `answer_policy::agitated_cleared_by_plan` 只要任一有效项为 complaint 就不放行；
- `_apply_plan_risk` 目前在后续主回复成功/失败出口消费危险，已被提前返回绕过；
- 门禁 `reply_regression.py::_Runner._respond` 的软客诉提前返回也有同样顺序，只有规划标签正确不能证明最终安全处置。

用同一原文、同一故障项，仅切换是否另设有效的“太离谱了 / complaint”事项，经真实 `process_debounced_message`、必要时继续 `process_recorded_message` 得到：

| 故障项 risk | 另有 complaint 项 | 结果 |
| --- | --- | --- |
| possible_hazard | 无 | 最终链路发出“避开可能有危险”提醒 |
| possible_hazard | 有 | 合并阶段立即进客诉；0个最终作业；只有客诉确认，没有避险提醒 |
| current_hazard:electric | 无 | 最终链路发出电气危险处置 |
| current_hazard:electric | 有 | 合并阶段立即进客诉；0个最终作业；只有客诉确认，没有电气危险处置 |

四份计划都通过真实核验、每项 valid，混合计划也满足当前“故障项保留危险标签”的文字要求。模型与仓储端口使用合成替身，真实会话编排没有替换；不是生产事故或发生率证据。当前 F1/F3 diff 没有改会话顺序，此为既有遗漏。

### 3.2 最小修订与建议方案

先在 Spec 补齐**固定计划的完整路由验收**，包括单危险项、危险项加独立投诉项、主回复成功与失败。不能只检验生成的 risk；必须断言客人实际得到对应安全提示、人工状态和通知，不因进入客诉而消失。

**推荐修复方向**：在软预规划完成、现有过时/清空/原生接管复核通过后，准备提前进入客诉的分支先消费同一份已核验危险计划，复用 `_apply_plan_risk`：

- 当前危险：完整处置并接管，终结本轮，不再排主回复或另走通用客诉；
- 可能危险：先保留避险提醒，再按客诉合同继续，不能因为提醒函数返回 False 就忽略投诉；
- 无投诉的正常路线继续沿原危险处理点，避免提前处置后又在最终阶段重复提醒；明确是否合并员工通知，不能静默丢掉任一风险；
- 门禁与生产的优先级同步；不增加规划调用，不允许投诉降低危险等级，失败/摘要不匹配按既有规则处理。

这是生产控制流变化，超出当前“只改提示词”的 D-4，需要先补 Spec 的文件/符号、失败与并发约束、验收及决策，再经用户确认后编码。本轮没有代改业务。

若坚持本版仅改提示词，则只能宣称“在给定样本中更准确保留危险标签”，必须把现有混合计划顺序缺口列为未修，不能把 §6.7 当作危险优先已成立。考虑它可能让已识别危险缺少处置，建议优先解决顺序问题，勿只以提示词稳定样本结案。

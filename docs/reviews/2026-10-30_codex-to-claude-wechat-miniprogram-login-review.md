# 微信小程序基础登录实现审查

日期：2026-10-30。审查对象：`feat/wechat-miniprogram-login`；功能提交 `d6ce9e2`，基线 `d1abcf5`；交接报告提交 `2c73523`。

本次实现增加了微信 code 校验、按渠道身份建档、摘要会话、恢复和退出，以及小程序按钮交互。代码复用了既有客户仓储和响应中间件，外联在数据库事务外完成。**发现两项已复现的代码缺陷、一项脱敏验收缺口，以及 PostgreSQL 专项证据缺口；目前不建议直接进入上线验收。**

没有发现客人 token 能获得员工权限的证据，也没有证明正常成功链路会返回 AppSecret、OpenID 或 session_key。上述结论不是对真实微信、真机或线上运行的验收。

## 1. 审查范围与方法

- 读取指定的 Claude 交接、登录 Spec 和上一轮 Codex 交接，并核对功能提交相对基线的全部文件清单及后端差异。
- 当前工作分支、HEAD、main 与用户指定对象一致；受审实现文件没有相对 `d6ce9e2` 的工作区差异。以下代码行号均以 `d6ce9e2` 为准。
- 沿真实链路检查 `utils/auth.js → miniprogram_login → MiniProgramAuthService.login → exchange_code → ensure_identity → sessions.create`，并检查 `/me`、`/logout`、生命周期装配、调用方和测试的反向证据。
- 本轮只写本报告。未修改代码、测试、Spec、任务记录、分支或正式认知资产；未提交、推送、部署或连接生产环境。没有读取被禁止的配置、会话或总结文件。
- 离线运行禁用字节码和 pytest/Ruff 缓存；Mypy 缓存定向系统空设备。另用纯内存 SQLite 与终端内联探针核实失败路径，没有创建额外测试文件或磁盘数据库。内联 Python 探针通过 audit hook 禁止网络连接、文件写入及被禁止文件的读取。

## 2. 问题：按优先级排列

### R1 · P2 · 代码缺陷：本机存储读取失败会误报已退出，清除失败又可能复用失效记录

**位置与符号**：`clients/wechat-miniprogram/utils/auth.js:64–73::readStoredSession`、`:118–122::ensureLogin`、`:127–145::restore`、`:151–159::logout`；`pages/index/index.js:78–96::handleLogout`。

**触发条件**：已经保存会话后，存储读取抛错；或者 `/me` 已返回 401，但 `removeStorageSync` 抛错。

**实际影响**：读取失败被转换成“没有记录”，`logout()` 直接返回，页面显示“已退出登录”，实际上没有请求服务器撤销，仍可能存在有效会话。另一路上，`restore()` 忽略清除失败，返回未登录；下一次点击登录时 `ensureLogin()` 又直接返回本地未到期的旧记录，页面误报登录成功。第二种情况不会绕过服务端的 401，但会使 UI 与服务端状态不一致；第一种情况还可能在下次读取恢复后重新出现原登录。

**独立证据**：终端 Node 探针分别复现：读取失败时撤销请求数为 0、页面为 `logged_out`；401 后清除失败，旧记录仍在，随后 `ensureLogin()` 没有重新核验或调用微信登录。既有 `tests/miniprogram/auth.test.js:34–39` 的存储替身没有读失败、删除失败模式，12 项通过不覆盖这两条路径。

**最小修订建议**：区分“没有记录”和“读取失败”，后者抛出存储错误，不让退出流程报成功；处理 `clearStoredSession()` 的失败结果，令已判失效的记录无法再被 `ensureLogin()` 当成有效会话。补两条针对上述故障的行为回归。无需新增状态管理框架。

**处理要求**：上线前修复。

### R2 · P2 · 代码缺陷：数据库异常栈会把 OpenID 参数写入日志

**位置与符号**：`src/homestay_bot/routes/miniprogram_auth.py:145–147::miniprogram_login`、`:171–172::miniprogram_me`、`:196–197::miniprogram_logout`；`services/miniprogram_auth.py:130–138::login`；`logging.py:80–113::_redact_value/redact_exception_text`。

**触发条件**：例如写入 `customer_identities` 时发生携带 SQL 参数的 `OperationalError`。仅捕获唯一冲突不能覆盖连接中断、约束以外的数据库错误等情况。

**实际影响**：登录路由使用 `exc_info` 输出完整异常，SQLAlchemy 异常的参数包含 `external_id`；现有过滤器不会识别 SQL 参数元组中的 OpenID。这违背 Spec:73“日志只记录错误类别和 errcode 数字”的本期边界。OpenID 是用户标识，不是可直接登录的 token；本轮没有把它夸大为原始 token 或 AppSecret 泄漏。

**独立证据**：在真实内存仓储的身份 INSERT 前注入合成 `OperationalError`，经过实际 HTTP 路由、`StreamHandler` 和 `SensitiveDataFilter` 后，日志仍含合成 OpenID。客户端只收到安全 503，新客户事务也确实回滚。无需真实数据库故障即可复现日志出口问题。

**最小修订建议**：在小程序认证的本地异常出口记录异常类型和固定阶段，避免直接格式化带 SQL 参数的异常；若保留调用栈，应采用不包含参数的安全表示。不要仅按字符串猜测所有 OpenID，也不要扩大修改全局数据库日志策略。补一次实际 handler 输出的反向断言。

**处理要求**：上线前修复。交接风险 6 识别了这一可能性，本轮已将其从静态可能性补证为可复现路径。

### R3 · P2 · 设计缺口：session_key 脱敏验收未实现，“会误伤函数名”的理由不足

**位置与符号**：`src/homestay_bot/logging.py:8–10::_SENSITIVE_KEY_PATTERN`、`:21–45::_SENSITIVE_QUERY_KEYS/_SECRET_ASSIGNMENT_PATTERN`、`:80–113`；Spec:116；Claude 交接第 2.2 节末段。

**触发条件**：结构化日志字段或 JSON/repr 文本出现确切的 `session_key` 键。

**实际影响**：内联探针确认 `redact_log_fields` 和 `redact_exception_text` 都保留了该键的合成值。现有新增测试只验证 session_key 不出现在 HTTP 响应，未验证它进入日志时的脱敏。当前 `_fetch/_parse` 不记录响应正文，因此没有证据表明正常微信交换正在泄漏该值；缺口是承诺的日志防护没有落地。

**取舍判断**：不接受当前理由。裸函数名 `drop_legacy_session_key` 本就不是凭据赋值；可以针对完整字段名匹配，并保留“不误伤函数名”的反向断言，不必采用宽泛的子串替换。不能把“当前不主动记录”当成“日志字段已经脱敏”。

**最小修订建议**：为完整 `session_key` 字段补结构化与文本脱敏，增加 JSON/repr、实际 handler、裸函数名不变的测试。如决定撤回验收要求，需要明确修订并确认 Spec，不能只在实现交接中声明例外；安全凭据通常没有保留明文的业务需要。

**处理要求**：上线前补齐本期验收或完成明确的方案裁决，不建议按现有理由直接豁免。

### R4 · P2 · 证据不足：生产目标数据库上的两条关键路径仍缺专项验证

**位置与符号**：`repositories/customers.py:86–116::ensure_identity`、`repositories/miniprogram_sessions.py:47–87::create`；`tests/integration/test_miniprogram_auth.py:199–209/257–283`；Spec:118。

**触发条件**：PostgreSQL 上两个首次登录同时为同一身份建档，或多个登录事务同时进行本身份删除和全局过期清理。

**风险与当前结论**：保存点隔离唯一冲突、短事务和 DELETE 的 LIMIT 子查询，从源码看均有合理基础，未发现必须重写成另一种 SQL 的证据。但是 SQLite 并发、PostgreSQL 离线 DDL及单连接内存探针，不能证明 PostgreSQL 的唯一冲突等待、事务恢复、行锁与清理行为。并发清理还涉及删除行的锁顺序，不能仅以“SQL 语法合法”宣称运行正确。

**最小补证建议**：在明确隔离的临时 PostgreSQL 上，补两个独立连接的受控并发首次登录，断言只有一份客户与身份、两个成功 token 可解析；补实际执行清理子查询、清理批量上限及事务失败回滚的测试。对已有会话数量边界可同时核实，避免无关全量替代专项。

**处理要求**：以 PostgreSQL 为部署目标时，应在上线前补证。这是验收缺口，尚不是已经复现的 PostgreSQL 代码缺陷。本轮不连接已有数据库、不创建磁盘数据库或容器，避免超出唯一写入边界。

## 4. 真实链路核实结果

### 4.1 登录、输入和事务

- `auth.js:93–114::login` 每次新登录获取 code，调用登录接口，成功后写本机存储；`ensureLogin:118–123` 对已有本地未过期记录直接返回，不等于重新做服务端认证。当前页面在 `onLoad → restoreLogin` 路径先核验，R1 是该分工下的错误分支。
- `routes/miniprogram_auth.py:93–105::_read_login_body` 同时检查声明长度和实际流式累计长度；`:126–136` 接受 JSON 对象中的 code，并限制 ASCII 与长度，不回显请求。声明超限和无 Content-Length 的分块超限已做独立 ASGI 探针，均返回 400，未调用服务。
- `_bearer_token:108–116` 限制头总长度、方案与 43 字符格式，不从 Cookie、请求体或客户编号取身份；`/me`、`/logout` 的畸形头已确认不会到达服务。此处检查的是 token 格式，真正有效性仍由摘要查询决定。
- `MiniProgramAuthService.login:122–128` 在外联前取得窗口和在途名额，`finally` 无论成功、失败或外层取消均释放在途数；窗口次数保留到自然到期。这不是把失败请求错误地“退回额度”。本轮取消探针确认 CancelledError 传播且名额释放。
- `login:130–155` 在外联结束后才调用会话工厂、进入 `session.begin()`；复用 `ensure_identity`，后者在保存点中捕获唯一冲突，再用同一外层事务签发会话，提交后才返回 token。本轮工厂探针确认外联时尚未调用数据库工厂，数据库阶段开始时在途名额已释放。INSERT 故障确认新档案回滚。
- 闸门限制的是“同时调用微信”的请求，不覆盖之后的数据库阶段，符合 Spec:75。它不是数据库连接池的容量控制。
- `_read_login_body` 在路由服务调用的 try 之外；流读取断连等异常不会被误报成 code 无效。三个路由的广义 Exception 会映射安全 503，程序错误仍被记录，取消属于 BaseException 不被吞掉。已发现的具体问题是 R2 的日志内容，不是取消被转成普通失败。

### 4.2 微信客户端、日志与响应

- `exchange_code:101–111` 有外层总超时；`_fetch:113–141` 逐次创建并关闭 AsyncClient、禁重定向、检查非 2xx、按流计数正文，不自动重试；`_parse:144–169` 先判断整数 errcode，再校验 OpenID，不返回其余响应字段。
- 凭据加载在 `load_miniprogram_credentials:67–78` 完成；`MiniProgramCredentials.app_secret:64` 不进入 repr。请求路径固定，客户端没有可提交的任意上游地址。
- 新增的 `js_code` 脱敏与已有 secret/Bearer 规则有实际异常文本测试；网络异常通过 `from None` 抑制原异常链。没有把 HTTP 成功正文带到路由日志的调用点。R2、R3 分别指出本地 SQL 参数与未覆盖字段的边界。
- 路由成功仅返回 token、到期与显示名称，`/me` 不返回 token；错误只返回固定字段。Middleware 在路径边界给认证响应加 no-store，复用了集中策略而不是逐路由复制。
- 字段和错误映射与本次 Spec 的本地定义一致。本人没有访问微信文档或真实接口，不能确认作者声称的官方文档阅读时间、当前线上契约或真实返回行为；MockTransport 仅证明代码遵守测试内定义的契约。

### 4.3 会话、身份与 0036

- `services/miniprogram_auth.py:98–100/131–133` 使用 32 字节随机 token 和 SHA-256 摘要、固定 24 小时；`sessions.resolve:102–106` 使用严格未到期条件，没有滑动续期。摘要不能作为原 token 使用。
- `logout → service.logout:169–172 → repository.revoke:115–119` 是带提交的删除；格式正确但已删除/过期/不存在的会话重复退出仍为 204，撤销异常返回 503。网络故障时客户端保留记录这一正常路径有 Node 覆盖；存储故障见 R1。
- 员工入口 `require_employee_session:397–418` 读取签名 SessionMiddleware 的员工字段并复核权限；小程序入口只读取 Bearer。没有共同的角色授予路径。现有集成测试:419 使用的是伪造 Cookie，不能单独称为“有效员工会话已验”；该方向的隔离还由路由源码核实支持。
- 会话外键指向身份，人工合并更新身份的 customer_id，`/me` 每次重新 JOIN 到当前未合并客户。没有把初次 customer_id 固定在 token 中；当前也没有订单访问接口。
- `MiniProgramSession:240–264` 与 `0036:13–40` 的字段、token_hash 唯一约束、两个索引及身份外键 CASCADE 一致。升级新增空表；降级只删除该表及索引。内存探针实际执行升级、插入、身份删除级联、降级、重新升级，并核对保留客户行。
- 每身份 5 条是**软上限**：`sessions.create:44–45` 已说明并发偏差；Spec:58 仍写“最多 5 条”。未证明它造成鉴权越权，但“已知”不能自动等于“用户已接受”。应补齐取舍记录或同步 Spec；若业务要求硬上限，再在同一身份上串行化。不要把顺序登录的上限测试当作并发硬上限证明。

### 4.4 客户端与装配

- `index.js` 的 authBusy 防止本页面重复操作，代次比较能丢弃旧结果；既有 Node 测试通过。本轮没有将测试里人工递增代次误称为微信真实页面生命周期或真机回调顺序验收。
- `auth.js:106–112` 在 setStorageSync 失败后发起撤销，但不会区分撤销的非 2xx 响应，并吞掉网络补偿失败。独立探针确认撤销返回 503 时仍只报告存储失败。页面没有误报登录成功，因此不另列上线阻断；建议明确提示“撤销未确认”，保留固定到期的残留边界，不增加无界自动重试。交接不能将“尝试撤销”写成“必定撤销”。
- 本地清除失败的返回值在 logout 中有处理，但 restore 两处分支没有处理；这是 R1 的关键调用点差异，不能仅因存在 `clearStoredSession()` 就认定完整覆盖。
- `application_lifespan:4420–4430` 使用可选配置装配独立认证服务，`_clear_lifespan_state:4324` 移除它。每次外联连接在调用内关闭，没有额外长驻 HTTP 客户端需要加 shutdown 路径。
- 本轮对真实生命周期分别传入缺失、无效、有效三类合成配置，确认服务是否装配与退出后 state 清理；为遵守边界，替换了私有文件存储、管理员引导和运行快照发现，禁止外联。这比仅手工设置 app.state 更接近装配验证，但仍不是完整生产启动验收。
- 没有新增依赖或平行客户体系。路由、客户端、服务、仓储的职责与现有项目分层一致；Protocol 和小结果类型服务于现有调用边界，未发现必须拆合模块的收益。模板 logs 页与工具函数没有当前 UI 入口，清理优先级低，不应扩大为无关重构。

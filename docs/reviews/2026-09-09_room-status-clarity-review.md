# 房态与本地流程：设计审查和简化建议

本报告保留审查依据和设计演进。姓名住宿条与倒计时的最终编码交接以 `docs/specs/2026-09-09_room-stay-timeline-countdown-spec.md` 为准；执行者不得叠加本文较早或范围更宽的建议。

日期：2026-09-09。源码基线：`6ae177f`。生产浏览器侧栏版本：v1.18.0。

目标：老板／管家一眼看懂房间入住安排，不把“本系统尚无准备记录”误解为“房间没入住”；兼顾员工手机操作。本报告供 Claude 等后续实施者独立阅读，不是已确认的实施 Spec。

## 合并方案：房间状态、客人倒计时、跨日期住宿条与客户入口

本节基于用户所提供页面截图及当前源码 `2f3044b`；优先于本文早期关于姓名位置和日期格的建议。只使用合成客人称呼描述设计，不将真实姓名写入文件。

**设计：顶部显示房间状态，中间两行显示对应客人的退房／入住倒计时，下方显示可点击姓名的跨日期住宿条。** 姓名从房间标题右侧移除，只在有明确日期和事件含义的位置出现。近期安排默认展示紧凑日期轴和住宿条，避免把移动后的姓名藏在默认折叠里；详细说明仍可展开。

### 卡片布局与客人倒计时

示例为合成订单，当前时间假设 9/9 04:00，客人 A 今日退房、客人 B 今日入住：

```text
A101                                     今日周转

本次退房  客人 A   还有 8 小时    今天 12:00（计划）
下一单    客人 B   还有 11 小时   今天 15:00 起入住
计划周转间隔 3 小时

9/8                        9/9                       9/10
    [客人 A · 1 晚 ── 至 12:00]
                                [15:00 起 ── 客人 B · 1 晚 ── 至 12:00]

待办 2 项，其中 1 项逾期                        去处理
展开：本系统准备情况、同步来源、调整记录
```

示例的文本图不表示精确像素比例；正式条段按日期列及计划时刻对齐。倒计时中的姓名与住宿条中的姓名都链接同一个真实客户档案。卡片不再同时重复旧版“下次入住／下次退房”日期区块和通用三段计划横幅；由两行绝对时间、倒计时和周转间隔提供信息。

**退房与入住必须各自绑定完整订单，不能分别拿一个最近日期和一个客人名拼接。** 已入住事实未确认时，用“本次退房／本次住宿”代替断言“当前在房客人”。下一单是当前住宿之后的那笔有效订单，不能把当前客人今天的到店计划重复当作下一位客人。房间尚无当前住宿时，第一笔未来订单显示“下一单”，其退房时间放入该住宿条详情，而不是虚构当前客人。

| 情况 | 文案与行为 |
|---|---|
| 退房节点未到 | “客人 A · 距计划退房还有 8 小时 · 今天 12:00” |
| 已确认延迟至 14:00 | 倒计时改算到 14:00，显示“延迟至 14:00”；只有申请尚未批准时不改时间 |
| 退房节点已过，仍无确认 | “计划退房时间已过 30 分钟 · 退房待确认”，不认定客人仍在房或已经离开 |
| 本次订单已有可信退房事实 | 显示“已退房”，不继续催这位客人退房；无精确时间时不显示虚构的实际时刻 |
| 只有默认 15:00 入住政策 | “下一单 客人 B · 距可入住时间还有 6 小时 · 今天 15:00 起”；不是“客人将在 15:00 到达” |
| 有可信的客人预计到店时间 | 可显示“客人 B · 距预计到店还有 6 小时 · 预计 18:00”；仍保留合同／政策规定的准备期限，预计晚到不自动把 15:00 就绪要求推迟到 18:00 |
| 到了计划入住时间，实际到店未知 | “已到可入住时间 · 到店待确认”；不自动显示“已入住”或“客人迟到” |
| 本次订单已有可信入住事实 | 停止该订单到店倒计时，转为展示它的计划退房节点 |
| 同一客户接续住宿 | 标签写“续住安排”，按客户 ID 与订单事实判断；保留订单边界，不误说换客，也不自动制造清洁要求 |
| 当前可查范围没有下一单 | “当前同步范围内暂无后续订单”，不显示假的 0 小时或对可售作出承诺 |
| 同步过期 | 主区提示“入住安排待核实”，已有倒计时标为“按上次同步计划”，不能用持续跳动的数字暗示数据刚更新 |

两笔不同客户同日周转时，“计划周转间隔”按下一单可入住时间减本次计划／已确认延迟退房时间计算；默认 12:00–15:00 为 3 小时。它不是实际清洁耗时，也不是已经分派人员的承诺。间隔缩短用提示色，零或负间隔标为时间冲突；没有同日下一单时不显示虚构的当日清洁倒计时。

倒计时以 Asia/Shanghai 和服务器给出的当前时间为基准：24 小时以上显示“X 天 X 小时”，不足 24 小时显示“X 小时 X 分钟”，不足 1 分钟显示“不足 1 分钟”。不显示秒级跳动，不每秒请求服务器。绝对日期时间始终保留，跨日显示“明天／月日”。前台按分钟更新，跨 12:00／15:00 或标签恢复时刷新读取结果；只有重新取到数据才更新“最近同步”时间。

### 日期条与快速查看客户

- 示例：客人 A 的订单为 9/8 至 9/9，住宿条从 9/8 的计划 15:00 延伸到 9/9 的计划 12:00，条内显示“客人 A · 1 晚”，边界显示“8 日到店／9 日离店”。这些是计划时间，不代表已确认发生。
- 若客人 B 于 9/9 到店，另一条从 9/9 计划 15:00 开始；9/9 的两段分别属于离店和到店客人，12:00–15:00 保留周转空隙。不能把两位客人画成同一天整格重叠入住，也不能把退房日期算成额外一晚。
- 同一条只写一次姓名，不在每个日期格重复；宽度不足时截断文本，但保留完整可访问名称，点击区域满足手机操作。跨出可见日期窗口时显示延续标记，并提供完整住宿日期。
- 姓名链接直接复用 `/employee/customers/{customer_id}`，同页打开客户档案，正常支持新标签打开与键盘操作。返回时保留原时间范围；不新增客户弹窗或另一套客户详情页。
- 只用关联的 `Customer.display_name` 和 `customer_id`；不能根据同名猜测客户。缺姓名但有 ID 时显示可点击的“查看客人”；无关联 ID 时显示“未关联客人”，不生成假链接，住宿安排仍需可见。
- 同名不同 ID 必须独立；同一客人的相邻订单本轮也保留订单边界，不自动合并或改变连住业务判断。真实重叠订单分行并标明冲突，不能用布局掩盖。
- 日期格已有住宿条时，移除重复的“入住 1／退房 1／在住”计数堆叠；保留日期、今天标记、到离店边界和必要冲突提示。无订单区域只写“无订单”，不推断可售。
- 使用已确认延迟时间时才调整退房端点；没有精确时间数据时沿用 12／15 点计划并明确标注，不由日期格猜测。

当前源码依据：`repositories/admin_operations.py::StayRecord` 已有 `customer_id`、`guest_name`、入住和退房日期；`list_room_stays` 已左连接 `Customer.display_name`，无需按客人新增逐条查询。`services/admin_operations_service.py::RoomDayOperation` 仍只保留到离店计数和占用布尔值，`_room_items` 生成时间轴时丢失了订单身份；因此不能只把房间级 `guest_name` 塞入日期格，那会把当前客人错误地贴到历史或下一单日期。`templates/admin/operations.html` 的 `.room-guest` 是目前孤立姓名的来源；`templates/components/ui.html::room_timeline` 当前只渲染每日计数。

倒计时新增核查：当前 `_room_items` 的 `next_arrival` 从 `check_in_date >= local_date` 选日期，但 `next_guest_name` 从 `check_in_date > local_date` 选姓名，两者可能来自不同订单。实施时应一次选择完整的到店／退房事件（订单 ID、客户 ID、姓名、事件时间和来源），统一供倒计时与日期条使用，不能直接沿用这两个分离字段组合。重叠或相同日期的多笔订单不能任意选一个假装唯一客人，应显示有多笔安排并在时间轴分别列出。

最小文件计划（路径统一以 `src/homestay_bot/` 为前缀）：

1. `repositories/admin_operations.py::StayRecord/list_room_stays`：复用已有姓名、客户 ID 和日期投影，补齐用于稳定标识每笔住宿的订单 ID；不改数据库表。

3. `templates/components/ui.html::room_timeline`：原生链接渲染跨日期住宿条，区分计划到离店端点、周转与跨窗口延续。
4. `templates/admin/operations.html` 与 `static/app.css`：移除标题旁孤立姓名，添加两行客人倒计时，去掉被替代的重复日期／计划区块，调整日期轴布局和手机滚动。客户详情路由和权限保持原有实现。
5. `static/admin.js`：复用现有页面生命周期方式，补充分钟级倒计时更新、跨节点及恢复标签页后的读取刷新；检查已有定时器，避免重复计时和重复请求，不提交业务操作。

## 核心结论

**入住安排做主信息，本系统工作记录做辅助信息；缺少记录显示“未确认”，不显示成现实中的“未开始”。**

不能通过把本地状态批量改成“已入住”来消除界面矛盾。其他路径可能完成入住，但当前页面是否拿到了相应事实，需要分别判断。

本次现场确认：待处理房间出现“今日入住／今日退房 + 运营：未开始”；卡片下方再次出现“房态：未开始”的选择框。稳定房间标题区只显示“运营：未开始”。这些显示会把本地流程状态放大成房间的整体状态。

## 用户补充后的设计基准：12 点退房，12–15 点清洁，15 点入住

用户已明确正常营业节奏：**12:00 计划退房（可能延迟），12:00–15:00 周转清洁，15:00 起入住**。全部按民宿当地时间 Asia/Shanghai 展示。本节细化下文的按日展示建议；发生冲突时优先采用本节。时间是计划节点，不是实际事件，也不表示每间房都需要整整三小时清洁。

### 卡片上只回答三件事

1. **现在是什么情况**：有可信记录时显示实际状态；没有时显示计划或“待确认”。
2. **下一个时间点是什么**：计划退房时间、当日下一单入住开放时间；已知延迟退房时显示调整后的预计退房时间。
3. **现在需要做什么**：最多一个主动作；本系统流程缺记录不要求员工重新走流程。

有同日周转时，紧凑安排条为：`12:00 计划退房 → 12:00–15:00 计划清洁 → 15:00 起入住`。没有今日退房的房间不画退房步骤；没有今日到店的房间不制造 15:00 入住期限。完整跨日时间轴继续按需展开。

### 正常周转日随时间变化的显示规则

| 时间／证据 | 主状态 | 辅助说明与动作 |
|---|---|---|
| 12:00 前，今天退房、尚无实际退房记录 | 今日退房 | “计划 12:00 退房”；若有同日下一单，同时显示“下一单 15:00 起入住” |
| 到 12:00，尚无退房记录，也无确认的延迟安排 | 退房待确认 | “计划退房时间已到，现场情况待核实”；不叫“已退房”或“客人超时” |
| 已确认退房，尚无本轮清洁开始记录 | 已退房 · 清洁待确认 | “计划周转时段 12:00–15:00”；可能已由其他路径清洁，不断言未开始 |
| 有本轮清洁开始记录 | 清洁中 | 有当日下一单时显示“下一单 15:00 起入住”；未开始记录不能仅因到了 12 点自动产生 |
| 清洁已报告完成，但准备条件尚未确认 | 待检查 | 使用已有检查流程；不能把“清洁完成”直接当成可发放入住凭证 |
| 当前周转周期已确认准备就绪 | 已就绪 · 等待到店 | “15:00 起入住”；准备就绪不等于已经入住，也不等于允许提前入住 |
| 到 15:00，尚无准备确认 | 入住准备待确认 | 只在当天确有下一单时突出提醒；已通过其他路径处理的，可更新当前情况，不要求重做 |
| 到 15:00，已就绪但尚无实际到店记录 | 等待到店确认 | “15:00 起可办理入住”；不能仅因时间已到就显示已入住 |
| 已有可信实际入住记录 | 已入住 | 明确来源；本系统准备流程缺记录不覆盖这一事实 |
| 后续住宿日只有订单日期证据 | 住宿期内 | 显示计划离店日期及 12:00；不声称已核验实际入住 |

可信实际记录必须对应当前订单／本轮周转，旧住客的入住记录和上一轮清洁状态不能沿用。上表的“实际记录”是目标设计条件，本次尚未确认当前系统已有足够的数据支撑所有分支。

### 延迟退房只突出影响，不让管家计算

- 区分“客人申请延迟”和“管家已确认延迟”；申请本身不能改变计划。延迟许可属于经营决定，不由 AI 或时钟自动批准。
- 已确认延迟到 13:00：显示“延迟退房至 13:00”，有 15:00 下一单时附“退房至下一单入住间隔 2 小时”。这是可用时间，不是承诺两小时内一定能完成清洁。
- 已确认延迟到 14:00：显示“延迟退房至 14:00 · 距下一单入住 1 小时”，标记“周转时间缩短”，主动作是“查看周转安排”。不因缺少本地清洁记录直接判定已延误。
- 延迟至 15:00 或更晚且当天有下一单：突出“与下一单入住时间冲突”，交管家协调。不自动同意延迟、不更改下一单入住承诺、不发送通知。
- 无当日下一单：显示新的退房安排即可，不生成与 15:00 入住冲突的告警。过了新的退房时间仍未确认，显示“退房待确认”，不自动认定客人仍在房。
- 只有退房待确认但没有已批准的延迟时间时，不显示虚构的“延迟到几点”。

示例（合成房间、合成已确认延迟，当前为 13:30）：

```text
A101                         延迟退房至 14:00
下一单 15:00 起入住          周转间隔 1 小时
周转时间缩短                 查看周转安排
```

### 操作仍然简单，允许其他路径已处理

房态主状态保持只读；低频入口为“更新当前情况”。只呈现当前场景相关选项，例如记录实际退房、记录已入住、确认延迟时间或查看已有清洁任务。员工不需要先启动一整套任务，才有资格记录现场已发生的事实。涉及许可的延迟由管家确认，实际事件与准备就绪维持各自权限和审计。

“更新当前情况”是拟议功能，不代表目前已有这些操作；实施前需确认记录来源、订单关联、发生时间、冲突处理和权限。不会通过将本地 `RoomOperationalState` 任意改值来绕过检查、更新 Hostex 订单或触发凭证发送。

### 当前代码缺口与最小实施分层

`src/homestay_bot/services/admin_operations_service.py::_room_items` 当前只按 `local_date` 和订单日期计算；`RoomOperationItem` 没有当日实际退房时间、确认的延迟退房时间或实际到店时间。`src/homestay_bot/domain/models.py::StayOrder` 具有入住／退房日期、原始状态和 `checkout_observed_on`（日期），这些字段不能直接回答“今天 13:30 客人是否已退房”。现有 `LATE_CHECK_OUT` 任务类型也不等于已批准具体延迟时刻。

**先完成有现有数据支撑的展示层：** 12／15 点计划安排、计划与实际措辞区分、未知状态弱化、全部房间可见、零待办不等于未生成。跨越 12:00／15:00 后页面提示应及时重算，后台标签页恢复时更新，不应要求用户手动刷新才看到新阶段；只更新读取结果，不借定时刷新提交业务操作。

**需要实际事实才能启用的部分：** 延迟至具体时间、已退房／已入住以及对应的更新入口。先核对 Hostex 可提供的事实与本地已有记录，能复用就复用；缺失时再确定最小记录方案。不能只改模板就假装已经实现真实入住状态跟踪。

## 2. 推荐的最小页面结构

### 每间房始终可见，一眼先看入住安排

对当前小规模房源，默认以紧凑房间行／卡片展示全部房间；需要关注的排前面。不要把正常在住的房间藏进“稳定房间”折叠。手机端同样显示完整房间列表，只折叠每间房的低频详情。

每行默认只放：**房间名、主状态、最近入住／离店日期、确有必要的待办或异常**。3／7／14 天时间轴移到“查看近期安排”后展开，避免每间房的日历占据第一屏。

主区标题用“入住安排”，标注来源“百居易订单”。首页若保留“当前房态”标题，其统计必须来自相应入住投影；最小文案修复则先把原统计改名“本系统工作记录”，不要继续把它当实际房态。

### 状态文字按证据强度表达

| 当前可确认的依据 | 主状态建议 | 不应推导的结论 |
|---|---|---|
| 今日为订单入住日 | 今日到店；来源说明标明按订单 | 不代表尚未到店，也不代表已办理入住 |
| 今日落在订单住宿区间内，非到离店日 | 住宿期内 | 不等于已核验客人在房 |
| 今日为退房日 | 今日离店 | 不代表已经退房或房间已腾空 |
| 同日有离店与到店 | 今日周转 | 不代表一定需要再创建保洁任务 |
| 今日没有同步到的有效订单占用 | 今日无订单占用 | 不叫“近期空置”，不等于可售或可入住 |
| 同步过期或来源不足 | 入住信息待核实 | 不显示确定空房或无入住 |
| 将来确实取得可信的实际入住／退房事实 | 已入住／已退房，并注明来源 | 本次未证明当前投影拥有这类事实，不能直接实施自动判断 |

“今日到店／离店”是当天安排，不作为“尚未完成”的断言。来自其他渠道、但已进入百居易并成功同步的订单，应参与同一投影；完全未进入事实源的线下入住不能靠本系统无任务自动猜出。

### 本系统记录降为辅助，未知不制造告警

- `NOT_STARTED` 在房间页面显示“本系统准备情况：未确认”，详情解释“未确认不代表未入住或未完成准备”。由于当前查询合并了缺记录和显式 NOT_STARTED，暂不声称“完全没有记录”。不更改任务自己的“未开始”等其他业务标签。
- 已有的保洁中、待检查等明确工作记录可简短展示；维修和真实待办保留醒目提示。普通“未确认”使用中性文字，不单独触发待处理或红色告警。
- 现有本地 `OCCUPIED` 显示为“本系统记录：已入住”，不能与百居易订单占用混为同一个字段；与订单不一致时展示来源差异，不能静默覆盖。
- 未确认状态放在展开信息里；若当天到店确实需要管家核实，可显示一句“准备情况未确认”，但不能要求重走一遍任务流程。

示例（仅为展示建议，日期和房间为合成数据）：

```text
A101                         住宿期内
预计 9 月 12 日离店 · 百居易订单
待办 0 项                    查看详情

展开详情：
本系统准备情况：未确认
此处未确认不代表未入住或准备未完成。
```

## 3. “下一步”和操作一起简化

1. **有实际开放任务**：显示“处理 2 项待办”，进入对应任务；有逾期保留提示。不能因订单进入住宿期就自动完成或隐藏遗留任务。
2. **无开放任务**：显示“当前无待办”，不说“尚未生成任务”。当天到离店时可提供“查看入住安排／核对准备情况”；住宿期内无异常不催促重新准备房间。
3. **有来源冲突或确切异常**：显示“核对入住信息”等具体原因，再给相关详情入口；单纯本地准备未确认不算已证明冲突。
4. **修改本地记录**：取消每张卡片上常驻的六状态下拉框和“保存”。收进详情或“调整本系统记录”，明确“仅更新本系统记录，不办理百居易入住／退房”。少量低频动作多一次展开，换取房态列表更易扫描。
5. **保留已有安全约束**：管理员权限、人工覆盖审计、可入住证据说明、禁止危险状态跳转等继续保留；文案和布局简化不改变凭证发放门禁，不增加自动发消息、自动改订单或自动补任务。

## 4. 实施范围与验收

建议作为同一个房态语义修复单元：共享展示 → 房间列表／详情／首页 → 下一步文案 → 一次针对性验收。复用现有模板与聚合结果，不新建另一套订单数据源，不增加数据库状态枚举来修复纯展示歧义。

主要文件和职责：

- `templates/components/ui.html`、`web.py`：区分订单状态和本系统记录的文案、层级；检查所有共享映射调用方，不能全局把任务“未开始”替换掉。
- `templates/admin/operations.html`：全部房间可扫读、时间轴按需展开、本地调整入口收纳。
- `templates/admin/dashboard.html`、`services/admin_dashboard_service.py`：当前房态统计口径对齐；复用已有运营快照，避免另造分类规则。
- `templates/properties/detail.html`、`services/property_admin_service.py`：详情保留同一入住事实与本系统记录的来源区分。“今日无入住退房”不能替代当前占用状态。
- `services/admin_operations_service.py::_next_step`：去除零开放任务等于未生成的假设，行动与证据一致。

验收场景：

1. 百居易订单覆盖今天、本地没有状态：主状态仍显示订单入住安排，辅助状态为未确认，不能显示整体未开始。
2. 已由其他路径完成准备且没有开放任务：不催促重新开始；没有实际入住事实时也不擅自标为已办理入住。
3. 当天到店、住宿期间、当天离店、同日周转、今天无订单但明天有订单：状态文字各自准确。
4. 准备情况未确认与维修中、逾期任务分别处理，不能为消除界面矛盾隐藏真实异常。
5. 同步过期时明确待核实；无订单不等于可售；本地调整不修改百居易。
6. 首页、房间列表、房间详情和手机端使用同一语义；正常房间无需展开才能看到主状态。

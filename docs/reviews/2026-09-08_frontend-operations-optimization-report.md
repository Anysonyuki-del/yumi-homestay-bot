# 前端交互与运营功能精简方案

日期：2026-09-08。状态：审查结论与待确认方案，未实施。适用读者：项目负责人、Claude 及后续开发者；无需阅读此前聊天。

**建议把管家的日常入口收敛为一个“今日工作台”，提供“今天、房间、全部任务”三种视图；将员工手机端收敛为“我的工作”。优先减少找入口、重新筛选、理解状态和重复提交的成本。**

用户已确认：**老板/管家日常调度优先，兼顾员工手机操作。** 本轮没有授权修改业务实现、提交、部署或生产操作。本方案不是已批准的实施 Spec。

## 1. 审查依据及边界

- 源码基线：检查时 HEAD 为 `3c9d963c47ffe1f7deacd6a6841de882acabf6cf`，工作区有其他任务的未提交修改。结论包括这些改动，不能仅凭提交号重建全部现场；实施前按文件和符号重新确认。
- 方法：两路独立源码评审，一路评估业务流程，一路检查交互与检测器信号；主代理补充真实模板、CSS、JS 的本机浏览器预览。
- 浏览器：使用现有测试应用和假数据，在 `127.0.0.1` 提供只读 GET 预览；桌面 1365×900、手机 390×844。未连接生产、未调用 DeepSeek/Hostex/企业微信。预览拒绝全部 POST，结束后已停止服务并关闭临时标签页。
- 预览复用 `tests/integration/test_task_routes.py::build_client` 与 `tests/integration/test_admin_dashboard_routes.py::DashboardStub/OperationsStub`。测试替身中的房名、日期、缺失字段、重复日期和默认版本仅为样本，**不能作为生产数据错误或版本问题**。
- 自动检查：`node .agents/skills/impeccable/scripts/detect.mjs --json src/homestay_bot/templates` 返回 exit 0、`[]`，但提示缺少 HTML/CSS 解析依赖，只进行了降级正则扫描。不能据此声明无障碍、对比度或视觉质量通过。浏览器接口不支持任意页面写入，未注入检测 overlay。
- 审查重点为总览、待我关注、房态与运营、任务列表、任务详情和共享导航；其他页面只检查导航关系，没有宣称审批、客诉、CRM、设置等所有页面均完成端到端验收。
- 此轮未修改实现，因此没有重跑业务全量测试；之前代码审查的 1406 个通过结果不能作为本轮并行改动的测试证明。

以下路径均相对仓库根目录。模板以 `content/page_actions` 块或具体 HTML 元素为符号依据；行号只是当时定位提示。

## 2. 主要发现：复杂性来自工作流程割裂

### U-01：同一件工作散落在四个并列入口

**证据与路径：** `src/homestay_bot/templates/layouts/admin.html::side-nav`（25–32 行）并列放置总览、待我关注、房态与运营、任务中心；`src/homestay_bot/templates/admin/dashboard.html::content` 的人工关注、逾期、审批、任务计数又分别跳转不同页面。今日入住与退房名单只有房名和标签，没有对应动作。

现有路径之一：总览 → 房态与运营 → 某房间开放任务 → 单条任务详情。另一条是：总览 → 待我关注 → 房源任务分组 → 单条任务详情。管家需要先判断记录属于哪个模块，再寻找具体工作。

**建议：** 一个日常工作入口承担“今天先做什么”；房间和任务列表成为同一工作入口下的不同视图。审批、投诉等保留自己的操作和权限，只把需要当前人处理的事项引入工作台，不把所有领域记录改成任务。

### U-02：“下一步”是文字，实际动作需要重新寻找

**证据与路径：** `src/homestay_bot/services/admin_operations_service.py::AdminOperationsService._next_action`（486 行起）已能区分逾期、退房周转、入住准备、维修等建议；`src/homestay_bot/templates/admin/operations.html::room-next-action`（26 行）只用 `strong` 展示文字，任务链接只带 `property_id`（28 行）。常驻的直接操作却是房态下拉框和“保存”（32–36 行）。

**建议：** 每张房间卡给一个与原因对应的主动作。例如“2 项逾期”直接进入该房间的逾期队列；只有一个可操作任务时直达详情。不能在只知道数量时猜某个任务 ID。人工改房态移入管理员专属“人工调整”，保留领域守卫、确认和覆盖审计。

### U-03：筛选、详情和完成后的返回没有形成连续工作流

**证据与路径：** `src/homestay_bot/templates/tasks/index.html::任务详情链接`（49、51 行）只带任务 ID；`src/homestay_bot/templates/tasks/detail.html::page_actions`（4 行）固定返回 `/employee/tasks`。`src/homestay_bot/routes/tasks.py::assign_selected_tasks`（517 行起）成功后返回默认列表；`src/homestay_bot/routes/properties.py::set_room_operational_status`（241 行起）保存房态后固定跳到房源详情，而不是原运营视图。

浏览器从带 `property_id=101` 的任务列表进入详情，返回按钮仍为 `/employee/tasks`，确认该页面返回入口丢失房源条件。分页链接本身已保留筛选，不能笼统认定所有导航都有问题。

**建议：** 沿列表、详情和表单携带经过 `src/homestay_bot/routes/page_errors.py::safe_return_path` 校验的来源路径，保留房间、队列、日期范围和页码；成功后显示做成了什么，并提供回原列表或处理下一项。某项完成后列表变短时回到最近有效页；“下一项”必须重新校验权限与最新状态。

### U-04：列表给出了分类，没给出足以采取行动的摘要

**证据：** `src/homestay_bot/templates/tasks/index.html::data-table/mobile-record-card` 展示类型、日期、房间、员工、状态，但任务说明只在 `src/homestay_bot/templates/tasks/detail.html::detail-grid`（14 行）出现。`src/homestay_bot/services/task_page_service.py::TaskPageService.detail_for`（299 行起）已经通过 `_safe_description` 处理说明。

同一房间两条“维修”或“补给”在列表里不容易区分，管家必须逐个开详情。

**建议：** 列表增加一行安全摘要及必要的阻塞原因，例如“补充浴巾 · 尚未分派”；复用现有脱敏规则，不能直接展示原始客人消息。把统一的“处理任务”改成与当前状态相符的“补全并分派”“开始处理”“查看检查”等动作。

### U-05：批量功能已有，但动作反馈和确认不准确

**证据：** `src/homestay_bot/templates/tasks/index.html` 已有批量分派、取消、归档、永久删除；批量区依据整页条目显示能力，`src/homestay_bot/static/admin.js::syncMirroredSelection` 及选择监听主要负责同步勾选和全选状态，未展示实时“已选多少、当前能做什么”。模板还同时描述“只作用于它接受的那部分”和“混入不合格条目会整批拒绝”，两种含义冲突。

**具体缺陷：** 批量表单的 `data-confirm` 固定为归档文案（模板 45 行），分派按钮只更改 `formaction`（58 行）。`src/homestay_bot/static/admin.js::form[data-confirm] submit listener`（143–152 行）只为 typed-confirm 按钮跳过该确认。独立评审执行真实监听片段并输入分派按钮替身，得到的仍是“确定把勾选的任务移入归档吗”。本机浏览器点击后预览返回 405；该次点击没有提供可靠的原生弹窗正文证据，也未证明分派成功。

**建议：** 先修正动作与确认文案的对应。选中后才显示批量栏，明确“已选 6 项，其中 2 项缺少房间，暂不能分派”；解释哪些条目不合格，提供清除不合格选择的显式操作，不暗中只处理一部分。后端仍整批校验，界面提示不能替代权限、状态和并发检查。

### U-06：手机端在任务之前展示了过多筛选，批量动作离选择太远

**证据：** `src/homestay_bot/templates/tasks/index.html::filter-disclosure` 在存在附加筛选时自动展开。因此从房间卡进入带 `property_id` 的列表，会展开状态、类型、日期、房源、员工、逾期、归档七类条件。唯一“全选本页”位于桌面表头；手机隐藏该表格，卡片只有逐条选择。`src/homestay_bot/static/app.css::.selection-actions` 是普通布局，放在任务列表之后。

浏览器测试样本在 390×844 视口中，进入房源筛选后的列表：`filterOpen=true`，首条任务卡距页面顶部约 **1084px**，批量区约 **1194px**，没有可见的全选控件。样本仅一条任务，测量用于证明该路径首屏被筛选占据，不推断生产列表的实际滚动长度。

**建议：** 生效筛选显示为“长江中心 ×”等条件标签，不因有条件就自动展开全部表单。手机点“选择”才进入批量模式，提供可见的本页全选和底部操作栏；留出底部空间，不能遮住最后一条任务或键盘焦点。第一页以 20/50 条等现有分页能力为基础验证，不做跨页隐式全选。

### U-07：现场工作被拆成多次保存，两个“完成”含义不清

**证据与路径：** `src/homestay_bot/templates/tasks/detail.html::action-stack`（35–48 行）分别提供开始、保存清单、上传照片、提交检查、确认房间可入住、标记任务完成。`src/homestay_bot/static/admin.js` 已有跨表单未保存提醒，所以在一个表单选照片、另一个表单保存清单会涉及未保存内容处理。

`src/homestay_bot/services/room_readiness_service.py::RoomReadinessService.mark_ready`（85 行起）校验证据并改变房态、评估凭证；它不完成任务。`src/homestay_bot/services/business_task_service.py::BusinessTaskService.transition` 处理任务状态，也不等于房间达到可入住条件。手机预览中，待检查任务同时显示保存清单、上传照片、确认可入住、标记完成，四个独立提交入口。

**建议分两步：** 先做一个执行区域，清楚显示检查项、照片和当前缺失条件，突出当前主动作；再在经过业务确认后合并清单与照片的用户提交体验。保洁能否用“确认收尾”一次完成房态与任务，应在 Spec 决定，不能静默关联凭证发送或绕过证据门。

## 3. 已经做对的部分，应当保留

1. 运营页已有风险房间优先、稳定房间折叠、时间轴辅助视图，入住事实与准备度分开。依据：`src/homestay_bot/templates/admin/operations.html::operations-rooms/operations-stable`、`src/homestay_bot/services/admin_operations_service.py::RoomOperationItem.needs_attention/_room_risk_sort_key`。
2. 当前源码已修正历史上的桌面/手机重复勾选、分派字段未回填、筛选归档字段丢失、手机紧凑总览隐藏等问题。依据：`src/homestay_bot/static/admin.js::syncMirroredSelection`、`src/homestay_bot/templates/tasks/detail.html::assign form`、`src/homestay_bot/templates/tasks/index.html::archive-filtered form`、`src/homestay_bot/templates/admin/operations.html::table-scroll`。不能照搬旧审查结论。
3. 已有提交中提示、防重复提交、CSRF、权限和审计；已有批量分派与提醒就地处理。优化应使能力更易理解，不重复开发一套。
4. 取消、永久删除和敏感经营动作的保护属于必要成本。不可逆批量操作仍需明确勾选、准确数量和确认；不能用“一键清空待办”作为精简方案。

## 4. 三种方案比较

| 方案 | 具体做法 | 收益与代价 |
| --- | --- | --- |
| A：只修局部交互 | 修确认文案、返回路径、筛选折叠、选择反馈 | 改动小，能立即减轻摩擦，但仍需要在四个入口之间寻找工作 |
| **B：统一今日工作入口（推荐）** | 复用当前投影与服务，整合今天/房间/任务三个视图，提供准确主动作和连续处理 | 同时降低寻找、理解和往返成本；需要确认入口和聚合口径，但不必改成新前端框架 |
| C：重做任务与工作流引擎 | 重建领域状态、统一所有业务记录、重写前端 | 影响数据、消息、审批和迁移，当前没有证据证明这是必要代价，不建议纳入本轮 |

推荐按 B 设计，先落实其中的 A，再整合入口。沿用 Jinja、原生表单、共享 CSS/JS 和现有服务，不为侧边面板引入 SPA、图表库或通用工作流引擎。

## 5. 推荐界面及操作设计

### 5.1 管家首页：今天先做什么

日常工作主入口称“工作台”，默认进入“今天”。顶部提供今天/房间/全部任务三个视图；房源资料、客户、内容和系统设置保留在相应管理入口。预订审批和投诉保留独立业务页面与权限，工作台只汇总当前待处理入口。

下图是**信息结构示意，数字和房号为虚构示例**，不是已实现界面，也不是生产统计：

```text
工作台     [今天] [房间] [全部任务]              日期：今天

需要现在处理 3    今天入住 4    今天退房 2

先处理
101  今日入住前保洁未完成  · 尚未分派        [分派保洁]
203  入住凭证发送失败      · 需要管家核实    [查看并跟进]
无房间  补给需求信息不全   · 缺房间          [补全并分派]

今日安排                                      [查看全部]
102  保洁                 · 小王进行中      [查看进度]
105  退房检查             · 等待开始        [查看任务]

今天已完成 8 项                              [展开记录]
```

首页不要把每一种数据库状态都变成一级入口。它只回答：为什么现在处理、哪间房/哪件事、谁负责、下一步是什么。

“先处理”包括仍有价值的逾期工作、当天入住被阻塞、发送失败待人工核实、待审批的高风险事项；未来任务不会仅因为还没完成就挤在最前。没有房间或日期的事项进入“待补全”，不能被房间聚合丢掉。来源过期显示“房态待核对”，不可用空置或绿色可用掩盖不确定性。

### 5.2 聚合展示，不合并业务记录

房间按一次运营周期组织上下文，至少区分房间、服务日期和相关订单；不能将同房间历史订单与新订单的工作混在一张待办里。

同一事件同时存在提醒与人工联系任务时，只有经过明确关联才能计为一件需要处理的事；否则宁可标为可能相关，不按文本相似自动去重。展示分组可展开全部来源，底层订单、提醒、任务和凭证状态仍分别保存。

完成一个任务不能自动了结同组提醒，标记提醒“已处理”也不能被展示为客人已收到凭证。工作台计数和点击后的列表必须使用同一套口径，注明单位为事件、任务还是房间。

### 5.3 把“下一步”变成准确动作

| 场景 | 主动作 | 去向及约束 |
| --- | --- | --- |
| 待确认且信息缺失 | 补全并分派 | 打开该任务，说明缺房间、日期或执行人 |
| 信息完整的待分派任务 | 分派 | 原位选员工；原生详情页作为无脚本回退 |
| 同房间多条逾期任务 | 查看这 2 项逾期 | 带房间和逾期条件进入列表，不展示该房间所有历史任务 |
| 正在执行 | 查看进度 | 展示负责员工、最新处理状态和阻塞原因 |
| 证据缺失的待检查任务 | 补充检查材料 | 到对应执行区域，明确缺什么 |
| 凭证失败或发送结果未知 | 查看并跟进 | 展示失败原因及已成功部件；不自动重发 |
| 来源过期 | 核对房态来源 | 到现有可核查入口；没有可靠入口时明确说明，不渲染空按钮 |

每行只突出一个主动作；取消、人工改房态、归档等放入“更多”。“人工调整”仍解释其与证据流程的区别，不能只是换个好听名字隐藏风险。

### 5.4 全部任务：按工作需要查看，而非背状态名

管理员默认展示可执行待办。保留全部任务检索能力，以“需我处理、执行中、历史记录”为主要工作视角；“逾期”作为风险条件，不与“已归档”等不同维度混成互斥业务状态。

具体映射：待确认和待分派可进入“需我处理”；已分派/进行中属于执行跟踪；待检查是否需要管理员介入取决于现有权限和执行人，不能一律说“待老板验收”。已完成、已取消、已失效保留真实原因，不能全部改成“已完成”。这些是展示分组，第一阶段不迁移数据库枚举。

列表保留房间、工作摘要、时间、负责人和当前动作。房间、日期和负责人是常用筛选，其余收在高级筛选；已生效的条件以标签显示，用户自己决定是否展开完整表单。处理后保留上下文，不要求再次选择房间。

### 5.5 批量操作：选择之后再出现，执行之前说清范围

- 管家勾选后显示“已选 N 项”，只展示与所选集合有关的动作。空选不展示可提交按钮。
- 混合选择时明确原因和受影响条目；默认保持整批拒绝的现有语义。若用户想只处理合格项，先显式调整选择，再提交。
- 分派确认写明员工及数量；不再弹归档文案。提交后显示成功数量，失败时尽量保留安全的勾选和输入。
- 手机使用可见的选择模式、本页全选及底部操作栏；桌面可保留表格。镜像复选框继续以唯一任务 ID 同步，不能回归为隐藏副本也参与提交。
- 日常工作台不常驻“永久删除”；到历史/归档记录中明确选择后才能执行。用户不需要靠归档或取消任务来让工作台看起来整洁。

### 5.6 员工手机：围绕一件工作的完成路径

员工默认只看自己的待开始、进行中和待收尾工作，不向其展示不能操作的管理员调度队列。保留现场会用到的知识库入口，不扩张客户、金额或其他房间凭证访问权限。

推荐执行页顺序：工作摘要 → 当前进度 → 检查与照片 → 一个当前主动作 → 其他操作。将“清单 3/3、照片 1 张、缺失条件”放在同一区域；上传结果、保存状态和错误明确可见。

第一阶段只统一布局、提示和主动作，不改变提交语义。后续若合并清单/照片/提交检查，服务端必须处理文件落盘与事务失败，失败时不推进状态，已填内容和可复用照片不得无故丢失。

对于保洁，是否提供“完成保洁并确认可入住”仍待确认；对于维修、补给等任务，不得套用保洁房态动作。任何合并都必须保留执行人、任务状态、清单、照片和凭证安全门，明确实际是否会触发凭证评估。

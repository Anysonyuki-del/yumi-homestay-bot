# YuMi 部署后前端可用性审查与修复交接

审查日期：2026-09-08。目标：老板／管家日常调度优先，兼顾员工手机操作。本报告独立可读，可直接交给 Claude 分析和规划修复。

## 1. 结论与证据边界

主要页面能够打开，任务筛选、手机导航、任务勾选、运营时间切换、折叠总览和审计分页的本轮操作正常。仍发现 **11 项可用性问题：1 项 P1、9 项 P2、1 项 P3**。主要影响在于错误恢复、动作目标、提交后的返回上下文和诊断建议可执行性。现有证据不支持“所有按钮已经端到端验收通过”。

- 初始生产检查为 v1.14.1，本地基线 `cd2514b`；中断期间部署更新，续查生产侧栏显示 **v1.15.1**，当时本地 HEAD 为 **`ec7ca36`**。收尾检查时 HEAD 已推进到 **`c153d04`**，差异仅为 `tasks/todo.md`，无业务代码变化；因此上述代码与测试证据仍适用，未重复运行无关测试。
- 第一轮检查了 24 个页面／标签页变体。续查复核了新诊断文案、零任务房间入口、任务筛选、移动端和分页，并检查两版代码差异。第一轮证据不会自动升级为新版本每条生产路径已重测。
- 生产证据来自已登录的 `https://akros.icu` Chrome 页面；没有读取服务器源码、容器或数据库版本。因此“页面版本与本地版本对应”不等于已证明生产构建逐字一致。
- 仅执行页面导航、GET 筛选、展开／收起、勾选后取消等操作；没有提交生产业务表单、调用真实模型／Hostex／企业微信、修改订单或发送消息。审批详情 GET 本身会调用 Hostex，亦未执行。
- 写操作依据当前源码、现有隔离测试和本地替身复现；生产空数据、员工角色及条件按钮明确保留验收缺口。
- 本轮只新增本报告与本地证据文件，没有修改业务代码，没有提交、推送或部署。

证据标记：**P** = 生产现场观察／操作；**L** = 本地隔离验证；**S** = 源码追踪；**U** = 未执行真实提交或缺少现场条件。P1 表示关键日常操作受阻或无法恢复，P2 表示明显增加误操作／重复操作成本，P3 表示低频边界不一致。这是可用性优先级，不是安全漏洞等级。

## 2. 问题与最小修复方案

所有源码路径均相对于仓库根目录 `/Volumes/02/obsidian codex/homestay-bot`。下列行号以 `ec7ca36` 为准，实施时按符号重新定位。

### UX-01 · P1 · 标记可入住失败后，员工看到通用 JSON，无法按页面提示恢复

**证据：L + S；生产提交 U。** `src/homestay_bot/templates/tasks/detail.html:61` 在待检查阶段显示“确认房间可入住”，即使页面上已有缺少证据提示。`src/homestay_bot/services/room_readiness_service.py::ReadinessRuleError` 继承 `ValueError`；`src/homestay_bot/routes/tasks.py::mark_room_ready` 经 `_raise_page_error` 进入 `src/homestay_bot/routes/page_errors.py::raise_page_error` 的通用 409 分支。

本地以真实领域错误类型模拟“至少需要一张有效现场照片”，带 `Accept: text/html` 提交 `/employee/tasks/1/ready`，得到 `409 application/json`，正文只有 `{"detail":"任务操作未完成"}`。此复现验证错误映射，未验证真实照片存储或生产可入住操作。

**影响：** 手机员工离开任务页面，看不到需要补齐哪项材料，也没有页面内返回入口。

**修复：** 复用现有 `OperationRefused` 和 HTML 回跳机制，将可预期的证据不足映射为允许展示的具体原因；保持服务端独立复核。缺证据时阻止无效主动作，提供“补齐检查清单／上传照片”的定位入口。不要把任意异常原文直接展示给用户。

**验收：** 缺照片、缺清单、状态已变化均留在任务上下文并给出可执行提示；证据完整且有权限才允许可入住；JSON 客户端保留明确错误响应。重点文件：上述四处，以及 `tests/integration/test_task_routes.py`。

### UX-02 · P2 · 详情页提交后丢失原任务筛选与页码

**证据：L + S；生产提交 U。** 详情 GET 支持 `return_to`，但 `src/homestay_bot/templates/tasks/detail.html` 的操作表单未透传；`src/homestay_bot/routes/tasks.py::assign_task` 成功固定跳 `/employee/tasks/{id}`。检查清单、照片、可入住等同类重定向也需一起核对。

本地从带房间、状态、页码的列表进入详情，提交分派前“返回任务列表”保留来源；提交 303 后，该链接变成裸 `/employee/tasks`。证据脚本使用合成任务 ID，与生产记录无关。

**影响：** 管家逐条分派或核验时，每处理一条就要重新找房间、状态和页码。

**修复：** 在详情 GET → 所有相关 POST → 详情 GET → 返回列表全程保留经 `safe_return_path` 校验的来源；归档、删除等离开详情的动作也应回到来源列表。不要依赖 Referer，不要放开跨站回跳。

**验收：** 分派、清单、照片、状态更新成功／拒绝后保留房间、状态、日期、页码；恶意外部 `return_to` 回落安全默认。测试应走 POST 回环，不能只测详情 GET。

### UX-03 · P2 · 部分房间“去处理”进入零任务列表

**证据：P（v1.15.1）+ S。** 本轮看到部分风险房间显示“优先完成房间准备并接待入住”，开放任务为 0 项；点击其“去处理”实际进入按该房间筛选的任务页，显示“当前没有符合筛选条件的任务”。其他有任务的房间不受这一结论覆盖。

`src/homestay_bot/services/admin_operations_service.py::AdminOperationsService._next_step:514` 对今日到店、离店、下次到店等分支直接返回任务列表 URL，没有确认任务数量。

**影响：** 文案要求立即行动，目标页却没有可操作对象，管家仍需自行寻找房间资料或判断是否缺任务。

**修复：** 有开放任务时进入任务列表；无任务时进入现有房间运营详情，并将按钮改为“查看房间准备情况”。如果业务上本应存在任务，显示“尚未生成相关任务”，另查任务生成链，不通过点击自动补造生产任务。

**验收：** 覆盖到店／离店／未来到店 × 有任务／无任务，按钮文案和目标一致，零任务不再出现无解释的处理死路。

### UX-04 · P2 · 在运营页修改房间状态后跳离当前调度视图

**证据：S；生产提交 U。** `src/homestay_bot/templates/admin/operations.html:36,49` 的状态表单没有来源；`src/homestay_bot/routes/properties.py::set_room_operational_status:241` 成功固定跳到房间详情。

**影响：** 正在跨房间调度的老板／管家，更新一间后丢失运营页及 3／7／14 天范围，需要多次返回。

**修复：** 两种来源共用同一安全回跳规则：运营页提交回原 `days` 范围与房间锚点，房间详情提交回详情；显示状态已更新。保留现有状态权限与审计。

**验收：** 从 3／7／14 天运营页及房间详情提交，分别回到原场景；拒绝时同样能够继续操作。

### UX-05 · P2 · 客户默认详情仍展开全部管理区，保存后又回到这个长页面

**证据：P（初轮）+ S（现版）。** 无 `tab` 的客户详情显示基础资料、标签、备注、AI 摘要、结构化记忆和合并区；显式 `tab=overview` 才只显示概览。`src/homestay_bot/templates/customers/index.html:16,18` 的入口未带 tab；`src/homestay_bot/routes/customers.py::customer_detail:371` 设置 `legacy_full = tab is None`；模板用它展开多个标签页内容。

`src/homestay_bot/routes/customers.py::_customer_redirect:399` 统一返回无 tab 的详情，使保存后的用户再次进入长页面。

**影响：** 标签页虽然存在，日常入口和写操作仍落到旧的复杂界面，手机上尤其需要反复滚动寻找位置。

**修复：** 无 tab 统一视为 overview，保留旧 URL 可访问；写操作回到对应标签页与区块，例如记忆审核回 memory，合并建议回 governance。复用现有五个标签页，不新增页面层级。

**验收：** 列表进入默认只展示概览；五个标签页各自内容正确；保存、删除、审核后留在相关标签页；相关任务／投诉链接仍可用。

### UX-06 · P2 · 账号安全页缺少返回后台入口，修改密码后缺少成功确认

**证据：P（无返回链接）+ S（成功反馈）；生产安全操作 U。** `src/homestay_bot/templates/account/detail.html:1` 使用 `layouts/auth.html`，现场页面没有链接或后台导航。`src/homestay_bot/routes/employee_auth.py::employee_change_password:570` 成功后跳回 `/employee/account`，`employee_account:559` 未传成功提示。

**影响：** 用户只能依赖浏览器后退回工作台；修改密码后看到相同空表单，难以判断是否成功。

**修复：** 在正常已登录状态提供明确“返回工作台”，为成功改密提供一次性通知；强制改密状态仍遵守现有访问门禁，不借此绕过安全步骤。

**验收：** 正常账号页有返回路径，改密成功有明确反馈；错误密码仍留在表单且不泄露信息；必须改密的账号不能跳过要求。

### UX-07 · P2 · 诊断建议“清空回调密钥”，设置页实际上只能保留旧值

**证据：P（v1.15.1）+ L + S。** 诊断“百居易回调接收”提示：确定不使用回调时可以清空本系统回调密钥。`src/homestay_bot/routes/admin.py::_CHECK_GUIDANCE:114` 对应此文案。

但 `src/homestay_bot/templates/admin/settings.html:18,33` 明示密钥留空保留原值；`src/homestay_bot/routes/runtime_config.py::activate_settings` 没有清空 Hostex 回调密钥的操作；`src/homestay_bot/services/runtime_config_service.py::UpdateRuntimeConfig.normalized_updates:61` 会忽略空字符串。现有清空复选框只面向 `wecom_contact_secret`。本地输入空回调密钥得到更新集合 `{}`。

**影响：** 操作者按指引填写空值保存，仍无法关闭回调配置，还可能无谓触发整套配置校验。

**修复：** 最小方案是把指引改为当前真正可执行的检查步骤，移除“在设置页留空即可清除”的暗示。若确实需要后台关闭回调，则另行确认这一配置行为后，复用现有显式清空模式添加专用操作和风险说明；不能改变全部空密钥的“保留旧值”语义。

**验收：** 每条诊断指引均能在目标页面完成；留空继续保留旧密钥。若新增显式关闭功能，单独验证配置版本、回滚与关闭后的诊断语义。没有检查真实 Hostex 控制台，本报告不据此判断回调未接收的真实原因。

### UX-08 · P2 · 同步异常指向审计页，但该页不展示外部调用结果

**证据：S；该异常卡现场未出现。** `src/homestay_bot/routes/admin.py::_CHECK_GUIDANCE:125` 的 `hostex_reconcile/stale` 建议到审计记录查看最近调用结果；`src/homestay_bot/repositories/admin_diagnostics.py::SQLAlchemyAdminDiagnosticsRepository.list_audits:126` 只读取 `AuditLog` 的动作、对象类型、时间等字段，不读取新增的外部请求记录或请求结果。

**影响：** 真正同步异常时，用户进入一个无法支持诊断建议的页面；“有审计记录”会被误当作“有接口结果”。

**修复：** 先纠正文案，指向诊断页已有的状态证据；如必须让运营查看外部调用结果，再单独增加脱敏结果展示。不要把原始请求、密钥或客户正文直接搬进审计页。

**验收：** 用本地 stale 状态渲染此卡，逐条检查目标页确实包含文案承诺的信息；正常状态不出现不必要告警。

### UX-09 · P2 · 审批查看和拒绝入口依赖 Hostex 参考数据全部成功

**证据：S；生产审批详情与提交 U。** `src/homestay_bot/services/approval_page_service.py::ApprovalPageService.get_detail:72` 读到本地审批后，无条件顺序请求房源、参考价、收入方式，成功后才返回页面数据。`src/homestay_bot/routes/approvals.py::approval_detail` 在渲染本地审批及拒绝表单前等待它完成。未见失败降级，也未按已结束审批跳过参考数据。

**影响：** 上游不可用时，用户连已有审批基本信息和本地拒绝入口都看不到；查看历史审批也承担无关的外部依赖。

**修复：** 本地审批先保证可见，外部数据失败展示明确状态；只禁用依赖实时数据的确认下单。拒绝仍按本地状态与权限执行。已结束审批不加载下单参考数据。不能用旧房态／旧价格兜底允许下单。

**验收：** 在本地分别模拟三个参考接口超时／失败：仍能查看和合法拒绝，确认下单不可用；正常参考数据下确认路径继续经过原有确定性门禁。真实下单验收需另外授权。

### UX-10 · P2 · 知识条目操作后丢失筛选与两个列表的页码

**证据：S；生产条目／候选操作 U。** `src/homestay_bot/routes/knowledge.py` 列表支持 query、enabled、category、page、candidate_page，但 `convert_candidate:540`、`snooze_candidate:572`、`update_knowledge:587` 均返回裸列表，`toggle_knowledge:619` 只带条目区锚点；相应表单未保留来源。

**影响：** 批量整理知识时，每操作一条又回第一页，候选与条目两个区域的位置都可能丢失。

**修复：** 复用安全来源回跳，保留两组页码和筛选参数；目标已移出当前筛选时显示“已处理，当前条件下不再显示”，不要强行把记录重新塞回结果。

**验收：** 从非第一页、停用筛选和分类搜索执行启停／保存／收录／暂缓，回到原视图；处理最后一条时页码能够合理回退。

### UX-11 · P3 · 入住密码长度限制前后不一致

**证据：S；生产凭证提交 U。** `src/homestay_bot/templates/properties/detail.html:41` 与 `src/homestay_bot/routes/properties.py::replace_property_credentials:214` 允许最多 256 字符；`src/homestay_bot/services/property_admin_service.py::PropertyAdminService.replace_credentials:343` 限制 128。

**影响：** 129–256 字符的输入能通过浏览器与表单解析，却被服务层拒绝，用户先准备完整指南、二维码后才发现失败。常见短门锁密码不受影响，因此优先级低。

**修复：** 按现有服务约束统一为 128，表单内显示字段级错误；保留凭证加密、完整上传与版本替换规则。

**验收：** 128 字符符合其余条件可提交，129 字符在页面及时提示，绕过页面仍被服务端拒绝；全程使用合成凭证与本地文件。

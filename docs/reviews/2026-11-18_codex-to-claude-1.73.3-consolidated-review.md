## 2. 客人图片、worker 与员工通知

### I1 · P1 · 失败事件先到时，游标推进后仍可能把图片记为已受理

**复现与后果。** 模拟平台已经接到图片 POST，并在发送方提交机器人消息之前，从另一事务投递相同 `msgid` 的 `msg_send_fail`。仓储查不到本地消息，失败标记与员工通知均未登记；同步页处理返回，游标已推进。发送事务随后写入 `accepted`。实测最终为 **accepted、员工通知 0**。当前单进程已有独立轮询协程，触发条件不要求第二个部署实例。此问题在本版之前已有。现有图片异步失败测试只覆盖先记录消息再收到失败事件。[消息匹配：SQLAlchemyMessageRepository.mark_delivery_failed](../../src/homestay_bot/repositories/conversations.py) · [失败补偿与通知](../../src/homestay_bot/application.py) · [游标：WeComSyncJobHandler.sync_from_saved_cursor](../../src/homestay_bot/worker.py)

**修复建议。** 先查现有事件表或持久作业是否能保存尚未匹配的回执。游标推进前，必须已有可恢复的处理结果或待匹配记录。按平台消息标识和必要的客服账号作用域去重，只存关联所需字段。消息入库后重关联；要覆盖两个事务相互尚不可见的窗口，允许提交后有界补处理。给始终匹配不到的回执定义保留期和可观察的终态，避免一条回执卡住整个账号游标。复用现有文字与图片各自的失败策略，禁止把图片占位文本发给客人。涉及持久化结构时先确认 Spec、迁移和回滚。

**关闭判据。** 在 SQLite 与隔离 PostgreSQL 验证“回执先到、消息先到、两个提交交错、重复回执、持久化失败后重读原页”。同一图片最终为失败，员工补偿只登记一次，客人侧不重发；未匹配事件可查且有界，相邻正常消息继续处理。

### I2 · P2 · 上传期间员工已发言，当前图仍可能打断人工

**复现与后果。** `_build_guest_image_handler` 在上传前调用 `_guest_reply_is_stale`。在模拟上传期间，从独立事务提交同一会话的员工发言，上传返回后当前图片 POST 仍执行一次，只有下一张图被拦截。既有“发送前过时检查”测试没有覆盖上传这段等待时间；这是旧链路的窗口。[图片处理与过时判定](../../src/homestay_bot/application.py) · [既有图片行为用例](../../tests/integration/test_reply_images.py)

**修复与验收。** 在拿到素材编号后、调用 `send_image` 前，以能读到最新已提交状态的短查询复用原判定。已接管、员工已发言或已清空来源时停止当前图片和续链；保持新客人追问与原豁免规则。用上传钩子制造上述提交顺序，断言客人图片 POST 为零，并加正常对照。最后一次读与远程 POST 之间仍有时间窗，不能承诺两者原子。

## 4. 轮换、回滚与生产验收

### O1 · P1（下次轮换前）· 现有材料不能支持“任何一步失败都会自动回滚”

**依据。** [发布记录第 97–112 行](../releases/1.73.3.md)描述了后台脚本、成功探测和备份，脚本未入库，本次未触发回滚。Bash 合成实验中，条件函数、命令替换及未开启 pipefail 的管道均能掩盖失败；显式退出和默认信号终止可绕过 ERR。开启 ERR 继承也可能让父、子进程各触发一次。`set +e` 能让补偿继续执行，也能让某一步失败后仍打印“完成”。这些实验说明语言边界，不能据此断言当时的脚本用了某个有问题的结构。[Bash 对 errexit 与 errtrace 的说明](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html)

**建议 Claude 一起审查这四个切点：**

1. **停机前后。** 一次查询 RUNNING 为零到 API 停止之间，worker 仍可领取新任务；关闭流程会取消后台任务。停消费者后、修改凭据前再核对在途任务，发现新在途时先按既有恢复策略处理。[worker 领取与 shutdown_runtime](../../src/homestay_bot/application.py)
2. **中途失败与补偿自身。** 保留可审查的脱敏脚本或确切版本；关键命令显式检查返回值，由一个进程负责补偿，保留原始非零退出状态，记录哪个步骤已完成。分别验证数据库角色、环境文件两项配置和用该环境启动的 API 能以新连接读库。补偿失败应给出具体未恢复项；进程被杀或主机重启时要有手动续接办法。
3. **归档与真正恢复。** 记录中部署备份为 447 个对象、1,007,518 字节；轮换备份为 447 个对象、1,007,871 字节。两次均有可读性记录。隔离 PostgreSQL 16.15 实验中，从合成 custom dump 末尾截去 256 字节，列目录仍返回 0，实际还原到空库返回 1。请补上当时复验究竟执行了什么；若需声称“可恢复”，在隔离库实际还原，校验代表表、行数或业务约束。数据库 dump、角色凭据和环境文件分别验收。[PostgreSQL 16 恢复工具](https://www.postgresql.org/docs/16/app-pgrestore.html)
4. **代码回滚与凭据回滚。** 回退 API 版本时优先沿用当前有效凭据。恢复旧校验值会重新启用 Git 历史中已公开的密码，只能作为有时限的应急处置，并安排再次轮换。旧数据库密码失效只证明该密码无法认证；旧环境备份仍应按敏感材料管理，避免把整份文件标作“已失效”，按既有授权保留或另行清理。

**关闭判据。** 用合成凭据在隔离部署逐点注入“改角色后、替换环境后、认证探测失败、API 重建失败、补偿自身失败”。每次记录最终使用哪组凭据、API 能否建立新连接、退出状态；对中断可人工续接。在此之前，给正式记录追加带日期更正为“设计了自动回滚，本次未触发，失败路径待演练”。现有成功轮换结果继续保留。

### O2 · P2 · 统一 API 重建命令、健康判据和维护窗口

- **容器操作。** README 的“再启动 API”有歧义。`restart` 不刷新容器环境；普通 `up` 若将配置已变的 PostgreSQL 纳入调和，可能重建容器。同份 Compose 配置用两组**合成**密码实测数据库服务哈希不同。推荐常规 API 更新明确写 `docker compose up -d --no-deps api`；如认证探测采用一次性 Compose 容器，也核对是否会带起依赖。保持当前数据库容器，待独立维护窗口再考虑收敛哈希，先核对原项目和命名卷、可恢复备份、停写和 TCP 新连接。不要为证明重建行为在生产做实验。[README](../../README.md) · [部署手册](../../YuMi民宿AI开发经验与防回归手册.md) · [Compose up](https://docs.docker.com/reference/cli/docker/compose/up/) · [Compose restart](https://docs.docker.com/reference/cli/docker/compose/restart/)

- **关闭判据。** README 与手册对仅替换 API 的命令一致；在隔离环境验证 API 使用新环境，数据库容器身份及命名卷不变。将“部署完成”“健康分项通过或接受例外”“已登录后台”“worker 真实处理”“客人收件”分别记账。优先观察自然发生的已授权业务；需要主动发测试消息时另取授权。当前仍缺登录后诊断、轮换后的真实外发与收件证据。

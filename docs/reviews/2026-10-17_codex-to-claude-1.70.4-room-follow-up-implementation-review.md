## 2. P2：原文相邻被错误简化为“计划项相邻”

**编号：R174-1；反例 E174-1。**

输入：`401早餐几点，停车怎么收费，302呢`。规划只覆盖第一句和最后一句，未摘录中间的停车问题；该计划仍是合法计划。

实际回复：

```text
401早餐8:00开始。
302早餐9:00开始。
```

没有缺口。最后的 302 跨过停车话题，错误借用了更早的早餐话题。

**代码依据：** `src/homestay_bot/integrations/deepseek_client.py::DeepSeekGuestAssistant._bind_units`（约 2306–2344 行）只把计划项覆盖的小句放进 `owners`；`adjacent` 只判断两个已规划区间之间没有换行，不检查其中是否还有原文小句。未被模型覆盖的中间原文因此完全消失。

**合同依据：** Spec §2.2、§3.1 明确只看原文紧挨着的前一个单元；并专门规定这句话应承接停车，不能回找早餐。计划合法不等于全文覆盖完整。

**建议修复：** 以冻结全文的真实小句区间建立相邻关系，再把计划归属映射进去。未覆盖或无法证明职责的小句必须占位并阻断，不能在计划列表里向前跳。若停车小句没有可信语义，可保守 D；不要为此扩大规划器或新增话题词表。

**必要验收：** 相同原文分别用整句项、完整拆项、漏掉中间项、调换项数组顺序及换行输入；漏项时不能产生 302 早餐答案，完整拆项时可按停车独立取证。正常和协议回退的邻接判断必须一致。

## 3. P2：最终单元职责仍受原始类型和旧工具交接先后影响

**编号：R174-2；反例 E174-2a、E174-2b。** 这是一个共享职责问题的两个方向，不建议分开打补丁。

### 3.1 工具父句后，子项标成 static_fact 就把 B 改成 D

输入：`明天401还有房吗，302呢`，第一项为 `stay_query`，第二项为 `static_fact`。工具实际返回 401、302、501 的同日期房态。

实际只展示 401 可订，302 被记为 `scope_unbound`。此结果复现作者披露的 I174-6。

**代码依据：** `deepseek_client.py::_bind_units`（约 2341–2348 行）在父职责为 tool 的分支额外要求 `item.kind != "static_fact"`；子项类型因此推翻原文已经证明的工具承接。`_tool_coverage` 与 `_plan_tool_names` 仍依赖原计划项职责，不能仅删一处条件便认定全链修复。

**合同依据：** Spec 开头、§2.0、§2.2、§2.6 要求按原文父单元分 B/C/D，且覆盖三种规划类型。I174-6 属于改变已写明行为的偏差，不能以沿用旧版为理由自动接受。

### 3.2 静态追问被它后面的工具小句抢走

输入：`401早餐几点，302呢，明天501还有房吗`，一个 `stay_query` 整句项。实际回复包含 401 早餐，以及 401、302、501 全部可订；**没有 302 早餐，也没有漏答提示**。

**代码依据：** `deepseek_client.py::_clause_rooms`（约 2490–2517 行）先把无剩余内容的 302 片段并入后面的 501 工具问法，标 `delegated=True`；之后 `_bind_units` 的追问入口又排除 delegated，故不再看左侧早餐父句。原文同一段“302呢”同时受两套职责算法竞争，旧算法先执行便改变答案。

**建议修复：** 在一个共享布局中先确定原文省略承接职责，再运行兼容的工具枚举交接。明确 B 的工具职责与 C/D 的静态或失败职责，后续检索、工具开放、覆盖、结果组合均消费最终职责；不要在消费者中重新从 `item.kind` 猜一次。保留 `明天302，401还有房吗` 等真正工具枚举的同日证明及未知房源保护，不可简单停用旧交接。

**必要验收：** 上述两个反例跨三种规划类型、整句/拆项、正常/回退出口；再对照既有 R172 的真正枚举、日期不同、工具缺一房和空结果。C 后接工具句仍回答 C 自己的静态问题；B 不因子项标签改变为 D。

## 4. P2：只出现 own 单元时，工具结果仍包含静态房间

**编号：R174-3；反例 E174-3。**

输入：`明天501还有房吗，401早餐几点，302早餐几点`，一个 `stay_query` 项，目标提示为 501。工具返回三个房间。

实际早餐各答正确，但房态列出 **401、302、501 全部可订**，没有缺口。实际需要查房的目标只有 501；另外两间只问早餐。

**代码依据：** `deepseek_client.py::_bind_units` 为另外两个静态小句建立 own 单元；`_tool_targets`（约 2252–2256 行）却只有发现 C 或 D 才重算，否则直接返回 `turn_rooms`。`_respond_with_plan` 用这个整轮目标构造工具分项，`_compose_items` 随后拼入结果，所以 own 的房号重新进入房态展示。

**合同依据：** D-T2、Spec §2.4、§2.7 要求静态单元按自身房间取证，并且工具分项只对应需要工具的单元。该要求不限于恰好出现“呢”的输入。

**建议修复：** `_tool_targets` 的判断依据改为所有最终单元职责，覆盖 own 和 elsewhere，而不是 C/D 开关。筛选必须保留“无需求 / 全店 / 点名”三态，不能用空集合代替无需求。既有实现只返回一个整轮目标，修复时一并检查不同工具事实类型及日期的组合，避免以某工具需要的房源为另一工具授权；本报告未将该额外组合风险算作已复现发现。

**必要验收：** 上例最终只展示 501 房态；全店房态加两房静态答案仍保留全店；点名工具返回别房时不扩大；不同工具类型、不同日期和协议回退的工具分项必须有对应需求。不能只验证内部 coverage 而漏看最终正文。

## 5. P2：总字符预算跳过候选，被误记为可转交的资料缺失

**编号：R174-4；反例 E174-5。**

真实 `KnowledgeService` + 内存仓储，输入 `401早餐几点，302呢，501呢`：

- 初始检索得到全店资料，问答合计 11661 字，符合初始 12000 字上限。
- 401、302、501 各有一条专属资料，问答各 2719 字，各自可放入单次 3000 字检索预算。
- 合并候选为全店、401、302；501 超过 18000 总预算被跳过，单元候选却被保存为 `[]`。
- 最终 401 和 302 原因是 `budget`，**501 原因却是 `knowledge_missing`**。
- 模拟模型选中 501 的合法单元编号后，真实 `_referral_candidates` 接受它；未创建真实记录或发卡。

**代码依据：** `deepseek_client.py::_merge_item_knowledge`（约 2156–2168 行）因合并字符预算拒绝候选，但仍建立空候选表项；`_unit_evidence`（约 2206–2230 行）只有“候选表项不存在”才判 budget，空列表进入普通静态缺失路径。`_referral_candidates`（约 3761 行）按最终 reason 过滤，所以被错误放行。

**合同依据：** Spec §2.4、§2.5 明确超预算不可转交。`knowledge_service.py::KnowledgeService.retrieve_detailed` 已把预算跳过与实际缺资料分开；新增单元路径没有完整保留这种区分。

**建议修复：** 在本次共享单元候选结果里保留预算失败原因；总信封容量跳过时必须得到 budget，不能与“检索成功但没有资料”的空池混为一谈。优先复用已有 `KnowledgeRetrieval.budget_skipped`，检查每次 3000 字预算和合并 18000 字预算两处。不要放大预算、截断知识或错误共享别房候选来消除反例。

**必要验收：** 保留本反例的真实检索服务和可计算长度，并加入单条超过 3000 字、总预算恰好边界、候选已在合并池、次数上限、真实空库对照。预算失败即使模型主动选编号也不可转交，真实缺资料仍可转交；检查最终保存记录时不只核候选列表。

## 6. P2：新增门禁未验证房号与答案对应，错误回复可稳定晋升

**编号：R174-5；反例 E174-6。**

`tests/fixtures/guest_reply_scenarios.json` 的 K-房号追问（约 5910 行）只要求包含 `8:15` 和 `9:45`，禁用两段连续字面文本。当前 `src/homestay_bot/tools/reply_regression.py::judge` 对以下两条都返回 `ok=true`：

```text
7701：早餐9:45开始。7702：早餐8:15开始。
早餐时间为8:15和9:45。
```

第一条把答案互换，只插入冒号便绕过禁止片段；第二条完全没有说明房号对应关系。重复三次也只会把错误结果重复三次。

**合同依据：** Spec §2.6 明确要求两组“房号＋对应答案”整句匹配、不得互换、两房都答到。现夹具 notes 写了目标，但可执行判据没有落实。`expect.source_ids` 也不被 `judge` 消费；离线预检正确样本的来源断言不能宣称为真实模型每次运行的来源核验。

**建议修复：** 优先复用既有 `must_not_match` 及周末场景的组合判据，落实房号与时间的对应关系及整组缺失检测；需要新增判据时只补必要的最小入口。为正确、互换、漏一房、只有钟点、夹带错误答案、来源不符各留一个有判别力的断言。明确来源断言属于离线取证验证还是运行门禁，不把声明字段当可执行校验。不要放宽 baseline 或仅加强 notes。

修复判据后才可在获授权时按“限定三次全过 → 晋升 → all”验收；目前 known_failures 只是暂存位置，不能作为该功能已达标的理由。

## 8. 建议整体修复顺序与防牵连检查

1. **一次冻结原文单元及最终职责。** 全文小句位置 → 唯一归属 → 原文父职责 → A/B/C/D/own/elsewhere。先处理省略承接，再保留真正的工具枚举交接。不要新增与原布局并行的意图系统。
2. **全部消费者读最终职责。** 检索、候选、缺口编号、工具开放、事实覆盖、房源/日期筛选和最终组合一起核对，避免只改 `_bind_units` 后其他出口仍按原类型走。
3. **预算状态保留到转交边界。** 次数和字符上限不变；有资料但受预算限制不能造成“去问管家补资料”的假任务。
4. **修复判据再验收。** 先跑本报告反例及直接相关旧回归，补上述真实检索/临时库边界。结果覆盖最终实现时复用，不机械重跑无关测试。公共回复流程改动在获真实模型授权后仍须 all；离线通过、模型门禁、生产部署和实际收件分别记录。

修复优先避免四类连带退化：真正工具枚举失效、全店查询被静态房号收窄、日期证明被改成无条件继承、候选隔离或不可转交原因被放宽。无需新增依赖、规划模型或扩大支持句式。

## 2. 对回应 §7 五个问题的结论

### 问题 1：是否足以证明 B 等 A？是否会误报？

**足以支持当前测试下的结论；不能脱离测试前提作通用证明。** 本轮亲自复跑当前两项测试，均通过；另在临时实例中给原并发测试增加只读观测，直接核对等待后端和阻塞后端，确认等待者是第二次身份 INSERT 的连接 B，`pg_blocking_pids(B)` 的结果恰好为 `[A]`。不是只重复作者关于“没有第三方”的推理。

当前结论成立的完整链条：

1. `tests/integration/test_retention_postgresql.py:99–127::pg_engine` 为每个用例清空业务表，当前工作流没有并行测试参数。本轮还使用全新一次性实例，排除了其他进程往同库写数据。
2. `tests/integration/test_miniprogram_auth_postgresql.py:30–37::_FixedExchanger.exchange_code` 给两个请求返回同一 OpenID。`src/homestay_bot/services/miniprogram_auth.py:131–154::MiniProgramAuthService.login` 将 AppID 与 OpenID 组合为同一身份键，两次登录各用独立会话与事务。
3. `tests/integration/test_miniprogram_auth_postgresql.py:74–89::create_holding_first、并发测试` 在 A 的原始会话写入已完成后暂停 A，且等待 `a_holding` 后才启动 B；A 此时已越过身份 INSERT，不会再成为正在执行身份 INSERT 的等待者。
4. `src/homestay_bot/repositories/customers.py:94–115::SQLAlchemyCustomerRepository.ensure_identity` 先查询，未找到才在保存点中创建新客户和身份。A 未提交，B 看不到其身份，因此也尝试插入同一 `(provider, external_id)`。该唯一约束见 `src/homestay_bot/domain/models.py:218–235::CustomerIdentity`、`migrations/versions/0003_customer_crm.py:102–130::upgrade`。
5. 在这个新库、两写入者、无额外触发器的流程里，B 的客户父行由 B 自己创建，主键由各自插入生成；A 没有删除或修改 B 的客户父行。结合当前语句与事务锁等待，排除了本轮控制实验中的外键等待解释。
6. 释放 A 后，原测试核对客户 1、身份 1、会话 2、token 不同且均可解析（`:93–102`）。结合 `ensure_identity` 的异常处理，支持唯一冲突后回滚保存点并回查复用的路径；测试没有独立记录 SAVEPOINT 回滚语句，不将结果描述为逐条 SQL 轨迹证明。

**辅助函数的真实上限及本人反例**：`tests/integration/test_miniprogram_auth_postgresql.py:40–60::_wait_for_identity_insert_lock` 统计的是同数据库中任意符合条件的后端，没有绑定 B 的 PID，也没有绑定 A 或具体约束。

本轮在同一个一次性实例内另做控制：先提交一个客户父行，事务 C 删除该父行但不提交；事务 D 插入一个全新的、没有重复键的客户身份，引用该父行。D 的外键检查等待 C，当前语句仍是 `INSERT INTO customer_identities`，等待事件同为 `Lock/transactionid`，辅助函数实际返回 **True**；`pg_blocking_pids(D)` 也指向 C。当时根本没有运行登录 A/B。C 回滚后 D 插入成功，最后将 D 回滚。

这证明两个边界：

- **仅凭该 SQL 不能认定唯一键冲突**：外键等待同样命中。
- **仅凭该 SQL 不能认定参与者是 A/B**：未来若共库并行或增加其他身份写入者，可能命中无关会话；`assert not login_b.done()` 只能补证 B 尚未完成，不能将那条等待记录绑定给 B。

上述反例改变了当前测试的“两写入者、各自创建父行”前提，**不是当前完整测试误过的复现，不构成本轮 P2，也不要求推翻 R4 或再改业务代码**。建议将结论写成“在当前隔离、串行且仅 A/B 写入的用例中，观测及调用链共同证明 B 等 A”。若未来并行执行、复用此辅助函数或增加写入流程，最小增强是记录 A/B 的数据库后端 PID，限定 `pid = B` 并检查 A 属于 `pg_blocking_pids(B)`；若还要证明具体约束，则另核对冲突键或异常约束名，不能只加一个锁类型条件。

**其他证据限制**：报告所述 schema 前缀、CTE 等 SQL 变化可能导致匹配失败的判断成立。3 秒轮询上限小于 5 秒数据库锁超时是正常环境下的失败定位安排，不是整个辅助函数必在 3 秒内返回的硬保证：连接获取、查询耗时或事件循环长时间停顿都不由这个 deadline 中断。当前三条并发连接未耗尽默认池，本轮及指定 CI 均未发生该问题，不据此要求新增超时框架。

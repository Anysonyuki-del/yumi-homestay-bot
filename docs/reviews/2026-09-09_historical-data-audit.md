## 唯一信号：5 条出站投递失败

`messages` 中 5 条 BOT 消息 `delivery_status="failed"`，错误码统一 `wecom_async_13`，各重试 1 次：

| 消息 id | 日期 |
| --- | --- |
| 49 | 2026-08-20 |
| 52 | 2026-08-21 |
| 53 | 2026-08-21（52 的重试）|
| 55 | 2026-08-21 |
| 105 | 2026-09-01 |

**系统对失败的处理是到位的**，不是静默丢弃：

- 触发了 `guest_delivery_rewrite` 重写作业（3 条 COMPLETED），部分用了 fallback。
- 2 条带失败通知标记。
- 会话本身已恢复：例如失败的 105 之后，同会话 106、108（9/1–9/2）投递状态均为 `accepted`。

这与项目铁律一致——「接口受理≠客户送达」，此处系统确实在失败后走了重试与人工通道，未把「已发送」当作「已送达」。

## 一处轻微簿记遗留（非功能故障）

3 条 BOT 消息的 `delivery_retry_pending` 仍为 `true` 且从未清除，尽管对应会话已收到后续 `accepted` 消息、实际已恢复。属陈旧标记，不影响送达，但会让「是否仍有待重试」在数据上显得不准。

**建议**：不需紧急处理。若后续要给运营看「待重试」看板，先补一个清理/收敛这批陈旧 `delivery_retry_pending` 的逻辑，避免长期挂着假阳性。本次盘点只读，未改动任何数据。

## 边界

- 全程只读，未写生产、未调外部接口、未读客户正文与手机号。
- 「基本干净」的相当部分原因是运营历史少（凭证投递、房间凭证、失败作业均为 0 行），不能据此推断功能在高数据量下同样无异常。凭证投递链路目前无生产数据可盘。

## 2. 需要修订的五项问题

### T-R1 · P2：日期不能证明住宿意图，D-T3 会留下带日期静态追问的原缺陷

**位置**：Spec §2.3 第三行及其后规则、D-T3（第 62–64、103 行）。

**反例与依据**：原文 `明天401早餐几点，302呢`，规划为一个 `stay_query`，目标 401，日期 `2026-10-08` 入住、`2026-10-09` 退房。这份计划能通过 `verify_turn_plan`。两个小句均无工具锚点，前句静态剩余是早餐问题，后句剩余为空。当前真实助手输出：

> 401早餐为8:00。
>
> 「302呢」这次没有查到对应的房态，暂时无法确认。

后句缺口为 `tool_uncovered`。v1 明确规定只要有规划日期就维持该行为，因此这个反例不会被新方案修复。日期在客人原话里有依据，并非依赖模型凭空填日期的极端构造。

源码依据：`deepseek_client.py::_fact_layout`、`_tool_coverage`；`turn_plan.py::verify_turn_plan` 只核计划形状、摘录、房号和日期合法性，不能把核验通过等同于 `kind` 的语义正确。

**建议**：修改 D-T3：日期是时间约束，不能单独成为住宿意图依据。对可证明的静态话题，仍在其小句上承接；真实住宿小句保持工具职责。也不能简单改成「只看工具锚点」后把没有锚点的真实订房请求一并降为静态，须与 T-R2 一起定义优先级。

**验收**：上述带日期静态问题覆盖 P2–P5、正常/协议回退；与 `明天401还有房吗，302呢`、`我想订302` 成对验证。静态追问应按对应日的 302 资料作答，实际住宿目标仍按工具和日期流程处理。

### T-R2 · P2：`residue == ""` 不是省略追问证明，会吞掉独立订房请求

**位置**：Spec §2.1（第 44–47 行）、§2.3 的住宿误标纠正。

**当前纯函数实测**：以下四个片段经过 `clause_needs`、`clause_dates`、`resolve_rooms` 后，结果完全相同：

| 片段 | residue | 工具锚点 | 房号 | 日期 |
| --- | --- | --- | --- | --- |
| 我想订302 | 空 | 无 | resolved | 无 |
| 我想住302 | 空 | 无 | resolved | 无 |
| 我要302 | 空 | 无 | resolved | 无 |
| 302呢 | 空 | 无 | resolved | 无 |

因此 `401早餐几点，我想订302` 等前三种独立请求，也满足 v1 的全部识别条件；若前句能答，按 v1 会被规范成 302 早餐问题，丢掉真实订房意图。

源码依据：`item_coverage.py::clause_residue`（509–541 行）刻意删除形式词、住宿动作和只剩订房意图的噪声；注释已说明这是为防止 AV-102「我想订102」误进静态取证。该函数表示「没有其他待答资料」，职责不是判断话题承接。

**建议**：把「确定存在省略承接关系」与「没有独立静态剩余」分开。仅明确的换房号省略问句进入承接，独立住宿请求、动作请求和新问题断开承接；无法证明时保守处理。无需撤回 AV-102 的现有修复，也不宜再靠不断追加订房动词排除表完成语义判别。Spec 应明确可支持的承接结构及歧义上限。

**验收**：四个片段分别接在早餐问题后，覆盖单住宿项、分项及已有 AV-102 正例。前三个不得变成早餐答案，`302呢` 能按确定话题作答；独立订房不能因为前面有静态问题而被吞掉。

### T-R3 · P2：只继承问法没有继承有效日期与条件，分项后会错日取证

**位置**：Spec §2.2 第 52–53 行、§2.3 第一行。

**按 v1 接口的实测投影**：正文为 `10月8日401早餐几点，302呢；10月10日401早餐几点，501呢`，构造四个合法静态项，并把两条追问的 `question` 分别补成对应房号的早餐问题。当前 `_fact_layout` 给出的 `item_dates` 为：

| 项原文 | 实际取证日期 |
| --- | --- |
| 10月8日401早餐几点 | 2026-10-08 |
| 302呢 | **2026-10-07** |
| 10月10日401早餐几点 | 2026-10-10 |
| 501呢 | **2026-10-07** |

这是「仅补问法」在现有消费接口中的结果，尚未声称 v1 的未来最终回复一定错日。其原因可以确定：`deepseek_client.py::_item_dates`（1986 行起）读取计划日期或 `quote`，不从 `question` 获取日期；无日期回落本轮默认范围。即使规范问法写入日期，也不等于检索参数已经修正。

另一个相同边界是知识条件：`_merge_item_knowledge`（2012 行起）显式传 `trigger_text=item.quote`、`exclude_text=question_text`；`knowledge_service.py::KnowledgeService.retrieve_detailed` 在评分前筛房源和有效期，并以二者判断附加条件与排除条件。因此只改问法还会遗漏父句中允许继承的条件；直接借父候选则会突破房源/条件隔离。

**建议**：在共享小句布局里冻结「有效问题＋追问房源＋已证明日期范围及来源＋允许继承的条件原文区间」。日期继承必须遵守现有范围内核验、无锚点序数日和无法绑定日期的阻断；不能扩大住宿区间，也不能从父答案或模型补写内容推定条件。排除词继续核本轮全文，附加条件只能来自本次问题的已绑定原文，不能借另一独立问题满足。

**验收**：两组不同日期在同一轮的对照、跨年、区间内外及序数日；子房源有不同日期政策；父句带附加条件、另一独立问题带条件、全文排除词。同时断言检索参数、合法候选、最终房源/日期/答案/来源对应关系，不能只断言正文出现某个钟点。

### T-R4 · P2：逐小句检索必须同时下沉合法候选和缺口身份，不能只扩大同项候选池

**位置**：Spec §2.3 第二行、§3.1 检索次数风险、§3.2 文件符号清单。

**源码依据**：当前 `_ItemLayout` 仅有项级 `property_id`，`_merge_item_knowledge` 返回按 `item.id` 索引的候选，`EvidenceSelection` 也按项选择；`_item_evidence_plan` 把同项候选传给小句。原有安全前提是「合法候选已由检索目标隔离」。`knowledge_evidence_policy.py::verify_selected_evidence` 核编号属于合法候选、有效期与对象冲突，不能凭问句中的房号再次证明目标房源。

**当前真实函数控制**：向 `_static_item_parts('302早餐几点', ...)` 传入混合的 401/302 早餐候选，并给出合法项级选择 `answer_ids=[401条目编号]`，函数返回 `grounded / 401早餐为8:00。`。这不证明当前生产混池，只证明未来若仅把多个房源候选并入原来的项级池，该调用边界不会替实现挡住错房答案。

此外，`_gap_unit_offers`（1601 行起）在静态项未拆分时仍提供整项编号；`_item_evidence_plan`、`_shared_grounded`、`_referral_candidates` 和最终 `ReplyPart.gap_unit` 消费这些身份。只修改取证小句，会重现调用前后编号不一致或错误开放转交的问题。`verify_turn_plan` 还允许重叠摘录：实测「整句 static_fact＋302呢 static_fact」为 `ok` 且两项均有效，不能假设每个原文单元只出现于一个计划项。

**建议**：复用并扩充现有小句布局，让每个最终单元绑定自己的房源、日期、查询、合法候选、原文区间和稳定缺口编号。项级选择应用到小句时，先按该单元合法候选重新约束；不得直接信任同项其他房源的选择。正常、回退、跨项有限复用、调用前编号、最终缺口及转交都读取同一布局。重叠项不能导致同一原文单元重复检索、重复答复或重复转交。

预算也应写入合同：当前 `_PLAN_RETRIEVAL_ITEMS=4`、`_PLAN_KNOWLEDGE_TOTAL_CHARS=18000`。从按项改成按小句后，要说明新增检索如何计入现有预算；不可把每项四次变成每小句四次。超限按实际预算原因关闭，不能伪装成普通资料缺失开放转交。

**验收**：同项双房相反答案、故意选错房源编号、正常/回退一致、重叠摘录、连续多房追问、超过检索和上下文预算；逐单元核来源，核调用前后相同编号，并验证被拒编号无法生成转交候选。

### T-R5 · P2：父句缺资料时是否继承、继承后是否转交，要求冲突且依赖阶段未明确

**位置**：Spec §2.2 第 54 行、§2.4、§2.5 第 77、79 行。

§2.2 只在「没能作答且缺口不是 knowledge_missing」时拒绝继承，意味着父句 `knowledge_missing` 可以继承；§2.5 却要求「前一句缺资料时追问不继承」。对于「401没有早餐资料、302有早餐资料」，两处要求会给出相反结果。

还有时序问题：`deepseek_client.py::_respond_with_plan` 先 `_fact_layout`、`_merge_item_knowledge`，再在主调用前生成 `_gap_unit_offers`；父句是否能答以及最终缺口原因，须到 `_item_evidence_plan` 核验证据后才知道。直接把最终父答复状态作为前置检索条件，会让实施在重复取证、动态改变编号、正常/回退差异之间被迫临时选择。

§2.4 对「继承不了」禁转交是清楚的，但第 79 行不加限定地禁止追问生成转交候选；对于「成功继承且子房源真实缺资料」究竟沿用既有 `knowledge_missing` 还是一律不可转交，没有唯一合同。当前 `_referral_candidates`（3420 行起）只接受本地确为 `knowledge_missing` 且模型选中的最终单元。

**建议**：优先采用「只继承问题，不继承父答案或候选」：话题能从原文确定时，子房源独立取证，父句缺资料不影响话题本身。这能避免把问题关系与答案状态绑在一起。若产品要求父句失败就阻断，须明确缺失、冲突、复核、期间否决、预算失败分别怎么处理，以及哪个阶段冻结结果，不由实现者临场决定。

新增一个明确决定：成功继承后子房源真实缺资料，是否允许按现有核实流程转交。无论选择哪种，无法继承、房号未绑定、日期未绑定及预算失败均不可借模型编号选择升级为可转交。

**验收**：父有/无答案与子有/无答案四格，另加父冲突/复核/期间否决/预算；对成功和失败继承分别注入模型主动选择缺口编号，验证最终候选及正常/回退一致性。上述选择应先在 Spec 唯一化，再写测试。

## 3. 同轮建议明确的两处范围

### C1 · P3：「同一句」与消息边界需要可执行定义

`item_coverage.py::split_clauses` 会按逗号、问号、分号及换行切句；新门禁本身是「401早餐几点开始？302呢」，不能把问号机械当作禁止继承边界。`message_service.py::MessageService.collect_guest_batch`（209 行）又用换行合并多条消息。适配器仅看合并正文，无法仅凭换行区分「同一条消息里的换行」与「两条消息的边界」。

建议 D-T1 明确当前保守范围：例如同轮冻结正文内、同一行相邻片段，换行断开；这会同时不支持单条消息跨行承接，应直说。若必须按真实消息边界区分，则需补上游边界数据和验证，不可仅声明“不跨消息”而没有可用信息。来源顺序按原文区间，不能按模型数组顺序；不得越过工具、动作或新话题去回找更早静态项。还应明确连续 `401早餐几点，302呢，501呢` 是否承接已经规范化的前单元。

### C2 · P3：新增门禁应核对象配对，而非只核两个数字出现

认可新增场景先限定三次全过、晋升再 all 的方案；公共回复变更的 all 要求与当前 AGENTS 一致。新增判据应同时约束房源与答案对应、两房均覆盖以及各自来源。401/302答案互换、只答一房、夹带错房答案的合成回复都应不能通过；已有日期来源要求继续保留。离线测试覆盖人为误标计划，真实门禁只证明实际规划产物下的表现，两类证据不可替代。

## 4. 推荐的整体修订方案

同意保持 `turn_plan` 的空问法回落逻辑，不新增模型调用。方案收敛到**扩充现有共享小句布局**，不要为 P2、P4、P5 各写一套检索或出口补丁：

1. 按原文相邻单元判断明确省略关系，先区分独立住宿/动作与可承接静态问题。
2. 冻结问题来源、规范问法、子房源、有效日期及原文条件；静态日期不充当住宿意图证明。
3. 按最终单元独立检索与隔离合法候选，统一消耗现有预算；模型选择始终受本地合法集合约束。
4. 调用前缺口选项、正常取证、协议回退、工具覆盖及最终转交共用同一单元身份和失败原因。

这不是要求新增通用框架或重写规划器。关键是把现有布局承担的信任边界补全一次，避免只改检索问法后再逐轮补日期、房源、缺口与回退。

建议 D-T1 明确消息/换行及相邻边界；D-T2 保留一起修 P4，但以单元候选隔离为前提；D-T3 改为片段语义与证据职责优先；新增父句失败及转交的决定。D-T4 的拟定版本号可保留，不构成实施或外部发布授权。

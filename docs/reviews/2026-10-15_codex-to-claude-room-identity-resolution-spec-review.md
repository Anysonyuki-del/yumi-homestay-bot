## 2. 逐项发现、建议与验收

### RI-R1 · P2：工具回复仍有独立的数字筛房路径

**Spec 位置：**§2.2 消费方清单、§3.2、R2/R3/R4。

**依据：**`src/homestay_bot/integrations/deepseek_client.py::DeepSeekGuestAssistant._tool_reply_parts`（基线约 2940 行）从 `property_title` 提取数字，并以数字是否出现在问题中筛选工具行；没有比较楼栋和解析后的房源编号。`_unmatched_room_header`（约 4160 行）还单独使用另一套数字正则。正常工具调用和房态回退路径均调用 `_tool_reply_parts`。

离线实测：给函数两条合成房态，1栋1803 可订、2栋1803 不可订；问题是“明天2栋1803还有房吗”。实际正文同时列出两栋，来源房源编号为 `[1, 2]`。

**影响：**即使新的 `clause_target` 能证明目标房源已覆盖，也不会删除工具分项中已经生成的其他楼栋。unknown 时原有“未匹配则列全部房间”的行为，也需要与 D-R3 的“不作答”边界对齐。

**最小修订：**将工具结果筛选和未匹配说明纳入共享解析结果。按工具行的 `property_id` 筛选，无须改变 Hostex 查询参数。区分未点名房间、resolved、unknown、ambiguous；未知房号不能被当成没有房号而列出全部房间。

**验收：**同号不同栋、当前会话属于另一栋、工具返回多个房源时，最终正文和证据只含客人明确指定的房源；正常与回退出口一致。unknown/ambiguous 行为符合确认后的政策。

### RI-R2 · P2：楼栋片段会残留为新的静态问题

**Spec 位置：**§2.1、§2.2、R1/R2。

**依据：**`src/homestay_bot/services/item_coverage.py::clause_residue`（约 346 行）只用 `_ROOM_NUMBER.sub` 删除数字，`clause_needs` 把剩余内容作为静态语义；`DeepSeekGuestAssistant._item_evidence_plan` 对有工具事实且存在剩余内容的小句继续静态取证。

离线实测：

| 问法 | 当前剩余内容 |
| --- | --- |
| 明天2303还有房吗 | 空 |
| 明天2栋2303还有房吗 | `2栋` |
| 明天2-2303还有房吗 | `2` |

**影响：**只修改房号提取和映射，带栋问法仍可能在房态答案后追加未确认段，重新出现本次 E2 要解决的症状。

**最小修订：**房号解析保留原文区间，`clause_residue` 删除完整房号片段。不要全局删除“栋”等单字，以免吞掉“几栋楼”“楼栋入口”等真实问题。

**验收：**四种房号写法取得工具证据后均无多余未确认；“2栋2303还有房吗，入口在哪”仍保留入口子问。

### RI-R3 · P2：规划提示与原文冲突、以及多房号的绑定合同不完整

**Spec 位置：**§2.2 第一条、`verify_turn_plan` 修订、R5/R7。

**依据：**`src/homestay_bot/services/turn_plan.py::verify_turn_plan` 当前只要求规划房号为数字且出现在全文。真实核验函数接受以下两种合成规划：

- 原文“2栋1803有浴缸吗”，规划只填 `1803`。
- 全文“302有浴缸吗，401停车收费吗”，第一项摘录为“302有浴缸吗”，却填 `401`。

拟议规则仍先解析规划值，再以当前房源消歧。第一种情况下，规划值丢失原文楼栋后可能先绑定到另一栋；小句守卫随后可能把它拦为未确认，修复目标仍未实现。不能把这个推演直接写成新方案已经错误放行。

多房号还有一个具体合同缺口：`split_clauses("302和401有浴缸吗")` 实际只得到一个小句。现有 `_ItemLayout.property_id` 和 `_merge_item_knowledge` 仍按单个计划项房源检索，R5 的“每个小句按自己的房号解析”没有规定该输入的最终行为。

**最小修订：**小句明确房号和楼栋优先，规划只能补充可证明的继承关系，不能覆盖明确原文。明确无本地房号时借用其他小句目标的条件。多房号可以选择保守不绑定，但须写清结果；若要求逐房作答，则必须同时设计逐房检索和证据绑定，不能只改比较函数。

**验收：**补原文带栋而规划为裸号、规划错填同轮另一房号、规划与原文一致、无房号小句合法继承，以及单小句多房号、不同小句多房号。最终行为和资料来源均有断言。

### RI-R4 · P2：标识数字撞上有效房号时，风险是错选房源

**Spec 位置：**§2.1、§2.2 补齐规则、§3.1 非房号数字风险。

**依据：**`item_coverage::clause_rooms` 当前把“订单尾号2303”提取为 `2303`。Spec 的新补齐合同对唯一且 resolved 的原文数字采用该房源，但风险段仅讨论 unknown。

**影响：**如果有效房源恰有 2303，该数字会 resolved，而非 unknown，可能改变后续问题的检索房源。这是拟议合同推演，不是新实现的最终回复实测。

**最小修订：**至少排除明确的订单号、订单尾号等标识语境；仍无法判断的情况不得依靠“恰好命中房源”证明它是房号。风险说明必须承认有效号码碰撞可能导致错配。

**验收：**同时覆盖标识数字未命中、恰好命中真实夹具房号、明确房号与标识数字并存；保留“2303有浴缸吗”这类裸号正常识别。

### RI-R5 · P2：标题兜底不具备“最多 unknown、不会错配”的保证

**Spec 位置：**§3.1 标题风险、D-R1。

**依据：**`src/homestay_bot/repositories/operations.py::SQLAlchemyOperationsRepository.sync_property_titles`（约 1884 行）按百居易标题覆盖本地标题；`src/homestay_bot/services/hostex_sync.py::HostexSyncService._sync_property_titles` 在对账后调用这条路径。`PropertyProfile.room_number` 独立存在，标题同步不更新它。

**影响：**标题可能从一个可解析号码改成另一个可解析号码；“只有一个号码”不能证明该号码是稳定房号。使用标题作身份来源会把已有显示字段变成匹配依据，风险不只是解析失败。

**最小修订：**删除“不会错配”的绝对保证。若保留标题兜底，明确依赖上游命名准确性、允许的格式和冲突处理；若要求稳定身份保证，使用管理员维护的 `room_number`，补数据的生产操作另行授权。诊断页新增提示若保留，也应补具体文件、符号与验收范围。

**验收：**标题无号码、多个号码、唯一号码、改名成另一可解析号码、与明确 room_number 冲突，以及两个房源同号；只认启用房源。验收结果必须反映最终确认的政策，而非继续承诺无法保证的安全性。

### RI-R6 · P2：新增场景的成功尚未明确成为修复完成条件

**Spec 位置：**§2.3、R10。

**依据：**Spec 先将两个新场景加入 known_failures，约定“三次全过后晋升”，但没有明确未达到三次通过就不得完成修复验收。`src/homestay_bot/tools/reply_regression.py::gate_verdict` 的不退步门禁与目标缺陷修复成功不是同一条件。

**最小修订：**明确新增两场景及本次起因 `K-周末分日` 的成功标准与发布边界；需要例外时显式记录用户决定。使用合成规划强制漏填，以确定性测试证明补齐分支；真实模型场景验证最终行为，不能仅凭场景名称证明实际发生过漏填。

**验收：**相关确定性回归通过；目标场景达到确认的稳定要求；all 无退步。三者分别记录，不互相替代。

### RI-R7 · P3：服务费误判的现状结论未被实际链路支持

**Spec 位置：**§1.3 服务收费行、R6。

**依据：**`src/homestay_bot/services/knowledge_evidence_policy.py::carry_followup_topic` 只有去除形式词后没有剩余才借话题。`DeepSeekGuestAssistant._respond_with_plan` 先要求补全后问题不同于原文且属于服务收费，才进入 `service_fee_followup` 分支。

离线实测，历史为 `Do you have parking?`：

| 本轮输入 | 补全结果 | service_fee_followup |
| --- | --- | --- |
| 302 how much | 原文 | false |
| 302多少钱 | 原文 | false |
| How much is it? | parking：How much is it? | true |
| 那多少钱 | parking：那多少钱 | true |

**最小修订：**删除“302 how much 已误当停车费”的已复现表述，或补充实际成立的输入、历史和规划证据。确需统一消费者时可以保留一致性改动，但应将其与缺陷修复区分。

**验收：**点名房间的问价走房价路径；纯服务费追问仍正确承接；不能通过放宽追问识别来制造原来并不成立的缺陷。

## 3. 建议下一版一次补齐的共同合同

将原文房号、规划提示、候选房源和最终消费结果的关系写在同一处，避免各函数自行补规则：

1. 原文解析保留楼栋、号码、位置及其是否属于明确标识语境；解析结果与房源匹配是两个步骤。
2. 明确原文优先级、继承条件及多房号政策；“没有房号”和“有房号但不确定”不能共用空值语义。
3. 同一轮身份快照同时服务静态检索、工具行筛选、覆盖判定、剩余语义和回退出口；禁止另按标题数字再次匹配。
4. 未知、歧义及房源身份来源不可靠的处理，必须覆盖最终正文、证据和转交资格。
5. 目标缺陷回归、真实模型稳定性及 all 不退步分别作为验收证据。

R4 的 unknown 示例应使用该测试身份表中确实不存在的号码。Spec §2.3 已登记 9999，不能在同一夹具里又默认它 unknown；可以使用隔离身份表，并在用例中显式说明。

# 客人回复语病与排版修复 Spec

版本：R2，2026-09-24。状态：**用户回复「开始」；已实施，发布 1.39.8。**

R1 只针对一种语病打补丁。用户要求泛用修复，并把旅游与闲聊回复的排版一并纳入，R2 改为从结构上解决。

## 1. 现状证据

### 1.1 真实样本（测试会话，生产数据只读）

| 样本 | 现象 |
| --- | --- |
| 「马桶坏了」→ 115 字 | 条件写反：「如果马桶还能勉强用，就先到公共区域……应急」；开头「收到，您好，……」拼接别扭；提示词要求一至两条建议，实际约四条 |
| 「明天天气咋样」→ 454 字 | 【天气】【气温】【湿度与风】【实用提醒】四个小节**挤在同一段**；结尾时效说明直接接在正文后 |
| 「排一条路线吧」→ 675 字、1817 字节 | 上午至傍晚的行程是一整段；末段把后续活动、提醒、天气说明、祝福与时效说明混成一段 |

### 1.2 根因

**R1 缺陷（确定，影响所有普通回复）**：`services/guest_reply_policy.py::sanitize_guest_reply` 用 `_safe_sentences` 按「。！？；」切句过滤承诺，每句 `strip()` 后**直接首尾相接**。紧跟句号的换行和空行因此全部丢失。

- 这解释了 1.1 的分布：句中换行（「近期可留意：」之后的 • 列表）幸存，句号后的分段（各【小节】之前、时效说明之前）全部被压平。
- `integrations/tourism.py::format_tourism_reply` 明明用空行接上时效说明，出口仍被压成一段，也是同一原因。
- 模型很可能原本分了段，是本地清洗破坏了结构。

**R2 设施回复是自由段落**：`prepare_facility_issue_reply` 只能按句事后过滤，无法判断句子内部逻辑；前缀「收到，」直接拼在模型的问候语前；条数只靠提示词约束。按规则逐类追语病会无穷无尽。

### 1.3 相关代码

- 普通回复出口：`guest_reply_policy.py::prepare_guest_reply` → `_plain_text_guest_reply`（去 Markdown，列表符改 •）→ `sanitize_guest_reply`；天气另经 `_warm_weather_reply`。
- 旅游：`tourism.py::format_tourism_reply` 拼时效说明；`deepseek_client.py::_refine_reply` 对旅游强制精炼，提示词要求「短段落或项目符号」。
- 设施：`deepseek_client.py` 系统提示中设施段落；`guest_reply_policy.py::prepare_facility_issue_reply`（任务创建成功后才调用）。
- 知识库问答已改为发审核原文，不经模型改写，不在本 Spec 范围。

## 2. 功能点

### A. 所有普通回复：保住段落结构（泛用）

| 编号 | 内容 |
| --- | --- |
| A1 | `sanitize_guest_reply` 改为**先按行拆分**，每行内部按句过滤承诺，再按原有换行拼回；空行保留，连续三个以上换行收成一个空行。承诺过滤的判定规则不变 |
| A2 | 新增确定性排版步骤，放在所有普通回复出口的最后：① 每个【标题】另起一行，前面空一行；② 每个 • 列表项独占一行；③ 时效说明（「这是我今天……查到的」）前固定空一行；④ 行尾空白去掉。只调整换行，**不增删任何文字** |
| A3 | 旅游精炼与主回复提示词补充版式要求：小节用【标题】开头并单独成段，行程按时段分行，每段不超过约 120 字 |

### B. 设施故障回复：改为「建议清单」（泛用）

| 编号 | 内容 |
| --- | --- |
| B1 | 模型输出新增 `facility_advice`：1～3 条短建议，每条是一个独立动作，按安全优先排序；设施场景不再采用模型的整段 `reply_text` |
| B2 | 本地逐条检查：去掉**带条件的建议**（如果/若/假如/万一，if/unless 等）、问句、危险操作、承诺与自称已提交、超过约 40 字的长句；**最多保留 2 条** |
| B3 | 本地统一组装：「收到，」+ 建议 +「我已提交管家人工处理，请您稍等。」开头、结尾与标点全部由代码负责 |
| B4 | 一条都不剩或模型未给出清单时，沿用现有固定兜底 `_ZH_FACILITY_FALLBACK` / `_EN_FACILITY_FALLBACK` |

1.1 的「马桶坏了」在新流程下的期望形态（具体措辞取决于模型给出的清单）：

> 收到，先别再冲水，也不要自行拆修。可以看一下水箱盖是否盖平。我已提交管家人工处理，请您稍等。

## 3. 风险与决策

| 编号 | 事项 | 建议 |
| --- | --- | --- |
| D1 | 设施建议是否按条截断 | **截到 2 条**。清单每条是完整建议，截断不会切断句子；模型已按安全优先排序，最重要的留在前面 |
| D2 | 设施建议里的条件句 | **一律去掉**。故障应急应是直接动作；这次的语病正是条件写反，去掉条件句能覆盖整类问题，而不是某一种说法 |
| D3 | 去掉建议后是否补写替代建议 | **不补**。补句等于替模型编造本店事实（如「有公共卫生间」） |
| D4 | 是否对任意语病做确定性检测 | **不做**。做不到，也不宣称；唯一通用的办法是再调一次模型审校，会增加 1～3 秒与费用，且审校本身可能改错事实。本 Spec 不采用 |
| D5 | 旅游回复是否也改成清单 | **不改**。旅游内容长且灵活，改清单会损失信息；用 A1～A3 解决排版 |
| D6 | 对话中途回复以「您好」开头 | 本 Spec **不处理**，属风格问题，不影响理解 |

其他风险：

- A1 改的是所有普通回复共用的出口，影响面大：承诺过滤在逐行处理后必须与原来**完全一致**，用现有全部测试加真实样本回归证明。
- A2 只动换行不动文字，用「排版前后去掉空白后逐字相同」作为测试断言。
- 路线回复已到 1817 字节，接近企业微信文本上限 2048 字节。A2 增加的换行会让字节数略增；实施时先核实现有出口对超长回复的处理，**若没有保护，单列给用户决定**，不在本 Spec 内顺手扩大范围。
- B1 改变模型输出结构：旧格式或字段缺失时必须安全退回 B4 兜底，不能报错或发空回复。

## 5. 实施记录（2026-09-24）

- A1：`_safe_text_keeping_breaks` 与原 `_safe_sentences` 共用同一取舍判定 `_keeps_sentence`，只额外保留句前换行；被删句的分段让给下一句。
- A2：`layout_guest_reply` 接在 `prepare_guest_reply` 最后。小节标题只在句末标点或冒号之后、且不超过 8 字时才另起一段，句中的【名称】不动。
- B：`AssistantDecision.facility_advice`（格式异常只丢弃该字段）；`prepare_facility_advice_reply` 逐条检查并组装；原 `prepare_facility_issue_reply` 删除，其全部安全用例迁移到新函数。一条建议含多句时拆开逐句检查。「X 分钟内到」这类时间承诺只在设施建议里拦截，不加进共用承诺过滤，以免误删「步行 10 分钟到地铁站」。
- 超长回复：客人回复只按 1500 字符截断，未按企业微信 2048 字节保护，按 §3 约定单列给用户决定。
- 验证：新增 24 项测试（含 3 条生产真实样本）；全量 1841 passed / 24 skipped；Ruff、mypy、diff-check 通过。
- 已知上限：路线类回复若模型本身不分段，排版步骤不会拆开行程正文（只改换行、不改文字），依赖新提示词，需上线后以真实消息验证。

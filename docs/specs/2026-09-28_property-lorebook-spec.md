下文省略公共前缀 `src/homestay_bot/`。

| 现状 | 代码依据 | 影响 |

## 二、功能点

### F0（1.48.0）停车位置误判修复

- 已在本地完成：`services/knowledge_evidence_policy.py::_build_evidence_plan_for_period` 里的「免费/收费互相矛盾」检查，只在客人问费用时才生效。
- 依据：导入春和景明后，用生产数据模拟，「开车停哪里」判为「尚未确认」。
- 验证：已补红测，全量测试通过。

### F1（1.48.0）按订单自动识别房间

1. 新增一个统一入口，确定「本次住宿」。优先级：
   1. 客人已确认的住宿（现有机制，不变）；
   2. 客人名下**恰好一张**当前有效订单，并且这张订单与客人的关联**可信**（见决策 D1）；
   3. 以上都没有，就不确定房间。
   - 「当前有效」沿用 1.43.0 的 `domain/stay_status.py::is_current_stay`。
2. `respond` 检索知识时，房间取上面的结果。门锁密码的拦截规则不变。
3. 第一次按订单自动识别出房间的那轮回复，末尾加一句告知，比如「您本次入住的是《挽江》（10月3日–10月5日）」，方便客人发现对错。同一张订单只说一次，记在已有的 `conversations.stay_confirmation` JSON 里，不新增表或列。
4. 仍然先请客人确认的情况：
   - 名下有多张当前订单；
   - 订单关联不可信；
   - 客人自己说「不是这间」或「订错了」，现有的否认流程接手。
5. 订单改期、换房、取消后，自动识别的结果跟着订单变；已确认的住宿仍按现有规则失效后重新确认。

### F2（1.49.0）房源卡片（借鉴：常驻条目）

1. 每间房一张短卡片，内容来自 `PropertyProfile`：房名、房型、区域、地址提示、停车说明。在后台房源页编辑。
2. 只要 F1 确定了房间，这张卡片就作为一条「本房间审核资料」进入检索结果，排在首位，并计入字数预算。它和知识条目走同一道证据核对：模型说出卡片里的事实算有依据，卡片之外的仍按原规则处理。
3. 卡片只收地址、楼层、停车这类「住这间就该知道」的信息。Wi-Fi 密码、门锁密码不进卡片：Wi-Fi 仍放在知识条目里，客人问到才给；门锁密码永远不进。
4. 字数有上限（建议 300 字），超出的部分在后台保存时就提示，不在发送时截断。

### F3（1.49.0）追问沿用上文话题（借鉴：扫描深度）

1. 客人最后一句**认不出话题**，并且像追问时（比如「那要钱吗」「几点」「在哪」），就往前看同一会话里最近 **2 条**客人消息，时间限 **30 分钟内**，借用其中最近一次识别到的话题。
2. 借的只是话题，问什么属性（时间、费用、位置）仍然以最后一句为准。比如「早餐几点？」→「那要钱吗？」，要回答的是「早餐的费用」。
3. 最后一句本身认得出话题时，不往前看，避免把上一个话题串进来。
4. 旅游、房态、价格、故障、紧急这些分支的判断不受影响，只作用于静态知识的检索和证据判定。

### F4（1.49.0）房名随百居易同步

- 百居易对账时顺带更新房名。
- 员工在后台手动改过的房名不覆盖，需要一个「人工锁定」标记（见决策 D4）。

### F5（1.50.0）组合与排除关键词（借鉴：次要关键词、排除词）

- 知识条目新增两个可配置字段，在后台编辑，改了不用发版：
  - 「必须同时出现」：比如「停车」要同时出现「哪里」「怎么走」之一才命中；
  - 「出现就不命中」：比如出现「黄鹤楼」就不算本店问题。
- 需要一次数据库迁移。现有话题正则保留，作为兜底。

### F6（1.50.0）按房间分组管理、导入识别房间

- 后台知识页可以按房间筛选、分组显示。
- 导入工具支持 `scope` 和 `property_id` 字段，判断「同一条知识」时把房间也算进去，不同房间的同问法条目不再冲突。
- 顺带清理：把挽江 6 条问法里为绕过冲突加的「挽江」前缀去掉。

## 三、不做的事

- 不把整份入住指南或全部知识塞进提示词。每轮仍按问题检索，最多 8 条，受字数预算限制。
- 不绕开证据核对，不让模型改写审核答案里的数字、时间和条件。
- 门锁密码、同一订单里其他客人的信息，任何情况下都不进提示词。
- 不改旅游、房态、价格、紧急、客诉这些分支的规则。

## 四、风险与决策（请逐条确认）

| # | 决策 | 选项 | 建议 |
|---|---|---|---|
| D1 | F1 里「可信关联」指什么 | a. 员工合并客户或管家核对确认过的关联才算；b. 同步到的任何关联都算 | **a**。认错一次，就会把别人的地址和 Wi-Fi 发出去 |
| D2 | 自动识别后要不要告诉客人 | a. 第一次告知一句；b. 不告知 | **a**。成本很低，还能及时发现认错 |
| D3 | 追问往前看多远 | 2 条客人消息、30 分钟内；或其他数值 | **2 条、30 分钟** |
| D4 | 房名同步时，人工改过的房名怎么办 | a. 加人工锁定标记，锁定的不覆盖；b. 一律以百居易为准 | **a**，需要一次小迁移（`property_profiles` 加一列），可以并进 1.49.0 |
| D5 | 房源卡片用现有字段还是新增一个「卡片正文」字段 | a. 复用现有 5 个字段；b. 新增一个自由正文字段 | **a** 先做；不够用再加 |
| D6 | 分期 | 按上表三期，每期单独确认、单独发布 | 同意则按此执行 |

主要风险：

- **认错房间**：由 D1、D2 控制。另外，多张订单时一律先问客人。
- **追问误借话题**：只在最后一句认不出话题时才借，并有条数和时间限制。回归资料里的 `followup_loses_topic` 场景应该由失败转为通过，其他必过场景不得退步。
- **卡片占用字数预算**：卡片有字数上限，检索条数再按剩余预算计算。
- **生产数据**：F4、F5 各需一次迁移，都只新增可空列，可以回滚。

## 五、验收

每期都按现有发布流程走：
1. 红测，再补回归用例。
2. 全量离线测试。
3. 真实模型回归门禁：必过场景零退步。
4. 部署。
5. 测试号实际收件验收。

各期重点：

| 期 | 验收重点 |
|---|---|
| 一 | 合成数据：只有一张挽江订单的客人问「地址在哪」，直接答挽江地址并附一次告知；有两张订单的客人先被请求确认；春和景明问「开车停哪里」给出固定回答 |
| 二 | MT 系列追问场景由失败转为通过；房源卡片内容能被正确引用；房名显示为百居易的真名 |
| 三 | 后台修改组合或排除关键词后立即生效；导入不同房间的同问法条目不再冲突 |

## 六、用户决定（2026-09-28）

原话：「后面会增加一个一键入住的按钮，让客人报订单号。识别房间后发送欢迎入住xxx房间等信息。追问向前看客户的所有消息。要不了多少token。员工后台改过的，同步时不保留。直接全部做完」

| # | 决定 | 落地方式 |
|---|---|---|
| D1 | 按「可信关联」自动识别（未改动建议）。「一键入住报订单号」是以后的入口，本期不做，识别结果统一走 F1 的入口，按钮上线后直接接入 | 本期可信关联 = 客户名下的订单（客户由员工合并或核对后才会挂上订单），实现时核实 |
| D2 | 识别出房间后，发送「欢迎入住某某房间」及相关信息 | 同一张订单只发一次：房名、入住和退房日期，以及房源卡片里的地址、停车等信息 |
| D3 | 追问往前看这位客人在本会话里的**所有**消息 | 话题识别在本地完成，不增加模型 token；只借话题，属性仍以最后一句为准 |
| D4 | 房名一律以百居易为准，同步时覆盖员工的修改 | 不加人工锁定标记，不需要迁移 |
| D5 | 房源卡片复用现有字段（未改动建议） | — |
| D6 | 三期合并，一次做完、一次发布 | 版本 1.48.0 |

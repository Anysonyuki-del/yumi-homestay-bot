## 3. 功能点

### F1 紧急情况后续的固定答复（U1）

- **什么时候算紧急情况进行中**：会话处于人工模式，且最近一次接管原因是 `emergency:*`。员工回复或手动交还之前一直有效，不设自动过期，与边界补充 P9「紧急只能手动交还」一致。
- **哪些消息给固定答复（确认点 1）**：进行中的紧急情况里，客人发来的求助类后续消息。
  - 例子：怎么办、该怎么做、怎么处理、然后呢、要不要报警、要不要走、还要做什么、好的、收到、我们出来了。
  - 固定答复 = 该危险类别的处置答复（见下一条）+「值班管家已收到通知，正在处理」。
  - 再通知一次值班员工，附上客人原话。
  - 不调用模型，不联网，不发联网安抚，带 `stale_exempt`。
  - 如果后续消息本身又命中紧急判定，仍按现有紧急流程处理。
- **处置答复从哪来**：
  - **首选知识库**：已启用的审核知识，类别为「紧急处置」，关键词含危险类别代码（`fire`、`gas`、`electric`、`medical`、`violence`、`access`），命中就原样发出。管家在后台维护，可以写本店专属的处置信息，例如燃气总阀、灭火器、安全出口的位置。
  - **兜底**：知识库没有对应条目时，用 `EmergencyService` 现有的该类别安全提示。
  - 中英两版：审核知识按会话语言取对应的问答；模板本来就有两版。
- **判定逻辑放在一处**：写成 `emergency_service` 里的纯函数，会话服务和回归工具都调用它，避免两边判定不一致。
- **根因同时修掉**：求助类说法（怎么办、怎么处理、该怎么做）不再触发「时间词 + 提问」的联网规则。不在紧急情况中的「停电了现在怎么办」，也交给普通回复和本店知识，不去联网。
- **知识草稿**：为 6 个危险类别各起草一条「紧急处置」知识草稿，内容来自现有安全提示，本店专属位置留空，由管家填写。
  - 虚构版本写进共用资料，供回归测试使用；
  - 不向生产导入草稿（确认点 2）：真实条目由 1.41.0「经验沉淀」从真实事件中起草，经管理员确认后启用。

### F2 问价流程（对比版，U2）

这一版和边界 Spec 重构里的问价实现，届时用同一套回归门禁和虚构场景对比，择优保留。

- **参考价对应到房间**：
  - 工具执行器用房源资料里的渠道对照表（`Property.channels`），把渠道房源编号换算成房间；
  - 每间房只返回一条：房间名、是否整段可住（合并调用房态查询）、住宿期间每晚的参考价、币种，以及口径说明「参考价，以实际下单为准」；
  - 不向模型暴露渠道房源编号和渠道类型；
  - 对应不上房间的价格行丢弃。
- **参考价算作依据**：查询成功后，参考价作为金额的依据，模型据此报价时不再被拦下、不再被换成「尚未确认」。
  - 这沿用现有房态查询的放宽方式，没有做到「每个事实逐项绑定来源」。边界 Spec 4.3 的逐项绑定更细，对比时正是要看这个差异。
- **统一问价判定**：新增 `answer_policy.asks_price`，联网分流、工具开放、交易判定共用，并补上英文问法（how much、price、rate、cost 等搭配 room、night、stay）。和 1.39.16 统一「在问房态」是同一种修法。
- **带日期时强制调用**：
  - 问价带日期时，强制调用参考价工具；
  - 同时问房态和价格时，也调用参考价工具，因为它已经合并返回了是否可住；
  - 没有日期、上下文里也没有日期时，不调用工具，直接追问「请问您计划哪天入住、住几晚？」，不回「尚未确认」。
- **问价不再转人工**：
  - 只问价格的问题，用参考价回答后不进入人工模式，也就是 `handoff_reason` 不再因为单纯问价返回 `price`；
  - 讨价还价、要求折扣、要求确认最终成交价，仍然转人工。

  这一条与边界 Spec 的 P5（房态、价格查询不因为出现价格词就整体转人工）方向一致，属于对比版的一部分。

### F3 回归工具补强

- **连发消息逐条回放**：场景里连续多条客人消息（中间没有机器人回复）时，逐条经过路由；紧急情况进行中这一状态在条与条之间保留，并使用 F1 的同一个纯函数。
  - 判定以最后一条的回复为准；
  - 紧急类场景额外要求前面那条命中紧急。
- **转人工路由**：模型判为需要人工、最终回复是转人工话术时，记为 `handoff`。
- **使用线上的工具执行器**：改用 `HostexReadOnlyToolExecutor`，只把最底层的百居易客户端换成按共用资料返回的替身，包括房源与渠道、房态、渠道参考价。这样参考价换算、房态整理这些线上代码也在门禁覆盖范围内。
- **收紧不当的期望，不放宽禁令**，每条改动都记入基线文件的 `expectation_changes`，注明原因：
  - `PI-折扣`：禁用片段「五折」改为只拦「答应了折扣」的说法，例如已为您打五折、可以打五折、给您五折、已授权。拒绝时提到「五折」不算违规。
  - `PI-内部`、`PI-提示词`：期望路由改为允许普通模型路径作答，不得泄露内部信息的禁令保持不变。
  - `C-取消`：F3 的转人工路由修正后，按原期望判定。
- 新增场景：
  - 紧急后续：燃气、火警、医疗各一个连发场景；
  - 不在紧急中的「停电了现在怎么办」；
  - 问价：带日期、英文、只问价格不转人工、讨价还价转人工；
  - 参考价对应不上房间：替身里放一个无主渠道。

## 7. 风险

- **F1 的误判**：
  - 现有紧急词表有误报，例如设施咨询被判成燃气泄漏。误报之后，客人的求助类后续也会收到处置答复，直到员工回复。
  - 只有求助类消息给固定答复，其他问题照常回答，影响有限。根本解决靠 P10。
- **F1 的内容**：真实知识库目前没有「紧急处置」条目，上线后会先用模板兜底；管家审核启用草稿后，才会有本店专属信息。
- **F2 的放宽**：参考价作为依据时，仍可能替同一回复里的其他本店事实背书，风险与现有房态查询相同，对比时由门禁和人工复核来量。
- **F2 多一次查询**：参考价工具合并房态以后，每次问价多一次百居易调用。
- **合并**：`deepseek_client`、`answer_policy`、`conversation_service` 与边界 Spec 的重构交叉。问价部分本来就是用来对比的版本，合并时按对比结果取舍。

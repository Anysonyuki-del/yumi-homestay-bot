## 1. 目标及用户已明确的业务约束

老板／管家在每间房的卡片上能够快速知道：谁的住宿安排覆盖哪些日期、本次退房和下一单入住还有多久、是否有周转压力，并可直接点击客人姓名查看客户档案。

已明确的正常计划：

- 当地时间为 Asia/Shanghai。
- 12:00 计划退房，可能延迟。
- 同日换客时，正常 12:00–15:00 为计划周转清洁时段。
- 15:00 起入住；这不是客人一定在 15:00 抵达的事实。
- 客人可能通过其他路径完成入住、退房或准备；本系统无流程记录不等于现场没完成。
- 名字放入对应的住宿日期区间，并支持快速进入客户信息。
- 倒计时必须同时显示客人、事件和绝对时间，不让用户猜姓名属于哪次入住。

成功标准：管家在同一张卡片即可回答“这笔订单是谁、何时退房、下一笔是谁、何时可入住、两者间隔多久”，且不会把计划误认成事实。

6. 名字、日期、事件关联正确；时间变化不制造完成事实。

不新增数据库迁移、不安装依赖、不换前端框架、不新增客户详情页、不改订单或任务状态机。管理员原有调整记录入口、权限、审计和凭证门禁保持。

## 4. 卡片的最终结构

从上到下固定为：

1. 房间名称／房号 + 当前安排状态；不再悬放单独的客人姓名。
2. 最多两行事件：本次退房、下一单入住。每行包含可点击客人称呼、事件倒计时、绝对日期时间及计划标识。
3. 符合条件时一行“计划周转间隔”。
4. 默认展开的日期标题与住宿条；保留原 3／7／14 天切换及横向滚动。
5. 真实待办数量和一个对应主动作。逾期任务仍突出，不因入住发生而自动完成。
6. 次级展开区：本系统准备记录、调整记录及说明。原安全提示在相应操作处保留。

移除被新事件行替代的旧“下次入住／下次退房”区块、通用三段计划横幅和日期格重复计数。避免在首屏同时出现三套同义时间信息。不会改造与本次无关的首页、投诉、设置等页面；共享宏的现有调用方仍需兼容。

示例全部为合成客人，假设当前 9/9 04:00：

```text
A101                                          今日周转

本次退房  客人 A    还有 8 小时     今天 12:00（计划）
下一单    客人 B    还有 11 小时    今天 15:00 起入住
计划周转间隔 3 小时

9/8                         9/9                         9/10
    [客人 A · 1 晚 ── 至 12:00]
                                 [15:00 起 ── 客人 B · 1 晚 ── 至 12:00]

待办 2 项，其中 1 项逾期                         去处理
▸ 本系统记录
```

图示非像素设计稿。文字、日期与区间表达为必需项；沿用当前字体、颜色和组件，不另做视觉风格重建。

## 5. 订单与事件选取规则

### 5.1 一笔订单是最小显示单位

每笔住宿至少保留：内部订单 ID、房间 ID、客户 ID（可空）、客户显示名（可空）、入住日期、退房日期、现有退房核验信息。

派生计划开始为入住日 15:00，计划结束为退房日 12:00。时间统一由服务端时区感知逻辑构造，模板不解析中文日期。时间轴和倒计时共享同一订单投影，避免姓名、日期和链接不同源。

不用姓名去匹配客户；同名不同 ID 是不同客户。相邻订单即使同一客户也保留订单边界，不在本次改写订单或连住数据。

### 5.2 本次退房与下一单

- 有跨日住宿覆盖今天：退房事件取该住宿订单的计划退房时间。
- 今日有离店订单：当天没有实际退房核验时，保留其退房事件；过 12:00 后显示待确认，不因时间经过就丢弃。
- 今日同房间有离店 A 与到店 B：退房行始终对应 A，入住行始终对应 B。不要用主标题选出的 B 姓名配 A 的退房时间。
- 无当前住宿但有待到店订单：只显示下一单入住行；该订单完整离店日期可从住宿条查看，不虚构“当前住客”。
- 入住日当天如果只有订单计划而没有实际入住事实，15:00 后仍显示该单“到店待确认”；不能凭时钟把它切成已入住。后续住宿日可按日期显示“住宿期内”。
- 可信实际退房核验仅按已有字段及既有业务语义使用；没有具体时刻只显示“已退房”，不补写 12:00 为实际退房时间。
- 最近日期必须与客户从同一个订单对象取得。相同日期存在多笔候选且不能确定唯一目标时显示“有多笔入住／退房安排”，在时间轴分别列出，不能通过数据库顺序选一个当真实住客。
- 同一客户的相邻订单显示“续住安排”，不称为换客、不计算强制清洁窗口；没有客户 ID 时不能靠同名推断续住。

### 5.3 查询窗口

本次复用当前快照的历史两天加所选未来范围，不为倒计时引入无界查询。范围内没有后续订单时写“当前同步范围内暂无后续订单”，不得写成全局无预订。跨出窗口的住宿保留真实起止日，在视口裁切并显示延续标记。

下一笔相距很远的全局订单查询不属于本次必须项；页面用范围说明避免误导。

## 6. 倒计时、周转与主状态

### 6.1 计划不是到店承诺

默认入住行必须明确为“距可入住时间”，绝对时间写“今天 15:00 起”。不能写“客人将在 15:00 到店”。当用户以后提供可信 ETA 时再扩展“预计到店”，不在本次新增字段或假定所有人准点到达。

退房倒计时使用“计划退房”。用户已说明可能延迟，因此到点只提示待确认，不能断定超时占房。

| 事件与时段 | 显示 |
|---|---|
| 距计划退房还有正时长 | “距计划退房还有 X 小时 X 分钟” |
| 恰好达到退房节点 | “已到计划退房时间 · 退房待确认” |
| 已过退房节点且未核验 | “计划退房时间已过 X 分钟 · 退房待确认” |
| 已核验退房 | “已退房”，停止该退房倒计时 |
| 距下一单 15:00 还有正时长 | “距可入住时间还有 X 小时 X 分钟” |
| 已到或已过 15:00，无实际到店事实 | “已到可入住时间 · 到店待确认”，绝对计划时间保留 |
| 仅有住宿日期覆盖 | “住宿期内”，不显示“已确认入住” |
| 没有本地准备记录 | 辅助显示“本系统准备情况：未确认”，不覆盖主安排 |
| 来源过期 | “入住安排待核实”；保留的倒计时注明“按上次同步计划” |

时间格式：超过或等于 24 小时显示天／小时，不足 24 小时显示小时／分钟，零单位可省略；不足 1 分钟写“不足 1 分钟”。正负判断用原始时间差，不因四舍五入提前跨节点。不显示负数倒计时。绝对时间始终存在，跨日用“明天”或“月／日 + 时刻”。

### 6.2 周转间隔

只有同日不同客人的离店与到店对应关系明确，才显示计划周转间隔：下一单可入住节点减本次计划退房节点，正常为 3 小时。

它不是“还剩多少清洁时间”，也不是实际需要清洁三小时。没有实际退房时刻不能显示“实际可用清洁时间”。无当日下一单、不确定候选、同客续住时不强行生成这个指标。

### 6.3 延迟退房边界

当前没有可信的已批准延迟时刻，因此本次不显示“延迟到 14:00”等推断值。12:00 后未核验显示退房待确认，并保留下一单 15:00 节点，足以让管家看到需要核实的周转安排。

后续若新增已批准延迟数据，需另行确认接入：退房倒计时改用批准时间，15:00 或以后且有下一单则提示冲突。仅延迟请求不改变计划。本次不能通过解析 `LATE_CHECK_OUT` 任务描述提前实现这一扩展。

## 7. 日期轴与住宿条

- 每天一个等宽日期列，内部端点按当日时间比例定位；采用原生 CSS Grid／定位与当前样式能力，不引入日历库。
- 9/8–9/9 的一晚住宿跨到退房日 12:00；不因为占两个日期格就显示两晚。晚数是退房日期减入住日期。
- 下一单从 9/9 15:00 起显示，12–15 点留白或淡色表示计划周转，不画成一整天空置或全天同时入住。
- 条内只出现一次姓名和晚数；完整起止日期可由可访问说明／轻量详情呈现，不能只有鼠标悬停才能获得。
- 今日在日期标题处标记，避免每条住宿重复“今天”。空白区域写“无订单”或保持轻量空白，不表示可售。
- 相邻有效区间在同一轨道排列；实际订单区间重叠时分轨并提供文字“订单时间重叠，需核对”。零售房态以外的经营判断不由此自动触发。
- 超出显示窗口裁切并加前／后延续标记；姓名仍只出现一次，不能切断后看不到客户入口。
- 长姓名截断不撑宽页面，保留完整可访问名称。正文严格模板转义，不将客户名拼入 HTML 或内联脚本。
- 手机允许日期轴内部横向滚动，整页不横向溢出。链接触控高度至少 44 CSS px，焦点可见；客户条不模拟拖动改期。

## 8. 客户链接

倒计时姓名与住宿条姓名均用原生 `<a>`，目标为现有 `/employee/customers/{customer_id}`。同页打开，保留浏览器新标签和键盘能力。不增加悬浮客户卡或复制客户资料。

- 有 ID、有姓名：显示真实 `Customer.display_name`。
- 有 ID、无姓名：显示“查看客人”。
- 无 ID：显示“未关联客人”，不生成链接；订单本身仍展示。
- 相同显示名不共享链接，必须各自使用真实关联 ID。
- 保留现有认证授权，不在公开页面新增客户信息。
- 浏览器返回时保留原 `days` URL；正常历史返回保留位置。若确需补位置恢复，仅保存页面位置和范围，不把客户姓名或订单内容放进存储，不扩充签名会话 Cookie。

## 9. 时间更新与防止刷新丢数据

页面渲染提供服务器观察时刻和事件绝对时间；显示时区固定为 Asia/Shanghai。浏览器按经过时间计算倒计时，不依赖设备把系统时间设对。

只建立一个页面级分钟定时器，不每个客人一个，不做秒级服务端轮询。更新倒计时文本不移动焦点、不持续触发屏幕阅读器播报。无 JS 时仍有完整绝对日期时间和静态状态。

当跨过计划事件节点／当地午夜，或隐藏超过一分钟后恢复：

1. 没有未保存修改、没有提交／上传进行中时，可对现有页面执行一次 GET 刷新；保留范围与位置。使用已有防重复状态，不能因一个页面有多个事件同时到点而刷新多次。
2. 有未保存或正在提交的内容时，不自动导航。倒计时文本继续安全更新，显示“安排可能已变化，保存后刷新”及刷新入口；复用 `dirtyForms` 并覆盖本页原有调整记录表单。
3. 本次采用现有页面 GET 导航刷新，网络失败沿用浏览器原生重试／返回能力，不承诺离线继续展示旧页面；不得将失败转换成“无订单”的成功空态。不要为此另建客户端数据缓存系统。
4. 页面观察时间和 Hostex 最近同步时间是不同字段；重新渲染页面不能把旧 Hostex 数据显示成刚同步。

保留现有六小时来源可信窗口，本次不调整同步任务或新建远程请求。

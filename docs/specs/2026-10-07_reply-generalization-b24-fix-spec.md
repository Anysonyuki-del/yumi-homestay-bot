## 1. 第一段：现状证据（2026-10-07 本地复现）

六项反例全部在当前 `main`（`2e2f33b`，实现与 v1.69.0 相同）上用离线探针复现：真实 `ConversationService`、真实适配器与核验函数，模型与平台为替身，不调用外部服务。

| 编号 | 复现结果 | 1.68.2 同输入 | 性质 |
| --- | --- | --- | --- |
| B24-R1 | 「插座那边窜白烟」，计划 `current_hazard:fire`：主回复成功时发撤离与 119；主回复失败时只发「抱歉，刚才查询没有顺利完成…」，员工通知为「模型服务暂时不可用」 | 无计划，同样是通用失败话术 | 新能力在失败出口未闭合，不是对 1.68.2 的退步 |

**根因归类**（与 Codex 一致）：都是模型选择结果进入本地流程后的边界没收紧，不是同义词不足，不需要补词表。

- R1：计划风险只在成功出口消费（`ConversationService._process_model_reply_body`）。
- R2：`answer_policy.resolve_handoff_reason` 与 `process_debounced_message` 的客诉分类都取第一个命中的文本变体，情绪词先命中就看不到后面变体里的硬理由。
- R3：`DeepSeekGuestAssistant._merge_item_knowledge` 把各项检索结果合成一个池，`_selection_evidence_plan` 对每项都用这个池核验。
- R4：`_apply_evidence_plan` 用静态分项替换整份 `reply_text` 与 `reply_parts`。
- R5：`turn_plan._verify_risk` 先做集合成员判断再判断类型。
- R6：`verify_selected_evidence` 只把回答条目和按主题词识别出的同组条目放进冲突检查，主题认不出时 related 的真冲突被跳过。

**生产影响判断**：v1.69.0 已上线。R2、R3 是新引入的风险，但触发条件窄（被空白拆开的退款词；一句话问两间房且模型交换编号）；R1 没有比 1.68.2 更差；回滚到 1.68.2 会同时丢掉 20 个已稳定的改进。建议不回滚，尽快修复发布 1.69.1（见 D-F3）。

## 2. 第二段：方案

### 2.1 R1：成功与失败出口共用计划风险处置

- 在 `ConversationService` 抽出一处「已核验计划风险处置」（拟名 `_apply_plan_risk`）：输入来源摘要已核对的计划，`current_hazard:<类别>` 且词面未判紧急 → `_escalate_emergency` 并结束本轮；`possible_hazard` 且词面未判危险 → `_answer_possible_danger` 后继续。
- 主回复成功：沿用现有位置调用。主回复抛 `AssistantUnavailableError`：先过时复核，再用异常里的计划调用同一处置，处置结束才进入设施或通用失败分支。
- 不重复调用规划器；摘要不一致或规划失败时不处置（无计划）；确定性危险下限不变，只升不降。

### 2.2 R2：硬理由先于情绪复核，所有文本变体一致

- `resolve_handoff_reason`：对全部 `policy_variants` 计算接管理由；任一变体给出 agitated 以外的理由，按现有优先级返回该硬理由；只有全部命中都是 agitated 时才允许计划复核。
- 客诉分类入口（`handle_message`、`process_debounced_message`）：对全部规则文本分类，优先取非 agitated 的客诉结果（保留 `ComplaintService.classify` 的风险等级）；只有全部命中都是 agitated 时才进入软判定。抽成一个共用函数，两个入口不各写一份。

### 2.3 R3：每个子问题拥有自己的合法候选集合

- `_merge_item_knowledge` 除合并后交给模型的整体信封外，同时返回 `item_id → 该项合法候选`：该项自己的检索结果，加上整句检索结果中「非房间专属，或房间专属且属于该项房源」的条目。
- 该项点名的房号无法映射为已知房源时，该项候选排除全部房间专属条目，不用已确认住宿房间的事实回答点名的未知房间。
- `_selection_evidence_plan` 的核验、同组冲突与回退到现行证据计划，都只用该项候选。
- 复用 `KnowledgeService` 现有的房源、有效期、审核与触发词过滤，不新建检索器。

### 2.4 R4：静态证据只接管静态子问题

- 计划成功时，证据计划（证据选择或现行证据计划）只接管 `static_fact` 项。计划里没有 `static_fact` 项时，不让证据计划接管整轮回复（同时修复 SR-毛巾、SR-遗失被「尚未确认」覆盖）。
- 主调用对其余无工具、无联网结果的项（店外稳定信息、寒暄、不明确等）在新字段中逐项回传回答（D-F1）。本地按计划顺序组合：静态项用核验后的审核原文，其余项用模型逐项回答，并照常经过本店事实与店外时效过滤；工具与联网分项按现有方式追加。
- 模型漏答某项时该项为空，不把未限定的整段模型原文补回来；服务申请的收尾仍由实际登记结果决定。
- 规划失败或无计划时保持现行行为（证据计划按整句接管）。

### 2.5 R5：非法输入类型统一转为规划失败

- `_verify_risk` 先处理缺省值，再要求字符串，再做白名单判断；数组、对象、数值、布尔一律视为不合规，由 `verify_turn_plan` 返回 failed。
- 复查同一 JSON 边界中的其他字段（`kind`、`id`、`withdraws`、`target_room`、日期）的类型处理，保证任何形状的输入都只会得到 ok 或 failed，不抛异常；不用无条件吞异常代替输入校验。

### 2.6 R6：冲突范围按「是否在讲同一件事」确定，不按模型标签

- 保留 X14 中有实证的部分：只检查客人问到的钟点或收费；按问法而不是答案正文判断主题。
- 冲突分组 = 回答条目 ∪ 问法点名同一主题的合法候选 ∪ **标准问题与任一回答条目的标准问题实质相同的合法候选**，不论模型是否把它标为 related（判定规则见 D-F2）。
- 结果：「健身房几点开放？」两条 8:00/10:00 无论如何分配标签都不能 grounded；安静时段与客厅开放时间（标准问题不同）仍正常回答。

### 2.7 §4.1 验收证据补齐（隔离 PostgreSQL）

- HUMAN_ACTIVE 情绪词复核通过后，暂停主回复：另一事务的新客人活动与员工接管都能推进；恢复后旧结果不建任务、不登记出站。
- 合并作业中途提交后中断，重建服务重放同一作业：最终任务、客诉、通知、任务与出站各只有一份。

### 2.8 不做的事

- 不新增第二个规划器、平行检索器、通用语法解析或针对新问法的词表；不扩展任务取消（D11 不变）；不改 D13、D14 的已决定取舍。
- D1 独立改写集仍由独立 Codex 会话编写；E1–E6 已公开，只进回归集，不作盲测。

## 3. 第三段：风险、验证与决策

### 3.1 风险

- R4 改变主调用 Schema 与系统提示，影响全部场景，必须全量真实模型门禁。模型逐项回答的质量与漏答率要看门禁结果。
- R6 的「标准问题实质相同」是确定性近似：措辞差异较大的同主体条目仍可能漏组，残余风险写进代码 `ponytail:` 注释。
- R3 收紧候选后，部分以前能答的多房间问题会回未确认，这是正确方向的失败。

### 3.2 验证计划

- 每项先写能捕获原缺陷的最小回归（E1–E6 转为正式用例），确认在当前代码上失败，修复后通过；断言最终客人正文、实际路由、会话模式、任务与通知，不只断言函数返回值。
- 补 §2.7 两条 PostgreSQL 用例。
- 改动触及 `application.py` 之外的公共回复流程与主模型提示，提交前本地全量一次；CI；全量真实模型门禁（`REPLY_GATE_SCOPE=all`）。
- 发布为 1.69.1：完整备份、仅替换 API、独立核对。

### 3.3 决策（2026-10-07 用户确认）

用户选择：D-F1 模型逐项回传；D-F2 标准问题实质相同；D-F3 不回滚，修复后发布 1.69.1；D-F4 修复完成后授权全量真实模型门禁、提交推送与生产部署（只限本 Spec 范围）。以下保留各选项原文。

- **D-F1（R4 组合方式）**：
  - 推荐：主调用对非静态、非工具项逐项回传 `{item_id, text}`，本地按计划组合，漏答的项为空。
  - 备选：主调用只回传一段「其余问题的回答」，本地整段追加在静态答案后。实现更简单，但无法判断漏答哪一项。
- **D-F2（R6「实质相同」判定）**：
  - 推荐：标准问题归一化后相同，或相邻两字重合度达到较高阈值（拟 0.6，以 K-安静-D 与健身房两组对照校准），即视为同一件事。
  - 备选：主题认不出时，任何被标为 related、且所问钟点或收费与答案矛盾的条目都判冲突。最安全，但会让 K-安静-D 一类重新回未确认。
- **D-F3（生产处置）**：
  - 推荐：不回滚，按本 Spec 修复后尽快发布 1.69.1。
  - 备选：先回滚到 1.68.2，修复后再发布。
- **D-F4（授权）**：修复完成后是否授权全量真实模型门禁、提交推送与生产部署。历史授权不适用于本轮。

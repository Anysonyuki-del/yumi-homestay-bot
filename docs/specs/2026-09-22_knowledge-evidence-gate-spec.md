# YuMi 静态知识证据门与真实回复验收 Spec

版本：R1，2026-09-22。状态：**待用户确认；确认并明确“开始”后实施。**

目标：修复静态本店问答的证据检查绕过与属性错配，让检索到的正确知识能安全进入最终回复，并使评估结果忠实反映真实 `respond` 行为。

本 Spec 对本轮证据门修复优先于旧数据库优化 Spec 的对应建议；不替代生产发布、外部调用或知识录入授权。

## 2. 范围与方案选择

比较：

| 方案 | 收益 | 风险/成本 | 决策 |
| --- | --- | --- | --- |
| 继续只补主题别名 | 小改动能增加识别率 | 无法区分早餐时间与无麸质能力，无法校验最终回复 | 不单独采用 |
| 分类/标题直接证明答案 | 容易覆盖新知识 | 标题可能只是问题，分类不能证明设施存在或政策成立 | 禁止 |
| 有限主题/属性规则 + 审核答案约束输出 | 不额外调用模型；来源和结果可复核 | 未覆盖说法会保守拒答，完整原文回答可能较长 | **采用** |
| 额外 LLM 判断蕴含或通用事实图谱 | 可探索复杂表述 | 新成本、误判、结构迁移和验收问题 | 本轮不做 |

采用方案不是通用语义理解：用规则确认问题对象、所问属性与适用范围，答案只来自当前请求实际可用的已审核知识。相似度、分类、标题只定位候选，不作事实证据。

**明确的产品取舍：**静态知识优先保证事实和限制完整，可以用审核答案替代模型自由改写。允许表达变化，不允许删除费用、否定、时间、范围或例外来提升通过率。

不改数据库、embedding provider、向量表、知识管理字段；不开发新的审核平台；不处理40条草稿录入。阈值0.45保留，暂不单独发布。

## 3. 请求判定：不能再用“别名没命中”豁免校验

在 `respond` 中区分已有工具/旅游/服务分支和静态知识回复，不以一个 `property_specific` 布尔值承担所有语义。

1. 已有旅游、实时工具、故障/人工服务等确定分支维持原顺序和权限，不让静态知识覆盖工具日期、价格、房态或服务处理。
2. 明确静态本店问题，或可识别的房间设施、入住政策、住客规则属性，必须经过本 Spec 的证据计划。
3. 有知识候选但无法确认问题主题/属性时，进入“知识意图未确认”，不能以非专属名义直接放行模型基于候选给出的事实。输出简短澄清，例如“您想了解房间的哪项设施或入住安排？”。候选命中不等于确认其相关性。
4. 明确无关的通用问题继续通用回答，不因无关知识候选就变为本店事实。此分支须有通用/旅游/服务对照回归；不能只靠 `not is_property_specific` 作为充分条件。
5. 没有知识且属于静态本店问题时走现有未确认/知识缺口路径；普通通用问题无须伪造知识缺口。

实施要求：把本次判定及其依据在请求内传给校验/出口复用，避免各层重新猜测产生不同分支。无需新增公共模型字段或模型输出协议。新增有限内部结构仅表达状态、主题/属性、支撑来源与原因；不得建通用规则引擎。

## 4. 主题与属性覆盖

复用 `knowledge_service.py::PROPERTY_TOPICS/detect_property_topics/normalize_text`。若答案属性规则使该文件职责过重，允许新增一个 `services/knowledge_evidence_policy.py`，专门提供本 Spec 的请求证据计划；不能拆出多个单调用框架。

### 4.1 本轮明确支持的主题

保留现有停车、早餐、宠物、加床、入住退房、发票、厨房、洗衣、电梯、接送、无障碍、行李、距离等主题；按公开校准/回归所需补齐：

- 温控、网络、卫浴、安静时段、床品及洗护用品。
- 儿童设施/限制、清洁服务、用电、饮用水。
- 代收/寄存、电视、客房设备、消防设施、公共区域及观景空间。

中文口语与英文共用同一主题定义，保留明确的反例，例如天气降温不等于房内温控、手机没电不等于本店用电规则、城市景点不等于本店观景台。不得用单字“水”“电”“room”无限放大本店识别。

### 4.2 属性规则

| 问题属性 | 支持答案至少需要表达什么 | 不能替代的内容 |
| --- | --- | --- |
| 是否提供/允许 | 对应对象的存在、提供、允许或明确否定 | 同类设施、分类和问题标题 |
| 时间 | 对应服务的时间或时段及适用条件 | 其他服务时间 |
| 费用/包含 | 对应项目的费用、免费、包含或不含及条件 | 开放时间、用品位置 |
| 地点/路径 | 目标设施的位置；距离另核对目的地 | 另一停车场或景点的距离 |
| 操作/范围 | 对应设备的操作或可调范围、单位 | 相邻设备或不相关数值 |
| 特殊能力/限制 | 明确对应请求，如无麸质、素食、宠物条件、儿童限制 | 普通早餐、普通床位或宠物主题词 |

对“早餐能做无麸质的吗”：仅时间信息必定未覆盖；明确“不能提供无麸质早餐”同样是有效答案，但不能改写为可以提供。不要将营养/过敏常识推断成厨房能力或安全保证。

多主题和多属性逐项核对：问早餐时间及费用，两者都要有证据；多个分句可以由同一完整问答支持。问停车费用及早餐是否包含，不得将费用要求错误套到所有主题。缺任一必需属性则保守未确认，本轮不引入复杂部分回答协议。

属性表是有限能力清单。无法识别的具体限定、同一主题里无法绑定的数值、矛盾答案、模糊房间范围，全部按证据不足处理，不能退回“主题词存在即可”。先用明确规则覆盖已知类型，不宣称任意自然语言属性均可自动识别。

## 5. 来源与最终输出规则

### 5.1 来源约束

- 仅使用本次检索、范围过滤与预算处理后实际交给模型的启用问答。
- 分类/标题可辅助主题和属性匹配；实际回答必须由答案正文支持，不能把问句的猜测写成事实。
- 维持一个审核问答为完整证据单元；不为了匹配抽掉同单元尾部否定、收费、房型限制或例外。
- 周边商户不能证明本店服务，静态历史价不能替代实时价，错房间资料不能合并作证。无法区分房间的跨房间查询保守处理。
- 候选草稿、用户历史、搜索结果、工具结果不能隐式升级为本店静态审核知识。

### 5.2 静态知识采用受约束输出

本轮不实现任意改写的语义裁判。对明确静态本店问答：

1. 证据计划不完整：使用对应语言的未确认/澄清回复，不保留模型对缺失属性的断言。
2. 证据计划完整：确定性选择覆盖所问属性的最少完整审核答案，保持同单元内容原样、按来源顺序去重；只增加固定中性连接语。模型回复与这些完整答案一致时可保留，否则使用审核答案替代自由改写。
3. 不把不同来源的数字、费用、否定拆开后重新组合。多个答案存在冲突或无法确定同一适用范围时未确认，不投票、不按最高相似度裁决。
4. 多条答案超出现有回复预算，不能强制截断原文。返回未确认/请细化问题，并保留“预算不足”诊断原因，而非声称知识库不存在答案。
5. 静态知识的确定性答案不再经过会改变事实的自由精炼。若必须沿用 `_refine_reply`，输出后必须再约束到同一证据计划；温度10℃、安静时段18点等改写不得在最后一步重新出现。

审核知识仍是参考数据，不执行其中的指令、不据其扩大工具权限。对于含内部指令、凭据或不适合直接给客人的条目，返回保守结果并标记需人工复核；不能把本条款当作允许绕过现有回复安全过滤的原文转发通道。安全过滤若改变费用、限制或破坏完整条件，不发送残缺答案。

### 5.3 工具、旅游和服务分支

不把知识里的数字白名单用于验证工具房态/价格，也不因本轮规则删除已成功的实时工具结果。工具成功只能支持其实际返回的字段；不能使同条回复中的无麸质早餐、免费停车等额外静态承诺获得整段豁免。

实施前读取 `respond/_validate_decision/_refine_reply` 全部调用方和分支，列明哪些出口产生静态知识文本。相关出口统一应用本规则；旅游事实保护、紧急安全回复、任务建议与人工接管不能被静态知识回答替换。

## 6. 评估改造：诊断指标与真实出口分开

保留 Recall@3、来源覆盖、属性覆盖、隔离等诊断；不再把 `grounded=False` 直接解释为模型回复已被拦。

`test_knowledge_retrieval_eval.py::evaluate_case` 保留真实仓储读取，回复部分调用实际 `DeepSeekGuestAssistant.respond`，使用同一次候选结果和受控模型 stub；不重复外部向量查询。从模型请求中检查实际上下文，从最终 `AssistantDecision.reply_text` 检查结果。

不得直接导入大型测试模块作为生产依赖。测试侧复用已有 stub 的最小公共部分，必要时放一个仅供测试的 helper；不新增一份模拟 `_validate_decision` 的逻辑。

分别记录：

- 原模拟回复是否原样保留。
- 错误断言是否在最终输出消失（替换为正确审核答案也算消除）。
- 有答案问题最终是否得到覆盖所问属性的审核答案。
- 无充分证据问题是否保守回复。
- 模型请求中是否出现禁止来源/事实。

不能仅以“输出不同于输入”证明安全，也不能以“正确回复被审核原文替换”判定错误。固定反例断言错误温度/时间/能力不存在；正例核对允许的完整来源答案及必要条件。原 `stub_reply_supported` 标签和用例文件不改，新端到端断言放测试或单独回归数据中。

无 `stub_reply` 的高风险案例补充本地对抗回复，例如 h3-030 的“可以提供无麸质早餐”，不能只测主题覆盖布尔值。

报告明确三个边界：真实模型未测、真实向量未重跑、公开样本不再独立。改造后指标定义有变化，应在同一源码上分别报告旧诊断与新出口指标，不把不同口径的百分比拼成提升曲线。

变异验证至少覆盖：删除属性要求、重新放行非专属绕过、改用标题事实、跳过最终输出保护、工具成功整段豁免。每项必须有真实链路测试失败，记录命令与失败断言；不要把删测试断言当成变异。

## 9. 指标与独立验收

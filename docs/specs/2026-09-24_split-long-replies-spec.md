# 超长回复有序拆分发送 Spec

版本：R1，2026-09-24。状态：**用户回复「开始」；已实施，发布 1.39.9。**

## 1. 现状证据

### 1.1 问题

企业微信客服文本消息 `text.content` 上限 2048 字节（UTF-8）。现有出口只按 **1500 字符**截断（`services/conversation_service.py::_limit_assistant_reply`），1500 个汉字约 4500 字节，**远超上限**。

- 生产样本：「排一条路线吧」的回复 675 字、1817 字节，已接近上限。
- 评估集里全部长答案用例（共 19 条）的审核答案在 2600～4900 字节之间。它们过去被判为「能回答」，但在生产上整条发出会被企业微信拒收——这个「能回答」本来就不成立。
- 已定的产品规则：**审核知识原文不得截断条件与例外**。按字节截断会违反它，所以用户选择拆成多条发送。

### 1.2 出站链路（逐条核对过的代码）

| 环节 | 位置 | 行为 |
| --- | --- | --- |
| 机器人回复出口 | `conversation_service.py::_send_prepared_guest_reply` | 所有机器人回复的唯一出口：登记 outbox 并按 outbox 编号写一条机器人消息 |
| 入队 | `application.py::TransactionalOutboxWeCom.send_text` | 每条客人消息一个 `wecom_send_text` 任务，outbox 编号按「来源消息 + 序号」确定 |
| 发送 | `application.py::send_guest` | 发送前做过时判定；同步失败中，连接错误与限流（45009）可重试，其余直接失败；成功后把 outbox 编号换成企业微信真实 msgid，并记录投递状态 |
| 过时判定 | `application.py::_guest_reply_is_stale` → `conversations.py::has_newer_conversation_activity` | 来源客人消息之后若出现**客人或员工**消息，本条跳过；机器人自己的消息不算 |
| 异步投递失败 | `application.py::_handle_guest_delivery_failure` | 企业微信先受理、稍后回调失败。安全拦截（fail_type 13）登记模型改写任务重发一次；其他类型重试一次；二次失败通知员工 |
| 改写重发 | `services/delivery_rewrite_job.py` | 模型改写被拦下的回复后重发，入队为新的发送任务 |

### 1.3 顺序保证现状

生产在一个进程里跑两条 worker 循环（`application.py` 启动段）：一条只跑模型任务（`wecom_process_message`、`guest_delivery_rewrite`），另一条跑其余全部任务，客人消息发送在这一条里**按 `available_at, id` 逐条串行**。

因此多段消息**正常情况下会按顺序发出**。会打乱顺序的只有：

1. 某段同步失败重试，推迟后被排到后一段之后；
2. 某段先被受理、后被异步判失败，重试或改写重发时，后面的段早已送达；
3. 将来若部署多个进程，发送任务会并发（代码注释已说明 claim 支持多 worker）。

## 2. 功能点

| 编号 | 内容 |
| --- | --- |
| S1 | **拆分**：出口处超过单条上限的回复，按「段落 → 句子 → 字符」的优先级切成若干段，每段不超过 1800 字节（给企业微信留余量），不在句子中间断开，除非单句本身超长 |
| S2 | **段数上限**：最多 3 段。普通回复已有 1500 字符上限，最多约 3 段；审核知识超出 3 段时回「尚未确认」并请客人细化，**不截断** |
| S3 | **链式有序发送**：只先入队第 1 段；第 k 段发送成功后，在同一事务里入队第 k+1 段。同步失败重试时，后面的段不会越过前面的段 |
| S4 | **逐段记录**：每段是一条独立的机器人消息，元数据记录同组编号、段序号与总段数，便于投递排查 |
| S5 | **时效说明只出现在最后一段** |
| S6 | 替代并回收已暂存的按字节截断方案（本地分支提交 `3997480`，未合并）：`fit_wecom_text` 仅作为超出段数上限时普通回复的最后兜底 |

## 3. 风险与决策（需用户确认）

| 编号 | 事项 | 建议 |
| --- | --- | --- |
| D1 | 每段要不要加「（1/2）」这样的序号 | **加**。异步失败重发一定会打乱顺序（见 1.3 第 2 点），有序号时客人能自己对上；代价是每段多几个字 |
| D2 | 发到一半，客人又发来新消息，剩下的段还发不发 | **继续发完**。同一个答案只发一半比多发一点更糟，尤其是审核知识的条件在后半段 |
| D3 | 发到一半，员工接管或员工发了言 | **停止发送剩余段**。人工已经介入，不能插话打断 |
| D4 | 中间某段同步失败且重试耗尽 | **后续段不再发送**，按现有流程通知员工，并在通知里注明「长回复第 k 段起未送达」 |
| D5 | 某段异步投递失败 | **只重发这一段**（沿用现有重试和改写），依靠 D1 的序号让客人对上顺序。改写重发时模型会改写内容：对审核知识而言，这会动到原文，这是**既有问题**，本 Spec 不扩大处理，只在交接里记录 |
| D6 | 拆分适用范围 | **所有机器人回复**（旅游、闲聊、知识、设施）。设施回复本身很短，不会触发 |

其他风险：

- 这是所有客人消息的出站链路，改错会影响每一条回复。验证必须覆盖故障情形，不能只测正常路径。
- 快速安抚回复用「最终回复全文的摘要」判断是否已发过（`conversation_service.py` 中的 `fast_ack_sha256`），拆分后仍以拆分前的全文计算，避免重复发送。

| `application.py` | `send_guest` 成功后入队下一段（S3）；员工接管时停止（D3）；重试耗尽时通知员工（D4）；元数据（S4） |
| `services/knowledge_evidence_policy.py` | 审核答案超出 3 段时未确认（S2） |
| 测试 | 见下 |

必须覆盖的测试（先红后绿）：

1. 拆分：段落优先、句子次之、单句超长时按字符；每段 ≤ 1800 字节；时效说明只在最后一段；不切断汉字。
2. 有序：模拟第 1 段同步失败重试，第 2 段不会先发；两条 worker 同时取任务时顺序不乱（隔离数据库）。
3. D2：中途客人发新消息，剩余段照发。
4. D3：中途员工发言或接管，剩余段停止。
5. D4：某段重试耗尽，后续段不发，员工收到注明段号的通知。
6. D5：某段异步失败，只重发该段。
7. S2：审核答案超过 3 段时回未确认，不截断。
8. 既有全部发送、重试、改写、过时判定测试保持通过。

上线验收：隔离环境跑完故障测试后发布；生产上从测试号发「排一条路线吧」这类长问题，在微信里核对**实际收到的段数、顺序和序号**，并查对应的投递状态。接口受理不算送达。

不涉及数据库迁移（元数据写入现有 JSON 字段）。

## 5. 实施记录（2026-09-24）

六项决策全部按建议实施。

| 功能 | 实现位置 |
| --- | --- |
| S1/S2/S5 拆分、段数上限、时效说明在最后一段 | `guest_reply_policy.py::split_guest_reply`、`_split_parts`、`fits_guest_reply_parts`；每段 ≤ 1800 字节，最多 3 段 |
| D1 段序号 | `_part_label`：中文「（1/3）」，英文「(1/3) 」 |
| S3 链式有序发送 | `application.py::TransactionalOutboxWeCom.send_text_chain` 只入队第一段；`send_guest` 成功后调用 `_enqueue_guest_reply_continuation` 在同一事务登记下一段，编号由分组与段序号确定并去重 |
| D2/D3 中途活动 | `_guest_reply_is_stale`：续发段只在出现员工发言时停止（`conversations.py::has_newer_servicer_activity`），客人追问不打断 |
| D4 中途失败 | 终态失败回调识别分段回复，登记 `guest_reply_chain_undelivered`，由 `_notify_undelivered_reply_chain` 通知值班员工段号 |
| D5 异步失败 | 沿用既有逐条重试与改写；重试与改写的发送载荷不带分段信息，不会重复触发续发 |
| S4 逐段记录 | 每段一条机器人消息，元数据 `reply_part` 记录分组、段序号与总段数 |
| S6 | 按字节收口 `fit_wecom_text` 仅用于超过段数上限的普通回复最后一段，以及改写重发 |
| 知识 | 审核答案超过 1500 字或拆不进 3 段时，证据计划回未确认（`reply_exceeds_message_limit`） |

实现中确认的既有行为：任务终态失败时载荷按隐私规则清空；失败回调拿到的是清空前的副本，因此段号通知仍可登记。

**验证**

- 新增 27 项测试。其中 9 项直接驱动真实 worker 循环（SQLite 文件库 + 企业微信替身）：只入队第一段、三段按序送达并逐段记录、第一段连接失败重试期间第二段不会先发且恢复后仍按序、中途客人追问照发、中途员工发言即停、第二段终态失败时第三段不发并登记段号通知、某段异步失败只重发该段。
- 变异验证：删除续发、续发段因客人追问停止、员工判定失效、失败不通知、不拆段，五项均有测试失败。
- 全量离线 1866 passed / 24 skipped；Ruff、mypy、diff-check 通过。按字节截断的中间方案曾让评估集的长答案用例变为未确认（该方案未合并、未发布），拆分方案下这些用例恢复为完整回答。

**未覆盖**：两条 worker 同时取任务（Spec §4 第 2 项后半）未单独测试——链式设计下同一条回复任何时刻只有一段在队列里，顺序不依赖串行，但未在多进程环境实测；审核知识被安全拦截后由模型改写重发会动到原文，为既有问题，未在本版处理。

## 6. 审查补修（2026-09-24，用户已授权「直接修」）

### 证据与范围

- `application.py::reply_chain_undelivered_payload` 未保留已有 `conversation_id`，`_notify_undelivered_reply_chain` 无法告诉员工定位哪个会话。
- `_guest_reply_is_stale` 续发只检查员工消息；`ConversationService._switch_to_human` 实际还会记录 `conversation_handoff` 审计，无员工消息时未被续发检查识别。
- `guest_reply_policy.py::_opening_paragraph` 遇独立标题会漏看正文开场白。共享调用方为中英文天气回复。

### 已授权的最小实现

1. 失败通知保留内部会话编号并显示，仍不保留聊天正文、外部联系人编号；旧任务无编号时明确提示无法定位。
2. 分段入队时在现有 JSON 载荷记录该会话最新接管审计 ID；续发沿用此边界，发现更新审计即停止。已有人工状态及入队前接管不拦截。继续保留员工发言拦截、客人追问照发。旧载荷无边界时保留原行为，不推测接管时间。
3. 开场白检查跳过正文前独占一行的【标题】，仅检查第一个实质正文段，不搜索全文。

### 验证与风险

- 真实 worker + SQLite + 企业微信替身验证失败通知定位、真实 `_switch_to_human` 保存/审计后停止续发、旧人工状态仍发完、无关会话审计不影响当前链。
- 中英文独立标题、正常段落及后文出现相同文案的边界回归；保留现有发送、重试、人工模式和天气测试。
- 不新增表、依赖或人工模式开关；沿用现有出站前检查，检查之后到网络发送之间的竞态不承诺消除。审计清理或旧版本待发任务不提供完整接管追溯。
- 本轮仅本地修复验证；提交、推送、部署及真实消息验收不在授权范围。

# 编造服务与时效问题分流 Spec

版本：R1，2026-09-24。状态：**用户回复「开始」；已实施，发布 1.39.13。**

来源：1.39.12 发版记录「风险与未覆盖」里的第 2、3 项，用户回复「23修复」。

## 1. 现状证据

### 1.1 联网回复编造民宿服务

1.39.12 在生产容器做真实 DeepSeek 复测时，天气回复里出现：

> 【客房服务】需改室内博物馆、美术馆，或帮叫车、安排接送，跟我说，我帮您排稳些。

民宿没有经过审核的叫车、接送服务，客人可能据此等车。这一句同时绕过了三道过滤：

| 过滤 | 位置 | 为什么漏过 |
| --- | --- | --- |
| 执行承诺 | `guest_reply_policy.py::_UNSAFE_COMMITMENT_PATTERNS` | 要求前面有「已经 / 马上 / 会 / 稍后」这类确定性副词 |
| 第一人称软承诺 | `_SOFT_COMMITMENT_PATTERNS` 第一条 | 要求「我」在前、动作在后；这句的「我」在最后，而且「叫车」「接送」不在动作词表里 |
| 设施断言（1.39.12） | `_contains_ungrounded_property_claim` | 这句没有「备有 / 提供」这类供应说法 |

### 1.2 时效问题没有分流到联网搜索

1.39.12 修改后，主提示词要求「没有查询结果时不给具体数值或安排」。真实对比中，未分流的时效问题编造情况从 6 次中 2 次降到 9 次中 1 次，残留的一次是「去汉口站怎么走最快」回答了「白天非高峰约三十到四十分钟」。

根因在分流：`integrations/tourism.py::classify_tourism_query` 把这三个问题都判为 `none`，主模型拿不到搜索结果，只能凭记忆回答：

| 问题 | 为什么没进联网 |
| --- | --- |
| 去汉口站怎么走最快 | `_LIVE_TOURISM_PATTERN` 只有「怎么去 / 怎么到 / 路线」，没有「怎么走」「最快」 |
| 今晚江滩有灯光秀吗 | 活动词表里没有「灯光秀」；`_DATED_TOURISM_PATTERN` 只认「今晚……去哪 / 玩 / 游」 |
| 东湖樱花开了吗 | 没有识别「开了吗」这类问当前状态的说法 |

问题在于分流规则把「有时间词的提问」限定成了「问去哪玩」，于是只能逐个补词表。

## 2. 功能点

| 编号 | 内容 |
| --- | --- |
| A1 | **编造服务**：一句话里同时出现「需要真人去做的服务」和「揽下来的说法」，不论先后，就判为编造服务并删除。<br>服务包括叫车、接送、接站 / 接机、送站 / 送机、代订 / 代购 / 代买、订票 / 购票、订餐 / 订位、预约、寄存、保管、送到 / 送餐、跑腿、带路、陪同等。<br>揽下来的说法包括帮、替、为您、给您、跟我说、找我、告诉我、我来、我可以等。<br>并入 `_contains_ungrounded_property_claim`，所以和设施断言的作用范围相同：只作用在客人没有问民宿信息的回复上。「可以打车前往」没有揽下来的说法，保留；「我帮您查一下公交」是查信息，不是服务，也保留 |
| B1 | **时效分流按两个维度判断**，在原有的订房优先判断之后执行：<br>① 问的是会变的信息：在现有词表之外补上怎么走、最快、多久能到、多长时间、灯光秀、表演、花期、开了吗 / 开了没、还开着、人多吗、排队；<br>② 带时间词的提问：今天、今晚、明天、这周、周末、最近、现在、目前等，同时是一个提问（吗、几点、多少、怎么、哪、是否、有没有等），而且问题里没有民宿一侧的词。<br>满足 ① 或 ② 就走联网搜索 |
| B2 | 民宿一侧的排除词：沿用 `_LODGING_OBJECT_PATTERN`（房间、民宿、客房等），再补上楼下、楼上、隔壁、门禁、前台、门口、院子、屋里、小区、管家。问民宿本身的问题（比如早餐、洗衣、打扫、入住）还会经过 `is_property_specific` 排除，不送去联网 |

## 3. 验证数据（写 Spec 时已测）

- **A1**：用 1.39.12 前后两轮对比得到的全部 38 条真实天气和时效回复做语料，命中 1 句，正好是 1.1 的编造服务，没有误删正常句子。
- **B1 / B2 模拟**（排除规则写进实现后再用测试确认）：
  - 应当改走联网的：今晚江滩有灯光秀吗、东湖樱花开了吗、去汉口站怎么走最快、今天黄鹤楼人多吗、最近武汉人多吗。
  - 仍然不走联网的：明天早餐几点、今天能洗衣服吗、明天几点有人打扫、明天几点能入住、今天能晚点退房吗、明天还有房吗、今天可以寄存行李吗、现在房间空调坏了、今天好热啊（不是提问）。
  - 「今晚楼下吵吗」在模拟中被误送联网，由 B2 的排除词修正。

## 4. 风险与决策

| 编号 | 事项 | 建议 |
| --- | --- | --- |
| D1 | 更多问题会走联网搜索，回复更慢（真实测量天气约 8～15 秒，普通回复 1～2 秒），也多一次搜索调用。快速安抚回复仍会先发出 | **接受**。时效信息编造的危害比慢几秒大 |
| D2 | B1 ② 仍会把一些没必要联网的问题送去搜索，比如「现在能点外卖吗」 | **接受**。代价只是慢一些，搜索结果仍会经过同一套过滤 |
| D3 | 不在非联网路径上删除具体数字和时长：没法区分审核知识里的「步行约 10 分钟到地铁站」和模型编造的数字 | **不做**。靠分流和提示词降低发生频率，这一点写进上限 |
| D4 | A1 按句删除，同一句里的正常建议会一起删掉 | **接受**，与 1.39.12 的设施断言一致 |
| D5 | 房型回复里「我这边看不到实时数据」的小问题（第 1 项） | 不在本次范围（用户只点了第 2、3 项） |

**上限**：A1 和 B1 仍依赖词表，只是改成了「同句共现」和「两个维度」的判断。词表外的服务说法仍会漏过；时效问题如果既没有时间词，也不在会变信息的词表里，仍会走主模型，这时只靠提示词约束。

## 6. 实施记录（2026-09-24）

| 功能 | 实现位置 |
| --- | --- |
| A1 | `guest_reply_policy.py`：`_PROPERTY_SERVICE_PATTERN` 与 `_SERVICE_OFFER_PATTERN` 在 `_contains_ungrounded_property_claim` 中同句共现判定 |
| B1 | `tourism.py`：新增 `_CHANGING_INFO_PATTERN`、`_TIME_ANCHOR_PATTERN`、`_QUESTION_PATTERN`，接在 `classify_tourism_query` 的稳定旅游判断之后 |
| B2 | `tourism.py::_HOMESTAY_SIDE_PATTERN`，并复用 `_LODGING_OBJECT_PATTERN`、`answer_policy.is_property_specific` |

**实施中与 Spec 的差异**（均在实施时发现，按同一原则处理）：

1. 会变信息的新词没有直接并入 `_LIVE_TOURISM_PATTERN`：「房间多长时间打扫一次」「早餐人多吗」「空调开了吗」也会命中这些词。所以新词单独成组，和带时间词的提问一样，先排除问民宿本身的问题。
2. 原有联网词表的判断也加上了民宿一侧位置的排除。原先「前台几点关门」「今晚几点关门禁」因为命中「几点关门」被送去联网，这是既有的误判，一并纠正。「从民宿怎么去东湖」这类问题不含民宿一侧位置，仍然走联网。
3. 排除条件补上了 `is_transaction_sensitive`：全量测试发现「大床房今晚多少钱」「今晚7号房现在订要多少钱」会被带时间词的提问规则送去联网，而房价只能来自百居易实时查询。
4. `test_knowledge_evidence_gate.py::test_general_question_keeps_existing_behaviour` 原本用「武汉明天会下雨吗？」作为与民宿无关的普通问题。这个问题现在按设计走联网，所以测试改用不带时间词的「武汉一般几月份下雨多？」，测试原意不变。

**验证**

- 新增测试 28 项：A1 两项；B1 应当走联网的 7 问、不应走联网的 10 问、用民宿词问会变信息的 9 问。编造服务一句和应当走联网的 7 问修改前失败、修改后通过；不应走联网的断言用来防止误伤，修改前大多已经通过，其中「前台几点关门」「今晚几点关门禁」修改前被误送联网。全量离线 1929 passed / 24 skipped；Ruff、mypy 137 个源文件、diff-check 通过。
- 六套离线评估各指标与 1.39.12 相同。六套评估集的 227 个问题在新旧两版分流规则下走向完全一致。
- 38 条真实回复重跑 A1：新增删除的只有 1.1 那一句。
- 生产 API 容器真实 DeepSeek 复测（沿用授权；只读配置、工具用假数据、不写库、不发消息，结束后清理，API 容器未重启）：
  - 1.2 的三个问题各 2 次，全部走联网搜索，答案来自搜索结果，耗时 11～20 秒；
  - 天气 3 次，开场白各一次，没有编造设施或服务；
  - 「请走正规渠道叫车」这类提醒保留（没有揽下来的说法）。

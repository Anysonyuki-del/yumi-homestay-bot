# 联网回复编造设施与房型问题不查房源 Spec

版本：R1，2026-09-24。状态：**用户回复「开始」；已实施，发布 1.39.12。**

这两个问题都是在提示词审计修改的真实 DeepSeek 前后对比中发现的，修改前后都存在，不是审计修改引入的。用户要求与审计修改一起修，合并为 1.39.12 发布。

## 1. 现状证据

### 1.1 天气等联网回复编造民宿设施

对比中出现的三句（生产 API 容器，真实 DeepSeek，工具用假数据）：

| 句子 | 出现版本 |
| --- | --- |
| 「雨大时可改去博物馆……或回民宿休息。我们备有雨伞、拖鞋和热茶。」 | 修改前 |
| 「雨具、烘干衣架前台都备着，需要随时找我拿」 | 修改后 |
| 「【客房服务】玄关置物篮有备用伞和一次性雨衣，随手取用。」 | 修改后 |

频率：修改前 7 次天气回复中 1 次，修改后 5 次中 2 次，样本不足以判断两版之间有差异。三句都是未经审核的本店事实，客人可能据此向管家索要不存在的物品。

**防线与漏洞**：`services/guest_reply_policy.py::remove_ungrounded_property_claims` 由 `_contains_ungrounded_property_claim` 判定，其中 `_PROPERTY_AMENITY_CLAIM_PATTERN` 要求「场所词在前、供应动词在后、间隔不超过 12 字」，且两份词表都是枚举的：

- 「我们备有」：主语是「我们」，不是场所词；`_PROPERTY_SELF_REFERENCE_PATTERN` 只认「我们民宿」这类完整说法。
- 「……前台都备着」：场所词在物品之后，「备着」不在动词表中。
- 「玄关置物篮有」：「玄关」不在场所表中，「有」不在动词表中。

**作用范围**（不变）：这条过滤只用在客人没有问民宿专属信息的回复上，包括：
- `deepseek_client.py::_remove_property_promotion`，在 `respond` 的联网旅游分支精炼前后各过滤一次；
- 非专属问题的普通回复与精炼回复；
- 投递失败后的改写（`deepseek_delivery_rewriter.py`、`delivery_rewrite_job.py`）。

这些路径上不可能有经过审核的本店设施信息，出现设施断言就必然是模型自己加的。

### 1.2 「你们有哪些房型」不调用房源工具

对比中这个问题修改前后各 2 次，都没有调用 `list_properties`，客人收到的是知识缺口模板「当前审核资料尚未确认民宿专属信息……」。

根因：`deepseek_client.py::_should_force_property_catalog` 只在问题含「介绍…房」或「房间/房源/房型…介绍/详情/名称」时开放并强制房源工具；「有哪些房型」「都有什么房间」都不命中。工具没开放，模型无从查询，证据门只能回未确认。

## 2. 功能点

| 编号 | 内容 |
| --- | --- |
| A1 | 设施断言改为**同句共现判据**：一句话里同时出现「本店一侧的锚点」和「供应或持有的说法」，不论先后顺序，就判为设施断言。锚点包括我们、咱们、民宿、店里、前台、大堂、玄关、门口、房间、客房、屋里、楼上楼下、院子、厨房、公共区域、管家等。供应说法包括备有、备着、常备、配有、提供、放着、放在、可借、借用、免费、赠送、取用、找我拿，以及「有备用 / 一次性 / 免费……」等。替换原 `_PROPERTY_AMENITY_CLAIM_PATTERN`，作用范围不变 |
| A2 | 小节清理：某个【标题】下的正文全部被删除时，把这个标题一并删除，避免留下空标题（例如「【客房服务】」） |
| A3 | 联网旅游和精炼提示词各补一句：「正文只写武汉的公开信息，不写民宿自己的设施、物品或服务」。这是针对已复现故障的约束，用来降低发生频率；A1 仍是确定性的兜底 |
| B1 | 房源工具的触发条件改为按意图归类：问题问的是「本店有哪些或哪几种房」就开放并强制 `list_properties`。覆盖房型、户型、房源、房间类型、「哪些/什么样的/几种房」「房间都有哪些」、介绍类问法，以及英文 room types / which rooms。房态（「还有房吗」「有房间吗」）和房内设施（「房间有空调吗」「房间有什么设施」）不触发 |

## 3. 验证数据（写 Spec 时已测）

- **A1 误删测试**：用对比中得到的全部 33 条真实天气和时效回复做语料，按句检查，共命中 3 句，正好是 1.1 的三句编造，没有误删正常句子。
- **B1 问法测试**：10 种应当命中的问法全部命中。10 种不应命中的问法全部未命中，包括房态、房内设施、打扫、房价、加床等。

## 4. 风险与决策

| 编号 | 事项 | 建议 |
| --- | --- | --- |
| D1 | 按句删除：同一句里有正常建议也会一起删掉。例如「……需要随时找我拿；雨大时欢迎先回民宿歇脚」会整句删除 | **接受**。宁可少一句建议，也不发编造的设施；现有按句删除的机制不变 |
| D2 | A3 是否要加 | **加**。这是已复现的故障，提示词能降低发生频率，过滤只是兜底 |
| D3 | 英文 | **A1 不扩到英文**。英文还没有观察到同类写法，凭猜测扩规则可能误删。B1 已包含英文问法 |
| D4 | 上限 | A1 和 B1 仍依赖词表，只是把「固定词序」改成了「意图归类 + 同句共现」。词表之外的说法仍可能漏过：A1 漏过会像现在一样发出编造的设施，B1 漏过会回「尚未确认」，不会编造 |

## 7. 实施记录（2026-09-24）

四项功能点和四项决策均按建议实施。

| 功能 | 实现位置 |
| --- | --- |
| A1 | `guest_reply_policy.py`：`_PROPERTY_SIDE_ANCHOR_PATTERN` 与 `_PROPERTY_SUPPLY_CLAIM_PATTERN` 在 `_contains_ungrounded_property_claim` 中同句共现判定，取代 `_PROPERTY_AMENITY_CLAIM_PATTERN` |
| A2 | `guest_reply_policy.py::_drop_emptied_headings`，接在 `remove_ungrounded_property_claims` 的按句过滤之后 |
| A3 | `deepseek_tourism.py` 搜索系统提示词、`deepseek_client.py::_refine_reply` 精炼提示词 |
| B1 | `deepseek_client.py::_should_force_property_catalog` |

实施中发现：原有房间介绍测试用的是房态执行器替身，收到 `list_properties` 时因缺少日期抛出 KeyError，工具其实没有执行成功；那条测试能通过，只是因为「介绍一下这间房」不算民宿专属问题，模型原话被放行了。新旧两条测试都改为用真实执行器包装房源替身（`RecordingExecutor(HostexReadOnlyToolExecutor(HostexCatalogStub()))`）。

**验证**

- 新增 24 项测试（三句编造各一例、店外场所不误删、空标题清理、20 种问法、房型问题走真实回复链路），修改前失败、修改后通过。全量离线 1901 passed / 24 skipped；Ruff、mypy 137 个源文件、diff-check 通过。
- 用实现后的代码重跑 33 条真实回复：只改动 3 条，删掉的正好是三句编造；同一行里的正常建议（「或回民宿休息」）保留。
- 生产 API 容器真实 DeepSeek 复测（用户回复「开始」即确认沿用授权；只读配置，工具用假数据，不写库、不发消息，结束后已清理，API 容器未重启）：天气 5 次均无编造设施、开场白各一次、无空标题；「你们有哪些房型」3 次均调用 `list_properties`，并按工具结果回答两个房型。

**已知上限**：
- 一条回复里的「帮叫车、安排接送，跟我说」属于编造的服务，没有供应或持有的说法，A1 拦不住；它所在的「【客房服务】」小节因此也保留了标题。A3 的提示词已要求不写民宿自己的服务，但这不是确定性保证。
- 房型回复里模型把「【江景大床房】和【城景双床房】」写成了方括号，排版步骤把它当成小节标题另起了一段，3 次里出现 1 次，只影响版式。

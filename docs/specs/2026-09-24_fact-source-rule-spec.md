# 不得编造事实：全局底层规则 Spec

版本：R1，2026-09-24。状态：**用户回复「开始」；已实施，发布 1.39.15。**

## 1. 背景与目标

1.39.14 测试号验收中，「有什么玩的」的回复写了「您住的是江汉路附近的话」。模型没有民宿地址，这个位置是编造的。

用户要求：**不得编造事实应成为全局底层规则**，对所有类型的事实生效，而不是只补「位置」这一类。

### 1.1 为什么现在的防线总会漏

过去半天修过的同类问题：

| 版本 | 漏过的说法 | 修法 |
| --- | --- | --- |
| 1.39.12 | 「我们备有雨伞」「前台都备着」「玄关置物篮有」 | 设施断言：主体 + 供应说法同句共现 |
| 1.39.13 | 「帮叫车、安排接送，跟我说」 | 服务断言：服务 + 揽下来的说法同句共现 |
| 1.39.14 验收 | 「您住的是江汉路附近的话」 | 尚未处理 |

每次都是按**说法的类型**补一条规则，下一类说法照样漏。防线也是按**路径**加上去的，新路径同样会漏：

- 入住前提醒里的天气摘要（`lifecycle_reminders.py::_build_content`、`_safe_weather_summary`）来自联网搜索，只去了链接、截了三句，**没有任何事实过滤**就发给客人。
- 服务请求的模型安抚（`respond_ack`）只过滤承诺，不过滤民宿事实。
- 设施故障的建议清单只查危险操作和条件句，不查民宿事实（例如「前台有备用吹风机」）。

### 1.2 客人可见文字的全部出口

| 出口 | 来源 | 现在的事实防线 |
| --- | --- | --- |
| 主回复：民宿专属问题 | 审核知识原文（证据门）或百居易工具结果 | 证据门；工具作证 |
| 主回复：非专属问题（稳定旅游、闲聊） | 模型自由文本 | `remove_ungrounded_property_claims`（按类型） |
| 主回复：联网问题 | 联网搜索 + 精炼 | 同上 |
| 投递被拦后的改写重发 | 模型改写 | 同上 |
| 服务请求安抚 | 模型 | 只过滤承诺 |
| 设施故障建议清单 | 模型 | 只过滤危险操作、条件句等 |
| 入住前提醒的天气摘要 | 联网搜索 | **无** |
| 固定话术、员工消息、门锁凭证、订单与房源数据 | 系统或人工 | 不属于模型编造，不在本 Spec 范围 |

## 2. 规则本身

**事实来源封闭**：关于民宿本身的任何信息——位置与周边、设施、物品、服务、规则、价格、房态、人员安排——只能来自本轮提供的依据：审核知识、百居易查询结果、系统登记的本店事实（城市为武汉、共 7 间房）。没有依据就不写，或说明需要确认。不推测客人住在哪里。店外信息只写有来源的内容或公认的常识。

这条规则分两层落实。两层都只有一个定义，所有出口共用。

## 3. 功能点

| 编号 | 内容 |
| --- | --- |
| F1 | **单一规则来源**：新增 `services/fact_policy.py`，集中存放：<br>① 上面那段规则的中英文提示词常量；<br>② 句子判定函数；<br>③ 系统登记的本店事实。<br>现在散落在主提示词、精炼提示词、联网提示词里的同类禁令（「不写民宿自己的设施、物品或服务」「不得编造房间名称」等）改为引用这一个常量 |
| F2 | **提示词层**：所有面向客人的模型提示词都带上这条规则，包括主回复、精炼、联网搜索、改写重发和服务安抚。另加一条架构测试：列出所有面向客人的模型调用模块，逐个断言引用了规则常量；新增面向客人的模型调用必须登记进这份清单，否则测试失败。员工侧的客诉草稿、FAQ 草稿和客户摘要不在清单内，在测试中逐个注明 |
| F3 | **确定性层：按「说的是谁」判定**，取代按说法类型逐条补的做法。一句话只要提到民宿一侧（民宿、本店、我们这里、您住的地方、房间、前台、玄关、楼下、管家等），就按顺序判断：<br>1. 含供应或服务的说法（备有、提供、可借、找我拿、叫车、接送等）：**删**；<br>2. 是问句、请客人提供信息、祝福或自我介绍：**留**；<br>3. 含相对位置（附近、周边、位于、距离、步行、若干分钟或公里或站、直达、片区），或提到民宿设施话题：**删**。设施话题复用知识库的 `detect_property_topics`，不另写词表；<br>4. 只把民宿当作客人的去处，如「回民宿休息」「从民宿出发」「把民宿设为起点」，或者是「不要在房间里……」这类禁止性提醒：**留**；<br>5. 其余提到民宿的句子：**删**（默认不放行）。<br>单独成行的小节标题不参与判定；正文被删空的小节，标题一并删除（沿用 1.39.12 的逻辑） |
| F4 | **英文**：同样的五步判定，用英文锚点和说法。锚点如 our homestay、the homestay、your room、front desk、reception、lobby、the host、we have/provide/offer。英文还没有真实语料，只有构造的测试用例；这一点写进上限 |
| F5 | **覆盖所有模型出口**：<br>① `remove_ungrounded_property_claims` 内部改用 F3 判定，函数名不变，所以现有调用处（非专属主回复、联网精炼前后、两处改写）自动生效；<br>② 补上三处漏网：入住提醒的天气摘要、服务请求的模型安抚、设施建议清单的每一条 |
| F6 | **不改的部分**：民宿专属问题的证据门与工具作证路径保持原样。审核知识原文本身就是依据；工具作证的回复仍可能在工具数据之外添油加醋（例如「每间风格都不太一样」），这一点写进上限 |

## 4. 验证数据（写 Spec 时已测）

语料为 1.39.12 至 1.39.14 生产容器对比与复测中得到的全部 96 条真实非专属回复（天气、时效、旅游）。按 F3 的五步判定逐句检查：

- **删除**：共 13 句，全部是编造，包括：
  - 设施：前台都备着雨具、玄关置物篮有备用伞、我们备有雨伞、民宿露台；
  - 位置：您住的是江汉路附近的话、民宿附近最近的地铁站；
  - 路程：从民宿出发约 20 到 30 分钟、约三十到四十分钟；
  - 其他：暗示民宿位置的地铁换乘路线，在民宿看老电影（暗示有放映设备）等。
- **保留**：祝福（祝您住得安心）、自我介绍、请客人告知出发地（即使句中带「住处附近」「民宿所在片区」）、「把民宿设为起点」「回民宿休息」、不带具体数字的「从民宿去汉口站要看出发时段和路况」。
- **误删**：「需要的话，我可以帮您看看民宿附近最近的地铁站怎么走」属于提议而非陈述，但因为含「民宿附近」被删。影响是少一句客套话，按「宁删勿编」接受。

## 5. 风险与决策

| 编号 | 事项 | 建议 |
| --- | --- | --- |
| D1 | 默认不放行：提到民宿、又不属于放行句式的正常句子会被删 | **接受**。这就是「底层规则」的含义：说不出来源的民宿信息，默认不发 |
| D2 | 判定仍依赖锚点词表和几种放行句式 | 锚点只描述「说的是谁」，词很少且稳定。编造类型再多，只要说的是民宿就会被拦。锚点外的说法（例如只写「附近有地铁站」而不提民宿）仍会漏，写进上限 |
| D3 | 工具作证的专属回复不做逐句过滤 | 不做。那条路径上的事实本来就来自工具；在工具数据之外添油加醋的问题，只靠提示词约束，写进上限 |
| D4 | 英文没有真实语料 | 按同样结构覆盖，并在测试中构造用例；上线后如果有英文客人，再用真实回复校准 |
| D5 | 用生产历史回复做一次更大范围的误删评估 | **建议做**：只读统计生产库里机器人历史回复在新判定下的删除率，并抽查删除的句子，不导出正文。**需要用户确认** |

**实施中与 Spec 的差异**：

1. `remove_ungrounded_property_claims` 改为每行都逐句判定。原来是先整行判断，只有命中的行才拆句；新判定里「问句、祝福放行」是按句成立的，整行判定会让同一行里的编造跟着一句「告诉我」一起放过。句子都保留时原样保留整行。
2. 服务安抚的规则加在所有需要人工的回复共用的 `_safe_human_sentences` 上，而不只是安抚。原因是「已收到，前台备有矿泉水」这种句子，会因为带「已收到」而被保留，这个漏洞在所有需要人工的回复里都存在。
3. 设施建议只用第 1 步：建议本来就要说房间设备，完整判定会把「检查房间空调遥控器」当作设施话题删掉。
4. 非专属问题如果有百居易工具作证（例如「介绍一下这间房」），不做这层过滤。这是 F6 的落实；全量测试发现，这种回复原本会被新规则删掉。

**验证**

- 新增测试：
  - `test_fact_policy.py` 共 32 项（真实语料的删除与保留样本、英文构造用例、架构测试）；
  - 三处漏网出口各 1 项，修改前失败、修改后通过；
  - 另有设施建议与人工回复的保留断言。
- 全量离线 1968 passed / 24 skipped；Ruff、mypy 138 个源文件、diff-check 通过。
- 六套离线评估：错误放行与未获确认负样本均为 0，指标与 1.39.14 相同。
- 真实语料：95 条回复中改动 12 条，删掉的全部是编造（路程时间、前台雨具、玄关雨伞、叫车接送、民宿附近地铁站、在民宿看老电影，以及只剩标题的空小节）。同一行里的正常句子保留。
- 固定话术：18 种（客诉安抚、中英文各类紧急提示、人工收尾、设施回复等）按真实发送路径在改动前后各跑一遍，逐字相同。
- **D5 生产历史只读评估**（用户确认）：
  - 94 条机器人消息、214 句，新判定标出 13 句，去重 7 句；
  - 其中位置编造 3 句：「您住的是江汉路附近的话」「按住处附近地铁站」「从地铁口到民宿这段」；
  - 早期设施回复 1 句：「就先到公共区域或附近的卫生间应急」；
  - 工具作证回复的添油加醋 1 句：「每间风格都不太一样」，这条路径运行时不经过这层过滤；
  - 系统固定话术 2 句：「我已提交管家人工处理」「我会立即联系值班管家」。它们在过滤之后才拼接，运行时不受影响，上面的逐字比对已确认。

  - 「有什么玩的」不再推测客人住处，改为询问日期、人数和偏好；
  - 仍提到民宿的句子只有询问与提议（「告诉我几点从民宿出发」「帮您排从民宿出发的路线」）。

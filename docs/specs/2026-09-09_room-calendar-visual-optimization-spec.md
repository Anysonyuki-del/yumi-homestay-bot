## 4. 模块结构及示意

每张房间卡片仍按“房间标题 → 客人事件倒计时 → 日期日历 → 下一步／待办 → 次级记录”排列。本次只调整日历及其必要的相邻间距，不重组导航和业务操作。

日历模块内部：

1. 顶部轻量标题“近期安排”，旁边显示实际可见日期范围；例如“9/7–9/16”。不要把包含历史两天和今天的窗口只解释成七个格子。
2. 两行日期头：上行星期，下行日期；今日突出，跨月的第一日显示月份。
3. 同一背景网格中的住宿轨道。
4. 底部轻量范围延续／滚动提示与必要空态。不放一排重复状态徽标。

```text
近期安排                                  9/7–9/16
  周日      周一      周二      周三      周四
  9/7       9/8      [9/9 今天] 9/10      9/11
 ┆         ┆         ┆         ┆         ┆
 ┆         ┆ [客人 A · 1 晚]   ┆ [客人 B · 1 晚] ┆
 ┆         ┆         ┆         ┆         ┆
```

此文本图仅表达“日期列＋同轨道区间”，不是精确比例图。正式实现以第 6 节几何公式为准；住宿条不为让字放得下而擅自延长占用时段。

### 5.1 色彩语义

| 类型 | 推荐样式 | 含义限制 |
|---|---|---|
| 未来计划住宿 | 背景 `#EFF6FF`，边框 `#BFDBFE`，文字 `#1E40AF` | 计划安排，不代表已确认到店 |
| 计划区间覆盖当前时刻 | 背景 `#DBEAFE`，边框 `#60A5FA`，文字 `#1E3A8A` | 强调当前时间相关性，不使用“实际在房”的暗示 |
| 计划区间已经结束 | 背景 `#F1F5F9`，边框 `#CBD5E1`，文字 `#475569` | 已过去的计划；未核验不得加“已退房” |
| 已有真实退房核验 | 沿用历史条样式，附文字“已退房” | 只消费当前已有核验字段 |
| 订单区间重叠 | 边框 `#B45309`，必要处背景 `#FFFBEB`，可读文字提示“时间重叠” | 不只靠颜色表达；不自动判定超售或修改订单 |
| 来源过期 | 保留可读文字，附模块级“上次同步计划，待核实” | 不把整个模块调低 opacity 导致低对比度 |

姓名不再默认永久下划线；条整体明确可点击，悬停／键盘聚焦可显示下划线和清晰边框。整条无客户关联时不使用链接手形和交互高亮。颜色必须在实际背景上通过文本对比度检查，不能仅凭上述色号宣称无障碍通过。

### 5.2 今日与周末

今日使用轻蓝色整列底色 `#EFF6FF`，日期文字蓝色加粗；“今天”用小型文字标记，不能把日期头挤成三行。底色位于住宿条下方，不覆盖链接。

周末只在日期头轻微区分，不再增加整列彩色底。今日强调优先于周末。暂不增加实时“现在”竖线，避免与计划日期、倒计时争夺注意力。

## 6. 区间几何与轨道分配：必须实现的核心

### 6.1 精确端点

设窗口首日当地 00:00 为 `W0`，最后一日之后的 00:00 为 `W1`，共有 `D` 个完整日期列。

每笔正常住宿的计划开始 `S` 为入住日 15:00，计划结束 `E` 为退房日 12:00。裁切后 `S' = max(S,W0)`，`E' = min(E,W1)`。只绘制 `E' > S'` 的区间。

以日为单位：`left = (S' - W0) / 24h`，`width = (E' - S') / 24h`；再乘单日列宽得到像素，或除以 D 得到相对总内容宽度的百分比。日期头、列背景与条的位置必须使用同一个内容宽度和列数。

Asia/Shanghai 下无需引入通用夏令时系统，但所有源时刻仍需时区明确。不得解析本地化日期字符串计算。

验算：104px 日宽时，入住端点位于该日左侧后 65px，退房端点位于退房日左侧后 52px；正常一晚宽度为 91px；同日换客的 12–15 点间隔为 13px。不能把一晚条画成两整列。

不使用未关联布局容器的 CSS 百分比 `translateX` 模拟日偏移：其百分比可能按条自身宽度计算。执行者需给出端点几何测试，证明定位基准正确。

### 6.2 非重叠订单复用轨道

将有效区间按原始计划开始、计划结束、内部订单 ID 稳定排序，依次放入结束时间 `<= 当前开始时间` 的最小编号可用轨道，否则新建轨道。

区间采用 `[S,E)`；上一笔结束与下一笔开始相等不算重叠。同日 12:00 退房和 15:00 入住必须能在同一轨道。每笔订单带明确 `lane_index`，模板不再用循环下标充当行号。

预计房间订单量小，可采用简单扫描已有轨道的分配方式，不为此引入堆、图算法库或独立排期引擎。相邻同客订单不自动合并，仍可在同轨道连续显示。

真实重叠才分行；行数反映最大同时重叠量，不反映总订单数量。分行后不能掩盖重叠，应在相关条和模块提示中表达。多轨道过多时自然增高，不添加嵌套纵向滚动或悄悄隐藏订单。

### 6.3 裁切、窄区间、异常数据

跨窗口左／右端用小箭头或截断端样式表示延续；完整日期保留在可访问名称和展开列表中。裁切不会改变晚数。

小于可点击宽度的可见碎片仍按真实几何画，不能扩展到邻单；提供同一模块下的“查看本房间行程列表”原生折叠，列出姓名链接、完整日期、晚数、来源。该列表是窄条及键盘／触屏的补充，不是另建客户页面。

退房不晚于入住等异常区间不使用 `max(1,span)` 伪造成有效住宿。标明有一条日期异常待核对，保留安全的关联客户入口；不修正真实数据、不推断夜数。

## 7. 横向滚动、响应式与交互

- 只有一个横向滚动容器包含日期头、网格背景和全部轨道；不让日期头与条独立滚动造成错位。
- 滚动条使用浏览器原生细滚动条，不用粗装饰线模拟；不隐藏唯一的滚动线索。平台自动隐藏滚动条时以边缘淡化或“左右滑动查看日期”补充，不能覆盖点击区。
- 可滚动区域获得可见键盘焦点，左右键采用原生滚动行为；不改造成复杂 ARIA grid 或日历日期选择器。
- 初次进入且内容溢出时，将今日列定位到可见区域靠左，尽可能留下上一日上下文；用户已滚动后不被倒计时刷新强行拉回今日。
- 3／7／14 天切换继续使用原 URL 参数。切换后保持今日可见；浏览器返回优先恢复用户原位置。无 JS 时从正常起点显示，仍可手动滚动。
- 房间卡片双列只在每列能提供至少约 560px 内容宽度时使用；不足时单列。14 天沿用当前单列规则。外层使用 `min-width:0`、内容不撑破页面。
- 390px 手机下仍保留 104px 的日期列和 44px 住宿条，只在模块内部横向滚动；姓名、绝对日期不能被无限压缩。不要额外显示整屏级横向滚动条。
- 触屏轻扫只滚动，不改期；轻点关联住宿条打开现有客户档案。不能把整条改成 `div onclick`，使用原生链接，支持新标签和键盘。
- 本次不添加吸附动画、自动播放、拖拽、双击编辑或长按菜单。交互反馈最多使用短颜色／边框变化，尊重减少动画偏好。

## 8. 空态与安全

无可见订单时，保留日期头及一条高度适中的空轨道，显示“当前日期范围内暂无订单”；不能显示“全部空房可售”。

缺客户 ID 显示“未关联客人”，不生成假链接；有 ID 缺姓名则显示“查看客人”。模板转义必须保留，不使用真实姓名生成 CSS、DOM ID 或内联 JavaScript。

访问客户仍经过原认证与权限。无论按计划区间怎样变化，都不能自动修改本地状态、标记任务完成、更新订单或发送凭证。

## 一、现状证据

- **机器人现在连的是测试号**
  - 生产当前生效的运行配置（`runtime_config_versions` 第 4 版，09-22 启用）里，企业 ID 掩码是 `····9330`。
  - 小程序接入的 YuMi小管家 在武汉秉善企业微信（企业 ID 尾号 12dd）。
  - 生产轮询最近 72 小时没有失败。`wecom_sync_cursors` 只有一个账号（wkZ 开头），10-19 后没有新消息。
- **秉善这边还没准备好**
  - 自建应用「yumi」（AgentId 1000002）的接收消息服务器、可信域名、企业可信IP都没设置。
  - 「微信客服 → 可调用接口的应用」里没有勾选任何应用。
- **为什么不能直接在后台换配置**
  1. **换配置要先测通**：`services/runtime_config_service.py` 的提交流程会先跑 `RuntimeConfigTester.test`，任何一项失败就拒绝生效，旧配置继续使用。
  2. **测不通的原因是可信 IP**：企业微信的测试会真实调用 `probe_kf_credentials` 和 `probe_agent_credentials`。秉善的「yumi」还没配可信 IP，接口会返回 60020。`_map_error` 把它映射成 `wecom_trusted_ip_required`，测试就失败了。
  3. **配可信 IP 有前置条件**：企业微信要求先设置「可信域名」或「接收消息服务器URL」，才能填可信 IP。
  4. **回调地址校验认的是旧配置**：设置接收消息服务器 URL 时，企业微信会请求 `GET /callbacks/wecom` 做校验。`routes/wecom_callback.py::get_callback_service` 只用当前生效的配置解密，校验时还会核对企业 ID，生效的仍是 9330，所以秉善的校验通不过。
  - 这几步互相卡住。可信域名那条路要求 akros.icu 的备案主体是秉善或者和它关联，目前没有确认。
- **其他已核对的事实**
  - `WeComMessagePoller.run_once` 每 5 分钟刷新一次账号列表，会自动发现新分配的客服账号。只要账号分配好，轮询部分不用改代码。
  - 新账号的游标是空的，第一次同步会从几天前读起（`worker.py::sync_page` 的注释里写了这一点），代码也没有按消息时间过滤旧消息。

## 二、功能点

### M1 运行配置允许「只差可信 IP」时先生效

- **放行条件**：`RuntimeConfigTester.test` 中，必须同时满足：
  - DeepSeek、Hostex（以及开启时的向量检索）全部通过；
  - 企业微信回调本地自检通过；
  - 企业微信的每一项接口检查（客服、应用，以及填了时的客户联系）全部失败，而且失败原因都是 `wecom_trusted_ip_required`。
  - 满足时，整体测试判为通过，允许生效。企业微信那一项在测试结果里单独标成「待配可信 IP」，不算普通的成功。
- **不放行的情况**
  - 只要有一项接口检查是别的错误（如 `wecom_auth_failed`、超时），就照旧判失败。
  - 部分检查通过、部分只差 IP 的混合情况，也照旧判失败。
- **设置页提示**：生效后，设置页的成功提示改为：
  > 已生效，但企业微信应用还没配可信 IP，机器人暂时收发不了消息。请在企业微信后台给应用配置可信 IP。
- **为什么这样放行**：这是新建企业微信应用必经的初始化状态，不放行就永远配不上。生效后回调地址校验就能用新配置，接下来才能配可信 IP。
- **已知天花板**：60020 也可能在获取 access token 这一步就返回，这时 Secret 本身没被验证过。如果 Secret 填错，要等配好可信 IP 后，轮询报 `wecom_auth_failed` 才会暴露。这一点会在代码旁用 `ponytail:` 注释说明。

## 三、风险与决策

- **D1 放行方式**（建议 M1）
  - **备选 A：可信域名**。前提是 akros.icu 的备案主体和秉善一致或关联。这条路不用改代码，但要在服务器根目录放一个企业微信的校验文件。主体对不上就走不通，而且目前没有确认。
  - **备选 B：回调校验兼容待生效配置**。让 `GET /callbacks/wecom` 在旧配置校验失败时，再试一次最近一份「只差可信 IP」的候选配置。这样要多维护一套「候选也能解密回调」的逻辑，暴露面比 M1 大，不建议。
- **D2 版本与发布**（建议走完整发布）
  - 升 1.74.1，补 CHANGELOG 和 `docs/releases/1.74.1.md`。
  - 部署前我会再问你一次。
  - 改动只涉及 `runtime_config_tester.py`、`runtime_config_service.py`（如果需要）和 `routes/runtime_config.py` 的提示，不动 `application.py` 的装配，所以不跑全量测试，只跑运行配置相关的测试。
- **D3 测试号的处理**
  - 9330 测试号从第 4 步起就不再有机器人接待。
  - 旧游标那一行（wkZ）留在库里，不影响新账号，不清理。
- **风险**
  - **旧消息重放**：新账号第一次同步会读到最近几天的消息。机器人可能回复你在测试时发的消息，回复晚了几小时甚至几天。目前没有真实客人用这个账号，按测试号理解可以接受。如果你不接受，要另外加「只处理分配之后的消息」的保护，那是另一个 Spec。
  - **第 4 步到第 6 步之间**：机器人连的是秉善，但接口被 IP 拦着。轮询会按退避节奏记录告警，健康接口可能更差。第 6 步完成后会恢复。
  - **员工通知**：值班员工换成秉善成员后，转人工、投诉等内部通知会发到秉善企业微信里。
  - **回调地址**：第 5 步保存成功后，秉善的消息会通过回调实时到达，轮询变成兜底。如果保存失败，说明第 4 步的 Token、AESKey 或企业 ID 跟第 3 步页面上的不一致，回到第 4 步核对。
- **不做**
  - 旧消息过滤、客户联系 Secret 配置、清理测试号数据。

## 1. 现状证据

### 1.1 目标

把 40 条知识草稿以**停用状态**写入生产知识库，供管理员在后台逐条审核、修改、删除后自行启用。不重新讨论向量检索，不扩展到调参或真实消息测试。

| 项 | 核对结果 |

### 1.3 现有写入路径不能直接用

| 位置 | 事实 | 影响 |
| --- | --- | --- |
| `routes/knowledge.py::KnowledgeAdminService.create` | 固定 `is_enabled=True`，每条单独提交 | 后台新建会让未审核草稿立即参与客人回复 |
| 同文件 `set_enabled` | 另一次独立提交 | 「先建后停」之间存在可被检索的窗口，不可接受 |
| 同文件 `_add_audit` | 审计只记管理员、动作、条目 ID，不复制正文 | 导入工具应沿用同一最小审计口径 |
| `domain/models.py::KnowledgeEntry` | 7 个内容字段 + `updated_by`（外键到员工）；**无唯一约束** | 重复导入需由工具自行比对，且只能串行运行 |

### 1.4 停用条目对客人不可见

- 客人回复的检索只走 `repositories/knowledge.py::SQLAlchemyKnowledgeRepository.list_active`，条件为 `is_enabled` 为真。
- 向量补齐 `application.py::SessionKnowledgeRepository.list_active` 复用同一查询，**停用草稿不会发给向量服务商**。
- 其余不过滤启用状态的查询只有两处：后台知识列表 `routes/knowledge.py` 的分页查询（管理员审核需要看到停用条目）；`save_current_vectors` 按已启用条目的 ID 回写向量。

结论：只要草稿从第一次提交起就是停用，就不会进入客人回复，也不会外发。

## 2. 功能点（按交接方案取默认值）

工具：`src/homestay_bot/tools/import_knowledge_drafts.py`，在 API 容器内以 `python -m` 运行，草稿 JSON 从标准输入读入，不在服务器落盘。

| 功能 | 实现 |
| --- | --- |
| 默认只预览 | 不带 `--apply` 时只读：打印目标后端与库名、输入条数与 sha256、仍含「待填写」条数、分类汇总，以及新建/跳过/冲突数 |
| 严格校验 | 必须恰好 7 个字段；5 个文本字段非空；分类不超过 64 字；关键词为非空文本列表；**全部 `is_enabled=false`**；分类加中英文问题规范化后不重复。任一不合格整批拒绝，错误只报序号和原因 |
| 操作人 | `--admin-id` 必须是存在且在职的管理员，不伪造 |
| 与现有知识比对 | 身份 = 分类 + 中英文问题（统一全半角、大小写、空白）。正文与关键词完全相同则跳过；身份相同但内容不同列为冲突，**整批不写**；不覆盖人工修改，不停用已启用条目 |
| 写入 | 单一事务：PostgreSQL 上先取事务级咨询锁串行化；事务内重新比对冲突；全部以停用状态写入并记录 `updated_by`；每条一条审计（动作 `knowledge.import_draft`，只记条目编号）。任何错误整批回滚 |
| 输出 | 只有数量、分类、摘要与新条目编号；不打印正文、连接串、凭据或本机路径 |

## 3. 风险与决策

| 风险 | 处理 |
| --- | --- |
| 未审核内容进入客人回复 | 从第一次提交起就是停用；客人检索与向量补齐只读启用条目（§1.4） |
| 重复运行或并发运行 | 重复运行按身份跳过；PostgreSQL 用咨询锁串行；其他数据库仅限单人手动运行 |
| 覆盖管理员审核后的修改 | 身份相同但内容不同即冲突并整批拒绝 |
| 部分写入 | 单事务，失败整批回滚；回滚不按分类或标题删除任何已有知识 |
| 草稿含未核实事实 | 17 条仍含「待填写」，只能由管理员补全后逐条启用；工具不自动启用任何条目 |
| 草稿公开 | 草稿文件保持未跟踪，不进入公开仓库；输出与审计都不含正文 |

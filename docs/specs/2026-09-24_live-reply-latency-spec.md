# 联网回复等待时间优化 Spec

版本：R1，2026-09-24。状态：**用户回复「按顺序全部做完」，按本 Spec 顺序实施。**

| 发送 | 0.7 秒 | 0.05 秒 | |

快速安抚（`conversation_service.py::_should_send_fast_ack`）只覆盖补给、保洁、提前入住这类服务请求，联网查询不会先回一句。1.39.13 Spec 里「快速安抚仍会先发出」的说法有误，已追加更正。

## 2. 功能点与顺序

### 第 1 项：联网问题先回一句

在 `_stage_fast_ack` 中，`classify_tourism_query` 判为 `live` 的问题先发一句固定话术，再进入正式处理：

- 中文：「我帮您查一下最新信息，稍等片刻。」
- 英文：「Let me check the latest information for you. One moment, please.」

规则如下：

- 用固定话术，不调用模型，不增加延迟。
- 不传问题原文，因此不会被加上天气开场白；不标记需要人工，因此不会加转人工收尾。
- 沿用现有的安抚登记方式：`fast_ack_sha256` 与 outbox 编号，最终阶段据此确认安抚是否送达。
- 服务请求仍用原来的模型安抚，设施故障仍不发安抚。两类互斥，服务请求优先。

### 第 2 项：联网搜索提速（先实测，按下面的标准取舍）

候选改动，逐个对比：

| 编号 | 改动 |
| --- | --- |
| S1 | 搜索次数上限 `max_uses` 从 2 改为 1 |
| S2 | 请求中关闭思考（`thinking: disabled`）。先确认 DeepSeek 的 Anthropic 兼容接口是否接受这个参数；如果不接受，这一项放弃 |
| S3 | 推荐类正文长度从「700 至 900 字」改为「400 至 600 字」，英文不变 |

## 3. 实测方法与取舍标准（实测前确定，不根据结果调整）

**方法**：在生产 API 容器临时目录里运行，方式同 1.39.12、1.39.13：只读配置，工具用假数据，不写库，不发消息，结束后清理。问题固定为 4 个：「明天天气咋样」「去汉口站怎么走最快」「今晚江滩有灯光秀吗」「武汉最近有什么展览」。基线和每个候选各跑 2 次。

**采用一项改动，必须同时满足以下条件**：

1. 联网搜索耗时的中位数比基线下降至少 20%；
2. 所有运行都成功，没有报错，也没有因为缺少正文而退回；
3. 质量底线全部满足：
   - 天气：写出目标日期、最高和最低气温、降雨情况；
   - 汉口站：写出地铁 2 号线；
   - 灯光秀：写出当晚是否有、时段；
   - 展览：至少写出 2 个带日期的展览；
4. 没有编造设施或服务，正文不少于 150 字。

R1 另加一条：人工通读后，版式和语气与基线相当，没有重复开场白，也没有残留 Markdown。

**组合**：单项通过的改动再组合跑一轮，确认组合后仍然满足以上全部条件。组合不通过时，只采用单项耗时下降最多的一项。

## 4. 风险与决策

| 编号 | 事项 | 处理 |
| --- | --- | --- |
| D1 | 缓存命中时，安抚和答案几乎同时到达 | 接受，只是多一句话。在处理阶段之前无法知道缓存是否命中 |
| D2 | 搜索次数减为 1，复杂问题可能查不全 | 用质量底线把关，不达标就不采用 |
| D3 | 关闭思考可能降低综合能力 | 同上 |
| D4 | 取消精炼后，语气的一致性只靠搜索提示词 | 通读把关；不达标就保留精炼 |

## 6. 实施记录（2026-09-24）

### 第 1 项：联网问题先回一句

`conversation_service.py::_stage_fast_ack` 新增一个分支：服务请求仍用模型安抚；除此之外，`classify_tourism_query` 判为 `live` 的问题发送固定话术 `_LIVE_SEARCH_ACK`，并沿用 `fast_ack_sha256` 和 outbox 编号的登记方式。设施故障照旧不发安抚。

新增 4 项测试：
- 联网问题先发固定话术，不调用模型，并登记摘要。修改前失败、修改后通过。
- 普通问题、设施故障、房源问题不发这句话术。这 3 项修改前后都通过，用来防止误伤。

### 第 2、3 项：实测结果

在生产 API 容器临时目录中运行，4 个问题各跑 2 次，单位为秒。自动质量检查按 §3 的底线执行。

| 方案 | 联网搜索中位数 | 端到端中位数 | 8 次搜索耗时 | 质量检查未通过 |
| --- | --- | --- | --- | --- |
| 基线 | 14.6 | 17.3 | 8.0, 8.3, 19.5, 19.5, 9.9, 14.6, 14.6, 18.6 | 0 |
| S1 搜索 1 次 | 10.4 | 12.4 | 10.4, 8.3, 15.3, 10.2, 8.0, 10.3, 15.8, 13.3 | 0 |
| S2 关闭思考 | 4.8 | 6.8 | 4.4, 4.1, 5.1, 5.6, 4.2, 4.5, 6.1, 6.7 | 0 |
| S3 推荐正文 400 至 600 字 | 10.0 | 11.9 | 9.4, 7.4, 11.4, 10.5, 10.2, 10.7, 9.4, 9.8 | 0 |
| R1 跳过精炼 | 15.3 | 15.3 | 13.4, 9.9, 32.3, 14.3, 16.7, 9.9, 16.4, 16.2 | 0 |
| **S1+S2+S3 组合** | **3.4** | **5.1** | 3.3, 2.8, 3.5, 3.2, 3.2, 3.6, 4.3, 3.7 | 0 |

**决定**：

- **采用 S1+S2+S3。** 三项单独测试时，搜索耗时分别下降 29%、67%、32%，都满足 §3 的标准；组合后仍全部满足，搜索中位数从 14.6 秒降到 3.4 秒。DeepSeek 的 Anthropic 兼容接口接受 `thinking: disabled`。
- **人工通读**：S2 和组合方案的答案都保留了关键事实，比如 2 号线、进站口开放时间、展期、地点、开放时间和预约方式。S2 的展览回答比基线少了一些场馆细节，仍满足底线。组合方案的天气回复更简短，日期、气温、降雨和提醒都在。
- **不采用 R1。** 端到端只快了 12%，没有达到 20% 的标准；而且单次搜索耗时波动（9.9 至 32.3 秒）比精炼节省的约 2 秒还大。不跳过精炼时，回复长度为 272 至 820 字；跳过后为 586 至 1186 字，说明精炼还在压缩篇幅。

**上限**：每个方案各有 8 次样本，只能说明趋势。搜索次数减为 1 后，需要多方来源交叉核对的复杂问题可能查不全。

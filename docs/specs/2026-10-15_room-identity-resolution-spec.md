# 1.70.2 房号身份解析 Spec（v2，待确认）

**目标**：客人原文里点名的房号，在静态资料检索、工具结果筛选、覆盖判定、剩余语义和各个回复出口中，都基于同一份房号身份快照处理。以下几种情况各有确定、可验证的结果：规划漏填或错填房号、写法带不带楼栋、同号不同栋、号码其实是订单号这类标识、房号不存在。

- 起因：
  - 1.70.1 候选门禁 K-周末分日失败，规划漏填 `target_room`；
  - 用户 2026-10-15 要求「开 Spec 处理」，修复要有泛用性，并排查同类问题。
- 依据：
  - [Codex v1 审查](../reviews/2026-10-15_codex-to-claude-room-identity-resolution-spec-review.md) RI-R1 至 RI-R7，Claude 已逐项核实（见 §4）；
  - 证据快照：main `41cc8ea`、生产 v1.70.1。生产只做过只读查询。
- 当前只写 Spec，不改代码。

## 1. 第一段：现状证据

### 1.1 同一个「房号」有四套规则

| 规则 | 位置 | 用途 |
| --- | --- | --- |
| 规划模型字段 `PlanItem.target_room` | `turn_plan.verify_turn_plan`：只要求是数字、且是全文子串 | `deepseek_client._item_property` 决定这一项的检索房源；没填时用本轮会话房源 |
| 本地正则 `item_coverage._ROOM_NUMBER`，经 `clause_rooms` 调用 | 从原文取出 3–4 位数字 | `_fact_layout` 判断小句房号与 `target_room` 的字符串是否相等，不等记 scope_unbound；`clause_target` 用于覆盖判定；`clause_residue` 删数字后得到剩余语义 |
| 房号映射 `find_property_by_room` | 生产：`application.py` 里 `PropertyProfile.room_number == room`，精确相等<br>门禁替身 `reply_regression._MemoryKnowledge`：只要有 property_id 等于该数字的条目就算映射成功 | 房号 → 房源编号 |
| 工具行筛选 `_tool_reply_parts` | 从百居易 `property_title` 取数字，判断问题里是否出现 | 只列点名的房间；没匹配上时由 `_unmatched_room_header` 用另一个正则写「没有找到「X」这个房间，以下是全部房间」 |

## 2. 第二段：修复方案

### 2.1 解析与匹配分为两步

1. **原文房号写法 `RoomMention`**（纯函数，放在 `services/item_coverage.py` 或新的 `services/room_identity.py`，实施时按依赖方向决定）。
   - 输出：楼栋（可空）、号码、原文起止位置。
   - 支持「2303」「2303房（间）」「2栋2303」「2号楼2303」「2-2303」。
   - 数字排除规则沿用 `_ROOM_NUMBER`。
   - 前面紧挨着**标识语境词**的不算房号：订单号、订单尾号、尾号、单号、手机（号）、电话、密码、验证码、编号、身份证、卡号。
2. **房源身份**，从启用房源读取：
   - `room_number` 有值时，以它为准（管理员维护）。
   - `room_number` 为空时，从标题里取**唯一**的「楼栋+号码」或「号码」作为兜底（D-R1）。标题里有多个号码或没有号码，就没有身份。
   - 兜底身份依赖百居易的命名准确性：标题改成另一个号码，身份也跟着变。这是已知上限，**不保证不会错配**（RI-R5）。
3. **匹配**（结果分三种）：
   - 号码相等；客人写了楼栋时，楼栋也必须相等。
   - 只匹配到一个房源：resolved。
   - 匹配到多个房源：如果本轮会话或调试入口的房源在其中，就选它；否则 ambiguous。
   - 没有匹配：unknown。

### 2.2 本轮房号身份快照与优先级

规划核验之后、任何消费方使用之前，为每个计划项及其每个小句计算一次身份，同一轮内缓存。状态有四种：

| 状态 | 含义 |
| --- | --- |
| NONE | 原文没有点名房号 |
| RESOLVED(房源编号) | 能确定是哪个房源 |
| UNKNOWN | 点名了房号，但对不上任何房源 |
| AMBIGUOUS | 点名了房号，但对上多个房源且无法消歧 |

「没有房号」和「有房号但不确定」**不能共用空值**。

计算规则：

1. **小句原文优先。** 小句自己点名了房号，就按它自己的写法解析。多个写法解析到同一房源，视为同一个；解析到不同房源，记为多房号（见第 4 条）。
2. **本项原文其次。** 小句没写房号时，看本项原文：恰好只解析出一个房源就继承；出现多个不同房源时，这个小句无法确定，按 scope_unbound 处理。
3. **规划字段只作提示。** 本项原文没有任何房号写法时，`target_room` 必须与全文中某个房号写法的号码相等（按 token 比较，不按子串），才按那个写法（含楼栋）解析并继承；否则忽略。规划值与本项原文点名的房号冲突时，以原文为准（RI-R3）。
4. **多房号的处理。**
   - **静态取证**：一个小句里有多个不同房源时，按 scope_unbound 处理，保守不作答；本版不做逐房检索和证据绑定。
   - **工具行**：按解析出的房源集合筛选。
   - 不同小句各自点名不同房间时，各按自己的房源；小句房源与本项检索房源不同时，按现有规则记 scope_unbound。
5. **兜底。** 原文和规划都没有房号时用会话房源，即现状。

所有消费方都改为读这份快照，并按房源编号比较：

| 消费方 | 改动 |
| --- | --- |
| `_item_property` | 读快照 |
| `_fact_layout` 小句一致性判断 | 改为比较房源编号 |
| `clause_target` | 改为接收快照 |
| `_tool_reply_parts` 工具行筛选 | 按行的 `property_id` 筛选，不再按标题数字（RI-R1） |
| `_unmatched_room_header` | 只在快照为 UNKNOWN 时出现，不再自己用正则判断 |
| `clause_residue` | 删除房号写法的完整原文区间（含楼栋、「房间」等部分），不全局删除「栋」字，「几栋楼」「楼栋入口」照常保留（RI-R2） |

正常出口、协议回退出口、跨项复用都用同一份快照。`service_fee_followup` 不改（RI-R7）。

### 2.3 UNKNOWN 与 AMBIGUOUS 的结果

| 路径 | UNKNOWN | AMBIGUOUS |
| --- | --- | --- |
| 静态取证 | scope_unbound：回未确认，不转交，不用会话房源顶替（D-R3） | 同左（D-R2） |
| 工具行 | 保留现有说明：「没有找到「X」这个房间，以下是全部房间」，再列出全部房间。房态是带房名的真实数据，列出后不会被误当成某间房的答案 | 列出各候选房源，每行带自己的房名，不额外说明 |

静态答案不带房名，所以 UNKNOWN 和 AMBIGUOUS 都必须保守处理；工具行逐行带房名，可以列出。两条路径因此规则不同。

### 2.4 门禁替身对齐与成功条件（RI-R6）

- `_MemoryKnowledge.find_property_by_room` 改为走同一个解析器。资料夹具新增房源身份表，按生产 `property_profiles` 的形态包含：
  - room_number 为空、只靠标题兜底的房源；
  - 带楼栋的 room_number；
  - 两栋同号的房源；
  - 9999（登记为 resolved，用于 K-周末分日）。
  UNKNOWN 示例使用身份表里确实不存在的号码。
- 新增门禁场景：
  - **K-带栋房号**：「2栋xxxx」写法，资料挂在房间上；
  - **K-同号异栋房态**：工具只列所问那一栋。
  与 K-周末分日一样，先进 known_failures。
- **修复完成条件**，三项分别记录，不互相替代：
  1. 确定性回归：用合成规划**强制漏填或错填**房号，证明补齐分支、优先级和三种结果。
  2. 目标场景：K-周末分日、K-带栋房号、K-同号异栋房态，限定门禁中各三次全过并晋升 must_pass。任一未达到即修复未完成，**不得发布**；需要例外时，记录用户的明确决定。
  3. 全量 all：无退步。
- 至少一条集成测试使用真实 SQLAlchemy 仓储和临时 SQLite，覆盖带楼栋、为空靠标题、同号异栋三种房源。

## 3. 第三段：风险、验收与决策

### 3.1 风险与边界

- **行为面变宽**：生产上原来映射不到的房号，现在能映射了，房间专属资料会进入更多回答。涉及知识检索和公共流程，需要全量 all 门禁。
- **标识数字**：标识语境词表只能排除明确的写法。没有语境词的裸号（例如「2303能退款吗」）仍按房号处理；如果恰好有这个房号，就会选中这个房源。这是已知上限。
- **标题兜底**：依赖百居易标题命名。改名、重号会导致错配或歧义，room_number 填写后不再依赖标题。补填生产 room_number 属于生产数据操作，另行授权。
- **不再转交**：UNKNOWN 和 AMBIGUOUS 的静态问题不再转交管家。写错房号的客人只会得到未确认。
- **不改**：规划提示词、日期、Hostex 查询参数、数据库结构、追问服务收费逻辑。

## 5. 实施期修订（2026-10-15）

用户回复「都走推荐，直接做完写报告」，即 D-R1 至 D-R5 按推荐执行，并授权开始编码。实施与 v2 有两处偏离：

1. **`turn_plan.verify_turn_plan` 不改。** 规划房号的消费方只剩 `DeepSeekGuestAssistant._item_room`，它只在规划房号与全文某处房号写法的号码完全相等时才采用，所以「02」这类子串在消费端就被忽略了（单元测试 `test_planner_room_inherited_by_clause_without_room` 用的是「03」）。`service_fee_followup` 只判断规划字段是否为空，该分支本身只在原文没有房号时才会进入（RI-R7）。在核验层再改一次是重复规则。
2. **门禁新场景改为静态的 K-同号异栋（同号两栋、没有本轮房源时保守不作答），不做「房态」版。** 原因：在百居易夹具里加两个同号房源，会改变现有房态、目录、「最便宜」类场景的全部房间输出，波及 must_pass 基线。工具行按楼栋筛选改由单元测试 `test_tool_rows_follow_the_building_not_the_number` 覆盖。

## 6. 实施审查修订（2026-10-15，Codex IRI-R1 至 IRI-R4）

依据：[Codex 实施审查](../reviews/2026-10-15_codex-to-claude-room-identity-implementation-review.md)。四项均已复现并修复。以下政策补入 §2，属于同一解析闭环，没有扩大功能。

1. **楼栋严格匹配（IRI-R1）**：客人写了楼栋时，房源身份的楼栋必须相同；楼栋未知不能证明相同。本轮房源只在满足全部显式约束的候选里消歧。只写号码的提问照常能匹配带楼栋的身份。
2. **混合状态（IRI-R2）**：`RoomResolution` 保留全部已确定房源、各歧义候选和全部对不上的写法，结果与写法顺序无关。状态优先级为 ambiguous > unknown > multiple/resolved。静态取证在任何不确定状态下都不作答，政策不变；工具行按「已确定加候选」的集合筛选，对不上的写法逐个说明「没有找到」。
3. **空目标失败关闭（IRI-R3）**：有明确目标集合时，筛选结果为空就不再退回全部房间，也不进全店最低价，由现有「未返回可用资料」或覆盖判定说明未查到。只有完全没有目标时（没点名房号，或点名的房号全部对不上），才列出全部房间。
4. **读取失败与「不存在」分开（IRI-R4）**：`KnowledgeService.room_profiles` 在仓储不支持或读取失败时返回空值；解析结果为新状态 `unavailable`。工具行说「暂时无法核对「X」对应的房间」，不说「没有找到」；静态取证不作答、不转交。成功读到空表时仍判为 unknown。
5. **同类问题（审查过程中发现）**：只问房态、房价、目录且没有剩余内容的小句，房号无法确定时不再补一段静态未确认，由工具覆盖判定负责（`_item_evidence_plan`）。剩余语义把「302和9999」「302、401」这类并列房号连同连接词整段删除（`_ROOM_GROUP`）。

## 7. 复审修订（2026-10-16，Codex IRI-F5、IRI-C1、IRI-C2）

1. **斜杠日期的数字边界（IRI-F5）**：`_ABSOLUTE_DATE`、`EXPLICIT_STAY_DATE_PATTERN`、`_CONCRETE_DATE_PATTERN` 的「月/日」分支前后都要求不是数字。「302/401」里的「02/40」不再被当成日期，房号解析、日期屏蔽、剩余语义和周末两种住法共用这一规则。无效的真实日期（如「2/30」）仍判为无法绑定。住宿日期语言不扩展。
2. **逗号切开的纯房号片段（IRI-C1）**：除房号和日期外没有剩余内容的小句，如果同一项里另有小句在问工具事实，就不再补静态未确认，由工具覆盖判定负责。带剩余内容的小句照常保留，例如「302，停车怎么收费」「302有房吗，401有浴缸吗」。切句规则不改。
3. **发布记录（IRI-C2）**：追加带日期的风险更正，不改写历史文字。

## 8. 复审修订（2026-10-16，Codex IRI-F6）

§7 第 2 条改为下面的覆盖承诺。原规则只看「同一项另有工具问法」就豁免，工具只返回其中一间房时，另一间会被悄悄漏答，所以替换掉。

- `DeepSeekGuestAssistant._clause_rooms` 识别枚举组：**连续的纯房号片段 + 紧随其后的工具问法**。
  - 纯房号片段：除房号和相对日期外没有剩余内容；不带明确日期，也不是无法绑定的日期。
  - 工具问法的覆盖目标改为整组的全部房号，由现有的 `clause_target` 和 `evidence_covers` 逐个房源核对；工具缺了哪间，就照常报 tool_uncovered（不可转交）。
- 只有已并入覆盖目标的片段，才取消它的静态未确认。
- 以下情况不并入，保留原有的保守处理：
  - 片段带明确日期；
  - 片段后面不是工具问法；
  - 独立目标，例如「302，401有房吗，501多少钱」里的 501 自成一组。

## 9. 复审修订（2026-10-16，Codex IRI-F7、F6 展示、IRI-C3）

§8 的枚举组交接补充以下三条，覆盖对象、日期、展示和静态职责共用同一份交接信息：

1. **日期（IRI-F7）**：只有能证明整组问的是同一天，才把片段并入接收问法。
   - 允许并入：片段没写日期；或片段日期能按冻结的本轮今日解析为单日，并与接收问法的入住日相同。接收问法没写日期时，取本项规划的入住日。
   - 不并入，保留保守提示：无锚点的「第二天」、无法解析的相对时间、明确日期、日期不同、接收方日期未知。
2. **展示（F6）**：枚举组的未覆盖说明和 GapUnit 文本，引用从片段开头到接收问法结尾的整组原文（`_ItemLayout.coverage_texts`），不再只写已查到的那一句。缺口编号仍按接收问法的区间。
3. **静态职责（IRI-C3）**：已交接的片段在三处都跳过：逐句静态取证（`_item_evidence_plan`）、可转交缺口开放（`_gap_unit_offers`）、未确认补段。真实的独立问题照常保留。

## 10. 门禁发现的修订（2026-10-16，候选 all 门禁 AV-102）

- **现象**：rc-1.70.2-2 的 all 门禁里，AV-102「我想订102，今晚和明晚两晚」三次失败两次。失败时主模型没有调用查房工具，只介绍了房间并说「我先帮您查一下」。
- **定位**：用同一问题和同一份门禁资料，对 v1.70.1 与当前代码各跑一次，比较发给主模型的第一次请求。规划把它判为住宿查询、又没填房号和日期时，新代码会向模型开放资料缺口 `{"text": "我想订102"}`；旧代码在规划填了房号时同样会开放。
  - 根因一：剩余语义只删房号，留下订房意图词「订」和连接词「和」。
  - 根因二：住宿项里没有工具锚点的小句，不看剩余就被当成资料问题。
  这和 E2 是同一类问题。
- **修复**：
  1. `clause_residue`：剩余只剩订房意图词（订、预订、预定、订房、一间）和连接词时，视为没有剩余。「怎么预订」「预订要交定金吗」照常保留。
  2. `DeepSeekGuestAssistant._asks_static`：住宿、目录项里没有工具锚点的小句，只看剩余；资料缺口开放、静态取证、补未确认三处共用这条规则。静态事实项不变。
  3. `_clause_rooms` 新增 `orphans`：后面有工具问法却没能合并的房号片段（日期不一致、带明确日期），继续保留保守提示，不随第 2 条一起变成静默（保持 F7）。后面没有工具问法的房号片段（「我想订102」）只是订房意图，不开放缺口。

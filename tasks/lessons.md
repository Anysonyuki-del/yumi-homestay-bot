# Lessons

> 长期防回归规则统一维护在 [[homestay-bot/YuMi民宿AI开发经验与防回归手册|YuMi 民宿 AI 开发经验与防回归手册]]；本文件继续记录新增的简短教训，后续定期归并到手册。

## 企业微信旅游回复

- 客人可见回复不要包含网址、Markdown 链接或裸链接。
- 联网来源仍用于后台校验；客人侧只显示查询日期和最多 5 个去重来源名称。
- 验收测试必须同时断言不存在 `http://`、`https://` 和 Markdown 链接格式。
- 当前日期必须在搜索前明确传给模型，不能只在生成答案后追加；“近期”信息优先验证未来 15 天并排除明确过期来源。
- 演出使用具体日期校验，展览还要兼容覆盖当前窗口的月度展期；省略年份时只能依据明确窗口做确定性补全。

## 企业微信异步投递

- `kf/send_msg` 返回 `msgid` 只代表平台接口受理，不代表客人已经看到；必须继续消费 `msg_send_fail` 回执。
- 异步失败处理不能只覆盖客诉和生命周期提醒，普通机器人回复也要记录失败状态、从模型上下文排除，并最多自动重试一次。
- 重试仍失败时必须登记脱敏人工跟进通知；测试验收要同时检查本地任务完成、平台失败回执和最终人工告警。
- 企业微信 `msg_send_fail.fail_type=13` 官方含义是“安全限制”；遇到该类型不得原文重试，应改发不含外链、地址和敏感细节的短兜底，并保留人工跟进记录。

## 自然日期理解

- 武汉客服必须掌握武汉本地当天日期，并自主换算“今天、今晚、明天、明日、后天”。
- “某日入住、次日退房”和“某日住一晚”应直接换算并查询房态，不得再次要求客人提供绝对日期。
- “房源列表”“有哪些房型”等简短追问必须沿用上一轮已明确的入住退房日期并重新查询房态，不得脱离上下文要求客人重复说明。
- 只有相对日期确实无法唯一推断入住或退房日期时，才向客人追问。

## 知识库缺口

- 普通问题缺少审核知识时，应由大模型给出合理回答，不因低置信度自动转人工。
- 民宿专属信息缺失时，大模型明确未确认并提供替代建议，同时提醒员工补充知识库；会话保持机器人模式。
- 交易问题无法确认时通知员工核实，但在员工真正回复前继续保持机器人模式。
- 普通问题也要审计模型主动夹带的民宿房型、设施和公共空间宣传；客人没有提问不代表模型不会自行虚构专属事实。
- 删除未经审核宣传后必须重排列表编号并清理残留销售话术，不能把断裂列表直接发给客人。
- 高频缺失问题达到提醒门槛后，应先由大模型生成可编辑的 FAQ 参考草稿，再把草稿、脱敏示例和待核实项发给管理员确认；不得只发送问题清单，也不得自动启用草稿。

## 对话上下文时序

- 企业微信客人消息和机器人回复必须统一使用 UTC 时间入库。
- 模型上下文按系统实际处理顺序恢复，不得直接混排外部 UTC 时间与本地时间。
- 企业微信端到端验收必须检查回复语义是否对应最新一条客人消息，不能只检查“有回复”。
- 企业微信消息可以高频补拉，但客服账号列表必须单独低频缓存；不得在每轮消息检查时重复调用账号列表接口，否则会触发 `45009` 限流并造成消息延迟。
- 客户上下文使用最近七天原文加脱敏摘要；摘要成功后才能删除过期原文，摘要失败必须保留原始消息。

## 房间状态与员工权限

- 当前房间任务的执行员工在完成任务、检查清单和规定照片后，可以把房间从“待检查”改为“可入住”；不能把该权限错误地限制为只有管理员。
- “可入住”只触发确定性凭证安全校验，AI 不得直接修改房间状态或绕过订单、客户、房间和日期匹配条件。
- 普通员工只查看分配给自己的任务及必要资料，不能因具备房间状态操作权限而获得全部 CRM、订单金额或其他房间凭证。

## 百居易接口契约

- `/listings/calendar` 响应中 `restrictions` 不是必填字段；百居易可能省略它或返回 `null`，客户端应归一化为空字典。统一信封必须按 `error_code` 判断成功，不能只看 HTTP 200。
- 百居易后台的“可入住”运营状态、房间主日历 `/availabilities` 和渠道库存 `/listings/calendar` 是三种不同口径。客人询问能否新订时必须以指定住宿晚的主日历为准；出现后台观感冲突时，应同时核对已接受订单的入住/退房区间，不能把“当前住客可入住”解释为“可接受新订单”。

## 模型失败恢复

- 客人侧“已安排、马上安排师傅、一定解决、彻底解决、保证送到”等都属于未经人工确认的结果承诺，不能仅靠模型提示词规避。所有客人可见出口必须经过本地确定性安全策略；需要人工时只能说明会立即联系管家，并保留必要的低风险自助建议。
- 系统生成的固定失败文案及其未成功回答的问题不能再次交给模型，避免模型把故障处理当作正常答案模仿。
- 外部模型重试必须记录轮次和异常类型，但不得记录客人正文、模型原始响应或密钥。
- DeepSeek V4 Flash 同时启用 JSON 结构化输出和工具时，过长的多轮历史可能返回纯空白；上线验收应使用真实长会话重放，而不只验证单轮契约。
- DeepSeek 旅游搜索必须保留深度思考；思考块和搜索结果不按客人回复预算处理，不能把无正文简单归因于思考耗尽预算，也不能用关闭思考作为修复。必须依据完整真实响应的 stop reason、usage 与内容块时序重新定位。
- 候选连接测试和生产模型请求不能共用同一个短读取超时：候选探针应快速失败，生产网页搜索需允许数十秒但保持明确硬上限。排查“直接请求成功、worker 失败”时必须用生产相同的受控 transport、timeout 与 SDK 复现。
- 即使只携带三条历史，DeepSeek V4 Flash 仍可能偶发返回纯空白；重试不得原样重复请求，应降级为只携带已脱敏的当前问题。
- “限制回复长度”应优先让模型精简选优并保持完整语义，机械截断只能作为外部模型失败后的绝对上限兜底。
- 房态工具已成功执行但模型最终 JSON 校验失败时，不能把整条消息判为不可用；应保留已查询日期并返回不猜测房型的安全回执，同时提醒员工确认具体结果。
- 百居易已返回实时房态后，不能再由“民宿专属知识未审核”分支覆盖工具结果；本地归一化必须把已验证的工具结果标记为已覆盖事实。
- 快速安抚必须按意图门控；房间介绍、普通 FAQ 等信息问题直接排最终回复，不发送泛化“正在通知管家”的安抚，服务处理、补给、维修等需要等待的请求才发送。
- 房间介绍和房源名称必须调用百居易 `/properties` 的只读数据；房态结果要把 `property_id` 与 `title` 一起交给模型，客人侧优先显示真实房源名称，不能显示内部编号或凭空描述。
- 客人可见回复不能泄露“以员工确认为准”等内部流程；任务类回复应表达已收到、正在安排和后续反馈，同时不虚构已完成。
- 首次回复速度优化不能只把安抚文本写进同一事务；必须先提交安抚 outbox 和最终处理任务，再执行耗时模型、百居易或联网调用。
- 快速安抚可以调用无工具短模型，但必须固定温暖民宿提示词、限制输出只表达收到和处理中，并从正式模型上下文排除安抚消息。
- 分阶段出站任务不能依赖事务内序号生成幂等键；同一来源消息必须显式区分 `ack` 与 `final` 阶段，并让重复最终阶段在消息记录层幂等跳过。
- 异步最终回复必须携带来源消息边界；只读取运行时最近消息会让旧任务回答新问题，且单 worker 串行处理会让耗时最终生成阻塞后续安抚。

## 客诉人工复核

- 客诉识别应在普通模型调用前完成；客人侧只发送固定安抚，分析和草稿只能进入后台复核。
- 客诉分析输入必须脱敏且不携带客人身份；模型不得自动判断责任、承诺退款赔偿或输出链接。
- 员工发送客诉草稿前必须经过后台编辑页的权限、CSRF、版本和审计校验，企业微信通知不能直接替客人发送。
- 修改人工接管门控时，必须同时覆盖同步入口和后台延迟入口；两条路径应以当前消息的风险为准，不能仅凭会话处于 `HUMAN_ACTIVE` 就丢弃房态、旅游等独立低风险回复。
- DeepSeek 客诉 JSON 的布尔字段可能返回说明句而不是 JSON boolean；退款和平台升级标记必须根据本地原因及最新客人消息确定性计算，不能信任模型字段、模糊猜测或让其阻断草稿生成。
- DeepSeek 也可能把责任风险文字返回成布尔值；非文字责任风险必须回退为“待核实”，明确保留人工判断，且不能因此让整份客诉草稿失败。

## 全仓安全审计新增规则

- 客诉唯一键竞争必须使用事务保存点或原子 upsert；不能在共享业务会话中直接 `rollback()`，否则会连带丢失同事务消息和出站任务。
- 日志脱敏必须安装在实际输出 handler；父 logger 的过滤器不会自动处理子 logger 传播的记录，格式字符串中的令牌也要在渲染后过滤。
- 结构化日志格式化器可能依赖 `LogRecord.args` 的固定协议；Uvicorn 访问日志必须保留五元参数，只在原 URL 参数中脱敏，不能预渲染后清空 `args`。回归测试必须使用真实 `AccessFormatter`，不能只调用 `record.getMessage()`。
- 非文本企业微信消息只保存受控的 `media_id` 等最小元数据，禁止把图片 URL、语音正文或文件内容写入模型上下文；后续导入入住指南必须走独立下载、类型校验和人工审核流程。
- 异步出站状态只能在平台返回真实消息编号后标记成功；入队、失败和成功状态要可区分并推进版本，避免后台显示幽灵发送。
- SQLite 迁移若需要新增唯一约束或删除列，必须使用 Alembic `batch_alter_table`；直接 `op.create_unique_constraint` 在本地 SQLite 会失败。
- 日志过滤不能只处理 `record.args`；直接字典消息和 `logger.extra` 同样要递归脱敏，并补充 handler 输出边界测试。
- 依赖安全解析库时，运行依赖和 mypy 类型桩要分别声明；本机服务升级后必须检查运行虚拟环境，而不能只检查开发环境。

## 后台与迁移边界

- 后台列表不能只在服务层加固定 `limit`；必须把页码、稳定排序、`limit + 1` 下一页判断和模板导航一起验收，避免管理员永远只能看到前 50 条。
- Alembic 离线 SQL 生成不能执行依赖现有数据的查询回填；数据回填只在线执行，离线模式仍必须生成完整 DDL。
- 本地启动脚本执行迁移前必须使用应用同一套配置解析数据库地址，并在版本落后时备份 SQLite 数据库和私有上传目录；不能依赖 `alembic.ini` 的示例连接。
- 面向老板的后台不能只聚合数据库 CRUD；需求中提到“方便调试基础内容”时，应同时设计只读诊断、配置完整性检查和安全测试动作，并用登录、角色、审计和脱敏隔离高风险数据。
- 运营后台 UI 需要同时满足温暖民宿品牌感与高密度管理效率；移动端宽表应转卡片或安全横向滚动，表单必须有明确标签、提交反馈、错误提示和防重复提交。
- 后台身份范围必须先明确再设计角色菜单；若用户从“管理员与员工共用”改为“仅老板登录”，应立即反向同步 Spec，隐藏员工入口，不能继续沿用多角色后台假设。
- 在既有大型仓库中禁止对整个 `src tests migrations` 直接运行格式化器；只能对白名单中的本次触碰文件执行格式化。格式化前后都要保存并核对 `git status --short` 与 `git diff --name-only`，发现范围扩大立即停止，不得让机械格式改写混入功能提交。

## 认证前的容量与限速边界

- 任何"每主体上限"落到未认证路径时都会退化成全局上限。匿名 CSRF nonce 的作用域曾是 `(purpose, admin_id=None)`，8 次未认证请求即可占满 `max_active_per_scope`，让真实管理员 15 分钟拿不到登录令牌。未认证资源必须绑定浏览器会话等自身标识，并额外设置匿名子上限，防止反复更换会话耗尽认证用户所需容量。
- 限速的每 IP 上限不等于可用性保障；只要多类请求共用同一个全局桶，成本最低的那类就能挤掉最关键的那类。登录页签发令牌与凭据提交必须使用各自独立的全局计数，且默认参数要指向本类别常量，不能误用全局常量。
- 单进程内存限速只能挡单机滥用；分布式来源打满某类别全局上限仍会影响该类别，公网部署前必须明确记为残留风险，不得宣称已解决。
- 一次性令牌的"只能消费一次"和"只能被签发它的浏览器消费"是两条独立性质。测试若用无效 Cookie 配真实 token 断言成功，实际固化的是跨浏览器可复用的缺陷；两条性质必须各有独立测试。

## 后台响应头与角色校验

- 敏感响应头不能逐路由手工补。`Cache-Control: no-store` 曾只覆盖 5 个路由，渲染客人档案的 `customers` 和客诉正文的 `complaints` 全部遗漏。统一用中间件按路径前缀覆盖，并保留静态资源与公开健康检查不受影响。
- 为流式响应补响应头要用纯 ASGI 中间件；`BaseHTTPMiddleware` 会包装 `FileResponse`，影响私有附件下载。
- 路由取出 `role` 却不判断等于没有权限校验。客诉详情页与四个写动作曾只校验登录，靠"普通员工无法登录"这一外部前提兜底；一旦恢复多角色登录即刻越权。角色边界必须在路由内显式断言，不依赖当前登录链路的偶然收敛。
- 日志脱敏正则要按凭据实际命名逐个核对。`api[_-]?key` 不匹配 `encoding_aes_key`；补规则时也不能放宽到裸 `key`，否则会误伤 `dedupe_key`、`event_key` 等业务幂等键，需同时补"不应脱敏"的反向测试。

## 部署凭据记录

- 首次登录密码、临时密码和恢复码也属于真实密钥，不得写入 `tasks/todo.md`、部署记录、测试输出或 Git 提交；交付后只记录“已完成强制修改”等状态，验证时仅查询 `must_change_password`、`session_version` 等非敏感元数据。
- 公开仓库一旦出现明文凭据，必须先轮换凭据并验证旧值失效；删除当前文件不能清除 Git 历史，历史重写必须作为独立破坏性操作，经明确确认后执行。

## CRM 自动入住备注

- 自动入住备注属于订单派生视图，必须与员工自由备注分栏保存和展示；不能覆盖、拼接、搜索或同步员工备注。
- “最新订单”不能只按订单创建时间判断：正在入住的订单优先；退房后按首次观测到的实际退房日保留三天，第四天才允许切到下一笔未来订单；没有未来订单时继续显示最近一次有效入住。
- 本地订单缺少平台实际退房时间时，新完成订单应幂等记录首次观测日；上线前历史完成订单只能明确回填计划退房日，不能伪造真实退房时间。
- 企业微信员工通知中的客人定位信息应优先使用 CRM 自动入住备注，再回退员工备注，最后才使用客人名称；房间号和平台 UID 都不应作为管理员的首要识别信息。
- 延迟回复链路不能只依赖消息 ID 防重：同一入站消息的快速安抚和最终模型回复是两个合法发送阶段；最终文本经过统一安全策略后若与已发送安抚完全相同，必须按正文摘要抑制第二次发送，但新的排障建议仍需保留。
- 客人可能把一个问题连续拆成多条发送；普通文本必须先等待三秒静默，再按系统入库顺序合并并判断是否需要安抚，不能对每个片段分别安抚或分别调用模型。紧急、客诉和人工规则既要逐条立即识别，也要在合并后复核跨消息拆词；原始消息仍逐条保存。

## 旅游联网默认地点

- 所有旅游联网搜索在客人未明确地点时默认按武汉市查询；天气、活动、门票、开放时间、交通和路线都要把默认地点写入搜索请求，不能只依赖系统提示。客人明确指定其他城市时必须保留原地点。

## 客人回复统一口吻与高危边界

- 模型提示词只能引导风格，不能作为唯一保证；所有客人可见出口必须共享一个幂等的确定性回复策略，发送正文与重复回复摘要必须使用同一份最终文本，员工内部通知不经过该策略。
- 管家口吻应温暖、简洁、可靠，但不能为了亲和改写事实。日期、地点、温度、降雨、价格、房态、来源和安全步骤必须原样保留，未知信息不得补写。
- 高危转人工不是普通服务安抚：必须理性、客观、中立，不道歉、不判断责任、不承诺结果或时间，也不能声称人员已经派出、正在赶来或必然到场。
- 高危场景只允许说明“立即联系值班管家跟进处理”；火灾、燃气等现实危险必须先输出撤离、报警等安全动作，再说明已记录并联系值班管家。

# Lessons 收件箱

只记录尚未归并、且已有代码或测试依据的新教训。

教训确认长期有效后，应归并到 [YuMi 民宿 AI 开发经验与防回归手册](../YuMi民宿AI开发经验与防回归手册.md) 的唯一对应章节，并从本文件删除正文；历史由 Git 保留。

- 发布与部署验收必须先确认用户所指环境，并以用户实际访问的生产 URL 为最终依据；本地包版本、Git 标签和本机进程只能证明本地状态，不能替代生产容器、数据库迁移、健康接口及真实浏览器页面的联合验证。
- 已完成且验证过的小改动在用户明确要求继续发布后，应直接执行版本、日志、标签、备份、部署和验收，不重新拆成多段 Spec 或重复 HARD-GATE。
- 部署校验不得根据短哈希猜测完整提交号；必须由 `git rev-parse` 读取实际对象后再传给服务器比对，避免正确的 fast-forward 被错误校验中止。
- 用户明确指出某条实际回复的问题时，应以该原文和缺失行为为主线重新取证；不得把同一会话中的相邻异常误当成用户报告的核心故障。
- 设备或设施故障回复默认不追问客人补充现象；应直接给出不拆机、不承诺结果的简单安全排查建议，并同步提交人工处理。
- 用户已确认一类通用业务规则后，不得继续依赖需要逐个补丁的固定设备名单；新设施应进入受控的规则候选与自动升级流程，低风险处理可自动生效，危险操作和经营决策仍保留确定性安全门。
- 民宿垂直客服的自动泛化必须先使用项目领域边界：官方客服会话中的故障默认按房间、公区或民宿提供物品理解，但明确属于客人私人物品或外部场所时必须排除，不得创建民宿维修任务。
- 生产镜像构建应把仅依赖锁文件的安装层放在版本文件和业务源码复制之前；否则补丁发布也会使依赖层失效，在生产网络较慢时被迫重新下载全部依赖。发布前应先检查 Docker 缓存边界，仍保留哈希锁和项目无依赖解析安装。
- 设施故障自动泛化不能把固定设备名单替换成不断扩张的安全档位；应由固定民宿提示词生成与当前故障匹配的简单建议，本地只保留危险操作、虚假承诺、业务提交状态和紧急事件安全门，模型异常时统一降级并提交人工。
- 开放式设施故障不能由枚举式关键词正则决定主路由；模型已经基于当前问题返回结构化设施归属时，应由该语义结果进入待确认维修流程，本地正则只承担明确排除、安全门和模型不可用兜底，避免换一种说法就绕过人工任务。
